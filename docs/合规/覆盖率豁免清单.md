# 覆盖率豁免与真机验证项清单

> **数据源：`docs/合规/覆盖率豁免清单.json`**（本文件是说明与摘要，数据以 JSON 为准；
> 两者由 `tests/unit/quality/test_coverage_exemptions.py` 守卫，不允许脱节）

## 这份清单用来回答什么

覆盖率报告只能告诉你"哪些行没被执行过"，但不能区分这两件性质完全不同的事：

- **该测但没测**——属于质量债，要继续补；
- **离线测不了**——需要真实 SoftHSM、真实 Redis 语义、真实对象存储、真实 GPU 或真实
  PostgreSQL 才能验证，硬补只能得到"mock 出来的绿"。

本清单登记的是第二类，逐条写清**离线已经覆盖到哪一层**、**现场要验什么**。

## 明确声明：本清单不参与降低门禁

CI 的覆盖率门禁（整体 80%、核心 81%，见 `pyproject.toml:32` 与
`.github/workflows/ci.yml`）一律对整个代码库计算，**与这份清单无关**。清单里出现某个
模块，不会让它的未覆盖行从门禁统计中消失，只是为发布报告提供一个可解释的边界。

### 刻意不列入本清单的项

- `app/inference/sustained_load_test.py`（0%）：纯现场长稳压测脚本，**没有任何"离线可覆盖
  的那一层"**。它留在清单里只会稀释清单的可信度——其验证动作归入现场验收清单。
- `app/config/redis.py`（降级场景⑦ Redis 主从切换秒级接管）：离线只能验证"Redis 不可用
  时降级"（灰度计数退化为进程内计数、必须留痕、Redis 恢复后立刻改走 Redis —— 已在
  `tests/integration/int/test_degradation_scenarios.py` 覆盖 3 条）；而"**切换的秒级接管
  时序 + 切换期间计数连续性**"只能由真实 Redis 主从演练证明。现场动作：做一次主从切换
  演练，记录切换耗时与切换前后计数是否连续。
- `app/services/safety_gateway_client.py`（降级场景③(b) 主服务崩溃 + SG 存活）：其**可离线
  层**已覆盖（SG 不可用→fail-closed 拒绝输出、短暂不可用→队列等待恢复、持续不可用→
  超时/熔断 E4005）；剩余部分（主服务进程整体崩溃期间，独立进程的 SG 仍拒绝输出）依赖
  真实进程编排。现场动作：kill 主服务进程，验证 SG 仍存活并返回 E4005。

（曾列入的两条已被移出：`app/services/dicom_storage.py` 补测到 95% 后按"达标即移出"

## 守卫机制（防止清单变成逃避口）

`tests/unit/quality/test_coverage_exemptions.py` 断言：

1. 每条都指向**真实存在**的模块文件；
2. 类别必须在白名单内，且每条必须写清"离线已覆盖到哪一层"（不足 20 字不收）；
3. 真机项必须给出**可执行的现场验证动作**，不能只写"需真机"；
4. **条目数受棘轮约束**——新增必须显式修改 `EXPECTED_ENTRY_COUNT` 并说明理由；
5. 条目覆盖率一旦 **≥90%** 必须移出清单（达标就说明离线能覆盖到位，留着就是占位掩护）；
6. 本说明文档必须列出清单里的每个模块。
