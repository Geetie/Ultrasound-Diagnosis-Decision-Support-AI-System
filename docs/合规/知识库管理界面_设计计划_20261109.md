# 知识库管理界面：设计计划

> 2026-11-09｜用户要求「知识库方面需要一个界面来管理，详细系统性地根据需求设计」

## 一、这个界面到底要解决什么问题

**核心矛盾**：知识库里同时装着多套权威指南，它们在同一问题上给出不同答案。
不同医院认的指南不同（三甲认中华医学会 C-TIRADS、基层认卫健委规范）。

**现有 `KbManagementPage.tsx` 只做了一件事**：列出 kb_version 与变更通知（且是 mock）。
**它回答不了医生最关心的三个问题**：
1. 我的知识库里有哪些**权威来源**？
2. 我们医院用的是哪几套？
3. 这**两套冲突**的地方，我们怎么定？

**所以这个界面不是"版本管理"，是「语料权威性的治理台」。**

## 二、三类用户，三种任务

| 用户 | 他要做什么 | 界面必须提供 |
|---|---|---|
| **科室主任 / 医务处** | 决定本院以哪几套指南为准 | 启用/停用某套语料；看到"停用后影响什么" |
| **报告医生** | 知道某条结论依据哪份指南 | 查某语料覆盖了哪些主题；看两套的分歧清单 |
| **信息科 / 运维** | 语料更新、重建索引 | 版本、来源、chunk 数、构建时间；冲突扫描结果 |

## 三、设计计划（token 系统）

### 3.1 色彩

这个界面的主题是**「多源权威性与分歧」**。要让人一眼看出"这里有多个声音，且它们不一致"。

不用暖米色+陶土橙（Claude 默认），也不用近黑+荧光绿（赛博风）。
选**学术机构的档案室**质感：纸白底、深墨文字、用**印章红**标记"需裁决"，**靛蓝**标记"已启用"。

```
纸白    #FBFAF7   页面底（不是纯白，像微微泛黄的档案纸）
墨黑    #1A1A18   正文（不用纯黑，像油墨）
印章红  #A33A2E   「口径不一致」标记 —— 唯一的强调色
靛蓝    #2C4A6E   「已启用」状态
石墨灰  #6B6B66   次级文字、分隔线
淡赭    #E8E2D5   表头/分组底
```

**克制原则**：印章红只用于"分歧"，全页最多出现个位数次。它一出现就说明"这里有需要你决定的事"。

### 3.2 字体

- **正文/UI**：`Source Han Serif SC`（思源宋体）—— 档案感、中文正文可读性强，
  且与"权威指南"这个概念同源（指南本身是排版严谨的印刷品）
- **数据/编码**：`JetBrains Mono` —— 只用于 chunk_id、版本号、百分比阈值

**为什么不用无衬线**：这个界面的内容是**引文与条款**，宋体的"书卷气"是内容属性，
不是为了装饰。而行距放宽到 1.75（宋体正文需要更多呼吸）。

### 3.3 布局

```
┌──────────────────────────────────────────────────────────────┐
│  语料权威性治理                                    C-TIRADS 4A │
│  ─────────────────────────────────────────────────────────    │
│  本院启用 3 套 · 已知 28 套 · 检出 4 处分歧需裁决              │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  ┌─ 需裁决（2）──────────────┐  ┌─ 本院启用（3）───────────┐ │
│  │ 4A 类 FNA 阈值            │  │ C-TIRADS 2021           │ │

│  │ 诊疗规范 2018  国家卫健委      2018   95   分级·随访  ✓  │  │
```

**对齐**：整体左对齐。表格内容左对齐（中文不宜右对齐）。
**唯一居中**：顶部的汇总数字。

**结构信息**（不是装饰）：
- 左侧「需裁决」卡片用**印章红左边框**——这是真实的待决策事项，不是装饰
- 表格里「启用」列用 ✓/○ 而非开关组件——因为**停用会产生影响**，需要先看影响再决定

### 3.4 三处设计选择，逐条说明为什么不是默认

| 选择 | 为什么不是默认 | 依据 |
|---|---|---|
| **不显示「01/02/03」编号** | 语料不是序列，是并列的权威 | 编号只在有先后顺序时用 |
| **不用卡片网格** | 一张卡片装不下"两套指南的同一事实对照" | 分歧需要**并排**才看得懂 |
| **「需裁决」不用弹窗** | 弹窗会让人以为"必须马上决定"；实际可以慢慢定 | 分歧是常态，不是错误 |

## 四、内容真实性（不写空话）

界面上的所有文案都要能回答"所以呢"：

- ❌ 「知识库管理」→ ✅ 「语料权威性治理」
- ❌ 「暂无数据」→ ✅ 「本院尚未启用任何语料，报告将无法引用权威依据。先从左侧选择一套。」
- ❌ 「操作成功」→ ✅ 「已停用《ACR TI-RADS 2017》。该语料覆盖的 12 个分级主题，现在只由 C-TIRADS 提供依据。」

## 五、需要后端补的 API（当前缺失）

现有 API 只有 `POST /api/v1/internal/obs/kb-cache/invalidate`，**下面四个都没有**：

| 端点 | 用途 |
|---|---|
| `GET /api/v1/kb/sources` | 列出全部语料（source_set + 机构 + 年份 + 块数 + 覆盖主题） |
| `GET /api/v1/kb/sources/{id}/conflicts` | 某语料与其他语料的分歧清单 |
| `PUT /api/v1/kb/enabled-sources` | 设置本院启用哪些（写 `rag_enabled_source_sets`） |
| `GET /api/v1/kb/versions` | 版本列表（现有页面 mock 的部分） |

**这四个要用真实数据**：`source_set.py` 已有 28 个来源的规则表，
`source_conflict.py` 已能检出分歧 —— **后端能力都在，只是没暴露成 API**。
