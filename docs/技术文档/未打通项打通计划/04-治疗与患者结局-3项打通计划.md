### 项 04-3 分级下界（复核状态：**关** —— 与答辩口径一致，但答辩的归因不完整）

**① 现状（代码证据）**

- 真实调用链（逐跳）：
  1. `app/rag/service.py:462-500`：`RAGServiceImpl.retrieve()` **每次检索**都评估一次分级下限（这就是"能力被生产路径调用"的证据）；
  2. `app/knowledge/grading_floor.py:93-186`：`apply_grading_floor()` 纯函数（只抬不降、不猜）；
  3. `app/inference/grading_definitions.py:289-302`：`grade_major_level()` 做主级比较（分级序单一事实源 `_GRADE_HIERARCHY`，`:89-101`）；
  4. `app/rag/service.py:487-496`：评估结果**只进 `logger.info("grading_floor_evaluated", ...)`**；
  5. **链条到此终止**：`floor_outcome` 没有被写回 `result`、没有被专科/融合层消费、没有进 `findings`、没有进报告 `content`。→ 即使填表+开开关，**临床输出零变化**。

- 开关/默认值：
  - `app/knowledge/grading_floor.py:41` `GRADING_FLOOR_ENABLED = False` —— 这是**模块级常量**，不在 `app/config/settings.py`（全仓 grep `grading_floor` 只命中模块本身、调用点、测试、文档，**无 settings 字段**）。因此改它 = 改代码 + 重启，**不是环境变量/灰度配置**。
  - 生效条件：`apply_grading_floor(..., enabled=None)` 时用常量（`:104,:117`）；生产唯一调用点 `app/rag/service.py:482` **不传 `enabled`**，测试/调用方才有注入口。
- 规则表：`app/knowledge/grading_floor.py:64` `GRADING_FLOOR_RULES: tuple[GradingFloorRule, ...] = ()`。
  - **是"空表"，不是"没加载"**：全仓**不存在**任何 loader（无 YAML/JSON/DB 读取、无环境变量、无 entry-point）；唯一"非空"出现在 `tests/unit/rag/test_a88_grading_floor.py:55-60` 的 `monkeypatch.setattr`。这两个原因的修法完全不同（补 loader vs 填内容），这里确认是**空表**。
- 输入分级从哪来：`app/rag/service.py:484` 取 `request.extra["report_grading"]`；全仓 grep `report_grading` **只命中测试与注释**（`tests/unit/rag/test_a88_grading_floor.py:198-216`），**没有任何生产调用方** → 生产路径 `grading` 恒为 `None`。
- 归一化不一致（接线会踩）：规则表/比较函数用的键是 `_GRADE_HIERARCHY` 的裸形式（`"1".."5"` / `"4a"` / `"normal"` / `"mild"`，`grading_definitions.py:89-101`），而专科产出的是 `"TR4"` / `"LR-5"`（`app/agents/specialist/thyroid.py:110-135`、`liver.py:120-145`）。直接传 `"TR4"` 会命中 `grading_floor.py:139-152` 的 `unparseable` 分支。
- 规则 schema（关键）：`GradingFloorRule` 只有 `organ / min_grade / reason / reference`（`grading_floor.py:45-59`），**没有"触发条件"字段**；而模块 docstring 举的临床例子是 **case 级**的（"已穿刺证实的病例报告仍写 TR2"，`:5-7`）。当前实现表达不了"某类病例才抬"，只能表达"该器官所有病例都抬"。
- 比较粒度：`grading_floor.py:147-160` 用主级比较 → `4a`/`4b` 主级都是 4（`grading_definitions.py:92`），**无法表达 `4a→4b` 这类亚级下界**。
- 已有测试：`tests/unit/rag/test_a88_grading_floor.py`（默认关 `:60-66`、只抬不降 `:92-120`、不被检索失败打断 `:246-270`、生产路径被调用 `:177-244`、反证腿写在其 docstring `:17-24`）。
- 台账：`16-开发进展汇报-20260928.md:7530` 记录"`GRADING_FLOOR_ENABLED=False` + **规则表为空** ⇒ 临床输出零变化；只抬不降"。
- **无**实测/报告证明"打开开关后报告分级真的变了"——本项从未有端到端验证（标「待验证」，因为代码路径上就不可能变）。

**② 缺口（为什么没通）**

> ⚠️ **与"最小改动=填表+开开关"的差异（以代码为准）**：填表+开开关**不够**，也不会产生任何可观察的临床变化。理由三条，逐条有行号：① 评估结果只写日志（`service.py:487-496`），没有任何写回；② `report_grading` 无生产调用方（grep 证据），评估输入恒空；③ 规则只有器官键、无触发条件（`grading_floor.py:45-59`），照"已穿刺证实"的例子填一条 `organ=thyroid,min_grade=4` 会把**全部**甲状腺病例抬到 TR4——这正是"把正常病例抬成高风险"。

- **没接线（写回缺失）**：`service.py` 只 `logger.info`，不改 `result`/`response`/`findings`。
- **挂了错的位置**：评估发生在**检索层（生成之前）**，而"报告分级"是 LLM 生成之后的产物 → 即便写回 `result.chunks` 也无从改结论。`service.py:466-478` 的注释自述了这次妥协（"本任务的写权限不含 specialist/base.py…代价是分级要由调用方提供"）。
- **没实现（规则条件）**：`GradingFloorRule` 无 `condition`，无法表达 case 级触发。
- **没配置化**：开关是模块常量，无法按环境/灰度切换，与仓库其它 feature flag（`settings.py`）风格不一致。
- **没实现（亚级）**：主级比较吃掉 `4a/4b/4c` 差异。
- 已知反例/教训："打开开关 ≠ 能力生效"（《_背景与口径.md》§6.1）；本项是其中最隐蔽的一种——**开关、规则表、纯函数、单测、台账全都有，唯独没有出口**。

**③ 打通方案（最小改动，ponytail 阶梯）**

- ① 这一步能不能不做？——**能，而且"改报告"这一半本轮不该做**。模块 docstring 自己写了：改分级 = 让没有临床验证的规则改医生结论，必须显式开启+留痕+可单独评测（`grading_floor.py:9-25`）。建议拆成 **Phase A（可审计评估，零临床输出变化）** 与 **Phase B（真改报告，须临床规则+评测，单独立项）**。
- ② 仓库里已有可复用的吗？——有：`apply_grading_floor` 纯函数、`grade_major_level` 单一分级序、`extract_grading_severest`（`grading_definitions.py:369+`，能从结论正文抽归一化分级）、`settings.py` 的既有 flag 风格、`tests/unit/rag/test_a88_grading_floor.py` 的守卫范式。**不要新写 TI-RADS/LI-RADS 评分器**（04-1 `app/knowledge/clinical_actions.py` 已有定性规则表）。
- ③ 标准库/既有依赖够吗？——够，不需要新依赖、不新增表。

**② 缺口（为什么没通）**

- **结论先行**：默认不进正式报告 = **已记载的产品/合规口径**（SRS 待决策项 + CER 核对项 + render_report docstring + 前端标注，四条独立证据），**不是接线缺陷**。答辩口径"后端已产出、默认不进报告"成立。

  1. 没有 HTTP 入口：`render_report` 的 `include_patient_explanation=True` 只有测试在传（grep：生产调用点两处均不传）；
