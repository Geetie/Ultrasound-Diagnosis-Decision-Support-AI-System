**② 缺口（为什么没通）**

1. **不是「过滤没写」，是「过滤没有输入」**。答辩写「只有标签、无运行时过滤」，容易被读成「补个 `if` 就行」；实测是**系统内没有任何一条结构化数据回答「当前这台机器属于基层还是三甲」**。补过滤前必须先决定这个输入从哪来，否则写出来的过滤只能读一个硬编码常量。
2. **标签的语义是「这条建议适用于谁」，不是「当前机构是谁」**。三值 `基层/三甲/通用` 描述的是**建议的适用范围**（`clinical_actions.py:11` 注释：「基层医院做不了穿刺」）。这是两个正交维度，混用会得出「三甲医院不该看到基层随访建议」这类错误结论。
3. **可达侧只做了「展示」，没做「裁剪」**。报告正文（`report_service.py:439`）会把「适用：三甲」印出来——这是**告知**，不是**过滤**。对基层医院而言，报告里照样会出现「建议行细针穿刺（适用：三甲）」，只是旁边标了「三甲」。**这是本项真正的临床风险点**：标注不等于不会误读。
4. **`MAX_ACTIONS=3` 的截断在过滤之前**（`clinical_actions.py:252`）。若先截断 3 条再过滤，会出现「过滤后只剩 1 条，而第 4 条本来该留」的丢结论问题。过滤必须插在 `return actions[:MAX_ACTIONS]` **之前**。
5. **反例警示（本仓库既有教训）**：`_背景与口径.md` §6.1「打开开关 ≠ 能力生效」。本项若只加 `if institution_level == "基层": actions = [a for a in actions if a.applicable_level != "三甲"]`，**必须给出「不开过滤时这条会失败」的反证**，否则无法证明生效（见 ⑤）。

**③ 打通方案（最小改动，ponytail 阶梯）**

**阶梯 1：这一步能不能不做？**
> **能，而且很可能应该不做——取决于一个产品决策。**

- 现状已满足「分层**告知**」：报告里印出了适用层级（`report_service.py:441-442`）。
- 真正的「运行时过滤」只在**一套系统交付给多种机构（基层版 + 三甲版）**时才有意义。若产品是**单院/单机构部署**（当前 `devices.location` 自由文本、`KBVersion.hospital_id` 恒 None 的形态说明架构上就是单机构假设），过滤器的输入无从获得，做了只能读一个写死的环境变量——**等于把「交付给谁」这件事从运维手册搬进代码**，没有收益。
- **结论：先让产品/交付方回答「是否需要按机构分层交付」。答案为否 → 本项关闭（记为「已满足告知口径」），不写代码。答案为是 → 走下面的最小实现。**
