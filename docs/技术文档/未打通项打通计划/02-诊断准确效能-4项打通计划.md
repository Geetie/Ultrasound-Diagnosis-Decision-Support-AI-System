## 0. 四项共享的档位链（本节是后面所有结论的前提，必须按顺序读）

```
前端 ExaminationPage.tsx:72  response_tier:'standard'   ← 硬编码，医生选不到 full

        ↓ repositories/diagnosis_repository.py:75  tier=response_tier.value  （落库）

```

**三条由代码直接读出的推论**（不是推测，逐条有行号）：

1. **`retrieval_confidence` 生产上恒为 `None`** —— `pipeline.py:137-153` 的 `_assess_routing` 只传 `query` / `target_organ` / `requested_tier` 三个参数。所以 `routing.py:330-334` 的"低置信 → 升 FULL"分支**在生产不可达**。
2. **`MULTI_FEATURE` 也不升档** —— `routing.py:381-391`（`is_multi_feature` 分支）返回的 `effective_tier = requested_tier`，只把 `requires_confirmation=True`；而 `requires_confirmation` 的确认入口 `POST .../routing/confirm`（`app/api/v1/diagnosis.py:505-540`，内部 `update_tier(..., FULL)`）**前端无任何调用点**（`grep -rn "confirm" frontend/src/` 只命中语音指令确认）→ 这条升级路径也是死路。
3. **因此：`effective_tier == FULL` 在生产上只有一条路可走 —— 请求体自己带 `response_tier='full'`。** 而前端 5 处全部硬编码 `'standard'`：`ExaminationPage.tsx:72`、`useWorkspaceFlow.ts:187`、`useWorkspaceFlow.ts:297`、`diagnosisService.ts:124`、`DiagnosisPage.tsx:59`（末者是轮询展示用，不参与提交）。

> **待验证（需真机 1 条请求证伪）**：以上是静态阅读结论。验证方式见 §02-3⑤ 的反证腿 V0（发一条 `response_tier='standard'` 的请求，断言 `findings.routing.effective_tier == 'standard'` 且 `findings.timings_ms["fusion.self_rag_skipped"] == true`）。

### ② 缺口（为什么没通）

1. **【接了但默认关】** `settings.py:487 = False`。这一条本身**一行 `.env` 即可解**，不是主要缺口。
2. **【产出无消费者】**（主缺口）`findings["t2a_classification"]` 在 `app/api/v1/diagnosis.py` 的 `DiagnosisResult` 组装处没有任何派生字段，前端零命中。即使把开关打开，医生端可见变化 = **0**。这是"接了 ≠ 生效"的最纯粹形态。
3. **【降级原因仍在】** 8003 `/v1/classify` 的**服务端**是否在部署环境常驻、模型是否随进程加载，仓库内**无证据**（`app/api/v1/health.py:92-104` 只是探针，未落基线报告）→ 标**待验证 🔬**。

**已知反例教训（必须引用）**：A.95.7 第 1 条——"**'打开开关'不等于'能力生效'**：影像腿 P1（可达）100%，但 P1b（送达）40%，中间隔着精排与 BM25 兜底两层"。T2a 这里是同一类病：**可达（HTTP 能通）≠ 落库 ≠ 医生看得见**，本次还多断了一环（落库了但没人读）。

### ② 缺口（为什么没通）

1. **【接了但只在小流量档】** `pipeline.py:344` 的 `== FULL` 是唯一闸门。答辩口径"仅 FULL 档"**属实**。

- 另有一条硬短路：`result.validate_degraded` 为真时不触发（`service.py:204`，A.51 注释：预算是"超时降载"不是"质检失败"）。

**产出写到哪里**：`findings->'fusion_result'->>'crag_triggered' / 'crag_recovered'`（`pipeline.py:2515-2516`）；日志 `fusion_crag_recovered` / `fusion_crag_not_recovered` / `fusion_crag_failed` / `crag_recovery_quality_rejected`（`service.py:226-236`、`crag.py:355-362`、`:379-387`）；`timings_ms["fusion.crag_ms"]`。

- **本次增量**：定位到**具体丢失点**（`crag.py:850-861` 构造处漏传 + `AgentContext` 无字段），A.62 当时只到"落库有、prompt 无"的现象层。

### ② 缺口（为什么没通）

1. **【接错 —— 数据中途丢失】**（P0 根因）`crag.py:838` 写、`:850` 丢。新证据**从未进入重生成 prompt**。
2. **【接了但只在小流量档】**（隐式）无显式开关；靠 `self_rag_passed is False` 间接限档，而该条件又只在 FULL 档可能出现 → 与 02-3 同一条死路。
3. **【质量门在缺陷下失去意义】** `min_evidence_score=0` + `revalidator=None` → 只剩 `citated` 比对；而 specialist 自己重跑检索**有可能独立命中同一 chunk** → `evidence_used` 偶然通过 → `crag_recovered=True` → **撤销 needs_review**。这是"假恢复"路径，A.88 T5-6 的质量门挡不住它（它挡的是"检索到但没用"，挡不住"用了但不是因为我们喂的"）。
4. **【消费者缺失】** `crag_*` 只声明未渲染，医生完全看不到"这次做过补充检索"。

**已知反例教训**：A.95.7 第 1 条（"接了 ≠ 生效"）在此处的最强形态 —— **不是送达率低（40%），而是送达率 0%。**

### ③ 打通方案（最小改动，ponytail 阶梯）

- **这一步能不能不做？** 不能（02-4 是立项目标；且当前状态会**主动抹掉复核标记**，属安全负收益，必须处理）。
- **仓库里已有同类实现可复用吗？** **有，而且这就是最小改法**：
  - `AgentContext.imaging_metadata`（`app/agents/protocols.py:78`）与 `retrieval_profile`（`:77`）都是"透传给专科智能体的旁路载荷"——**已存在的通道**。任务里提到 `imaging_metadata` 被用于注入分割特征（`pipeline.py:344-350` 注释），说明**专科智能体确实消费 `imaging_metadata`**。
  - 因此最小改动**不需要给 `AgentContext` 加新字段**，把 `crag_evidence_chunks` 挂进 `imaging_metadata` 即可（或加 1 个语义正确的 `retrieval_context` 字段，二选一，见下）。
- **标准库/已装依赖够不够？** 够，无新增依赖。

### ② 缺口（为什么没通）

1. **【链 A：接了但只在小流量档】** `pipeline.py:2081` 的 `is_full_tier`。而 FULL 档在生产 UI 不可达（§0 推论 3）→ **默认路径上幻觉检测从不执行** → `hallucination_severity` 恒 `None` → 前端 `QualityControlBadge` 的幻觉 Tag **永远不渲染**、`DiagnosisConclusion` 的安全等级永远不会因幻觉降为 C。这是"界面元素存在但永远不出现"的形态。
2. **【链 B：观测样本为 0】** CUSUM 的唯一数据源是 `detector.detect()` 末尾的 `_report_to_cusum`（`hallucination_detector.py:584`）。检测器只在 FULL 档被调 → **默认档下 CUSUM 的 `total_observations` 永远 0、`s_plus` 永远 0、永不触发**。答辩说"CUSUM 只告警不阻断"，实际是**连告警都不会发出**（默认路径）。
3. **【链 B：告警无持久化、重启即失忆】** 熔断状态、CUSUM 累计量、`_active_alerts` 全是**进程内内存**（`monitor.py:41-52`、`circuit_breaker.py:37-49`、`manager.py:77-78`）→ 服务重启后 `s_plus` 归零、`SUSPENDED` 状态消失。对"熔断"这种安全状态机，**重启清空是可被利用的漏洞**（连续重启即永不熔断）。标**待验证**（未见持久化代码）。
4. **【链 B：阻断缺失 + 单进程前提】** 若要"阻断"，还需知道进程模型：`app/main.py:69-80` `_detect_worker_count()` 读 `WEB_CONCURRENCY`（缺省 1）且注释写"单进程是本系统的**硬前提**"；`scripts/start_main.sh:88-90` 也是单进程 uvicorn。→ **当前进程模型下"进程内单例"恰好可用**，但一旦扩多 worker，CUSUM 状态会分片、熔断只在单个 worker 生效。这是"阻断方案必须写进风险"的前置条件。

**已知反例教训**：`_detect_hallucination_safely` 的 docstring（`pipeline.py:2030-2041`）自己就写了"成本与档位：…在 FAST/COMPACT 档默认不跑"——**设计意图是省 1ms 的正则遍历**，代价是**两条安全链同时归零**。这是"为极小的性能收益关掉安全能力"的典型，值得在方案里明写为"不划算"。

  - **链 B 最大风险：误停**。按 ④#1，FPR=0.01 下漏检 >2/3、且本仓 `s_plus` 几乎不衰减（非 severe 一次仅 -0.0075）→ **历史上 4 次严重幻觉就会让"当前"一直处于 pending**。缓解：①先只做语义 ①（降级不禁用）；②加"衰减/窗口"校准（需 300 例标定，`obs_cusum_calibration_samples`）；③`_confirm_seconds` 保留 900s 人工确认窗口。

  - **单进程前提若破**：多 worker 下每个进程一套 CUSUM → 熔断分片失效。**实现 B1 前须在 00 号写明"该实现依赖单进程"**。
