## 5. 每一「项」的交付格式（照抄 6 段，缺一段视为未交付）

```md
### 项 <编号> <名称>（复核状态：通/部/关/未 —— 与答辩口径一致/不一致：说明）

**① 现状（代码证据）**
- 真实调用链：`文件:行号` → `文件:行号` …（逐跳到「最后一步停在哪」）
- 开关/默认值：`settings.py:行号` 字段名 = 值；生效条件（档位/环境变量/重启）
- 已有测试或报告：`tests/...` / `tests/reports/...`（有就点名，没有写「无」）

**② 缺口（为什么没通）**
- 一条一句，指到具体行/配置/条件。区分：*没接线* / *接了但默认关* / *接了但只在小流量档* / *没实现*。
- 已知反例/实测教训（例如「打开开关 ≠ 能力生效」）要在这一节点名。

**③ 打通方案（最小改动，ponytail 阶梯）**
- 先答「这一步能不能不做」；再答「仓库里是否已有同类实现可复用」；再答「标准库/既有依赖能否覆盖」。
- 步骤表：`文件` → 改什么 → 为什么（每步一行，含预计 diff 规模：±N 行）
- **不做什么**（YAGNI 清单）：明确写「本次不做 X，因为 Y」。

**④ 外部方案调研（ego-browser / web 取证）**
- 现成轮子/标准做法：名称 + 链接 + 许可 + 为什么够/为什么不够。
- 本机调研通道见 §6.4；每条结论必须带可点开的 URL，**不得凭记忆写库名/版本**。

**⑤ 验收（可执行，必须是端到端而非「开关已打开」）**
- 验证命令（完整可复制）+ 通过判据（数字/断言/退出码）
- 需要造什么数据（多少例、从哪来、许可是否允许）
- **反证腿**：怎么证明「没打通时这条会失败」

**⑥ 依赖 / 风险 / 工作量**
- 依赖（其它项的编号、外部资源、人）
- 风险（最坏情况、回滚方式）
- 工作量（人日，含评测）与优先级（P0/P1/P2）
```

## 6. 硬规则（违反即返工）

### 6.1 证据纪律（本仓库的既有血泪）

- **只认代码与仓库内报告**；文档与代码冲突 → 以代码为准并写明。给不出 `path:行号` 或实测数字的，
  一律标 **「待验证」**，不得写成结论。
- **禁止无证据宣称「已完成 / 已打通 / 已优化」**。
- **「打开开关」≠「能力生效」**：答辩 P7 的 18 项里，一半以上是「接了但默认关 / 限档 / 只告警」。
  方案必须回答「打开之后凭什么说它真的生效」，并给出可见证据（trace/日志/接口字段/界面元素）。
- **单一标记不得定罪**（历史教训：把答案里出现 `PATIENT_001` 当模板回显，误删 415 条真结论）。
  判定必须两条以上独立证据。
- 不要为了凑数放宽口径（去重口径、门槛都不得下调）。

### 6.2 ponytail（每个 Agent 都必须加载并遵守）

- 阶梯：① 需要存在吗 → ② 仓库里已有吗 → ③ 标准库 → ④ 平台原生 → ⑤ 已装依赖 → ⑥ 一行 → ⑦ 最小实现。
- **删除优于新增**；最短路可行的方案就是对的方案；方案里写「不做什么」比写「要做什么」更重要。
- 但**不许省掉理解问题**：先读通整条链路再选阶梯。
- 保留必要的校准参数（阈值/分布类常量要写清「多少例后重定」）。

### 6.3 代码只读

- 本次任务是**调研 + 出方案**，不改 `app/`、`frontend/`、`tests/`。需要验证时只读代码、跑只读命令
  （`grep` / `python -c` 只读探针 / `pytest --collect-only` 之类），**不得起服务、不得改库、不得部署**。
- 服务器 / 真机动作**不做**（本机没有 GPU 环境；需要真机的验证写进「⑤ 验收」，标注 🔬）。

### 6.4 本机调研通道（负责人的已知事实，别浪费时间去踩）
