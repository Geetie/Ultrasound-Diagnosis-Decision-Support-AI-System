# 可观测性与运维

## 1. 日志体系

**full profile**：
| 组件 | 日志框架 | 存储方式 |
|---|---|---|
| FastAPI 服务 | Python logging + structlog | Filebeat → Elasticsearch |
| 智能体 | 自定义 AgentLogger | Filebeat → Elasticsearch |
| 数据层 | PostgreSQL 慢查询日志 | pg_stat_statements |

**compact profile**：不部署 Elasticsearch，安全合规关键审计日志存 PostgreSQL `audit_logs` 表，应用运行日志存 PostgreSQL `app_runtime_logs` 表（详见 [01-系统架构设计](01-系统架构设计.md) §5.8 部署 Profile 表及 [04-安全合规](04-安全合规.md) §3 审计日志存储方案统一）。compact 模式统一使用 PostgreSQL 存储所有日志，不使用 SQLite。SQLite 仅作为 full Profile 下 Elasticsearch 不可用时应用运行日志的临时降级方案（安全合规关键审计日志仍写入 PostgreSQL `audit_logs` 表，不降级），与 [01-系统架构设计](01-系统架构设计.md) §5.8 部署 Profile 表统一。

**诊断日志保留策略**：诊断日志（完整推理链路 + 知识库版本号）保留**门诊 15 年 / 住院 30 年**（与 [04-安全合规](04-安全合规.md) §1 数据保留策略明细表及 §3 审计日志保留期限一致），独立于普通操作日志的 5 年保留期。诊断日志在冷热分层中优先归档至冷存储（对象存储/本地文件归档），但须确保保留期内可检索。

**日志分类判定规则**：凡直接影响诊断结论的操作（阈值调整、模型版本变更、知识库更新、脱敏规则更新）一律归入诊断日志（门诊 15 年 / 住院 30 年），纯系统运维操作归入操作日志（5 年），详见[04-安全合规](04-安全合规.md) §3 日志分类判定规则表。

**边缘端日志收集方案**

> **审计日志 NTP 同步状态标记**：所有审计日志记录须附加 `ntp_sync_status` 字段（取值：`"synced"` | `"degraded"` | `"unreachable"`），详见[04-安全合规](04-安全合规.md) §5 边缘端时间同步规范对齐。NTP 偏差 > 1s 时标记为 `"degraded"`，NTP 不可达时标记为 `"unreachable"`。此标记用于 IEC 62304 合规审计时判断日志时间戳可信度。

| 维度 | 方案 |
|---|---|
| 本地存储 | 边缘端日志写入本地文件（`/var/log/ultrasound-edge/`），按天轮转，保留 7 天 |
| 传输方式 | 网络可用时批量上传至后端 PostgreSQL（每 5 分钟或日志量 > 1MB 时触发） |
| 后端不可达 | 本地暂存，网络恢复后自动续传；本地存储满时清理最旧日志 |
| 关键日志优先 | 安全相关日志（同意状态变更、模型加载失败、降级事件）**立即触发一次日志批量上传**（不等 5 分钟间隔），或通过 WebSocket `metric_alert` 通道实时上报（与 §2 边缘端实时指标上报方案对齐），确保安全事件在 ≤5s 内到达后端。**关键日志独立上传机制**：若批量上传因网络短暂可用（≤5 秒窗口）而中断，关键日志须支持**独立上传**（不等批量窗口），并携带最小上下文（前后各 3 条日志摘要，含时间戳、日志级别、事件类型），确保即使批量上传失败，关键事件的上下文也可追溯。独立上传的关键日志在后端标记为 `standalone_upload=true`，运维可通过此标记识别不完整的批量上传并触发补充拉取 |
| 日志格式 | 与主服务一致的结构化 JSON 格式，含设备 ID 和时间戳 |

**边缘端实时指标上报方案**
| 维度 | 方案 |
|---|---|
| 传输通道 | 复用导航通道 WebSocket 连接（`/api/v1/realtime/nav`），增加 `type: "metric_alert"` 消息类型 |
| 上报条件 | 仅 Critical 级别指标实时上报（GPU 温度 > 85°C、导航推理延迟 > 80ms、显存利用率 > 90%、导航健康探测连续失败），Warning 级别指标随日志批量上传 |
| 消息格式 | `{"type": "metric_alert", "device_id": "...", "metric_name": "gpu_temperature", "metric_value": 87.5, "threshold": 85.0, "severity": "critical", "timestamp": ...}` |
| 后端处理 | 后端收到 `metric_alert` 消息后立即触发对应告警流程，无需等待日志批量上传 |
| WebSocket 不可达 | 降级为日志批量上传（延迟增加但功能不丢失），后端通过设备注册心跳超时感知边缘端异常 |

> 日志写入通过 `LogStorage` 抽象层适配，通过 `DEPLOYMENT_PROFILE` 自动选择存储后端。

**缓存防护告警升级流程**：

| 告警场景 | 升级策略 |
|----------|----------|
| 缓存命中率 < 40% Critical | 立即检查 Redis 可用性 → 检查布隆过滤器加载状态 → 检查热点 key 永不过期配置 → 必要时手动触发缓存预热 |
| 穿透至数据库查询率 > 10% Critical | 检查布隆过滤器是否正常加载 → 检查空值缓存 TTL 配置 → 检查是否有新类型的无效查询模式 |
| 缓存同时失效 > 100 个 Critical | 确认 TTL 随机化是否生效 → 检查是否有批量 key 被手动清除 → 触发紧急缓存预热 |
| 互斥锁等待超时 > 50 次/小时 Critical | 检查热点 key 加载耗时 → 考虑扩大互斥锁超时时间 → 检查数据库查询性能 |

**缓存防护日志收集要求**：

| 日志事件 | 日志级别 | 收集字段 | 说明 |
|----------|----------|----------|------|
| 布隆过滤器加载完成 | INFO | `loaded_keys`, `bloom_size`, `load_time_ms` | 启动时记录布隆过滤器加载状态 |
| 空值缓存写入 | DEBUG | `key_hash`, `ttl_seconds` | 记录空值缓存写入（生产环境可降为 TRACE） |
| 互斥锁获取失败 | WARN | `key`, `retry_count`, `wait_time_ms` | 记录互斥锁竞争情况 |
| 缓存预热完成 | INFO | `warmed_keys`, `total_keys`, `warmup_time_ms` | 记录预热完成状态 |
| 缓存预热失败 | ERROR | `failed_keys`, `error_message` | 预热失败需立即排查 |
| TTL 随机化配置检查 | INFO | `randomization_percent`, `actual_offsets_sample` | 启动时记录随机化配置和实际偏移样本 |

**边缘端监控指南**

| 指标 | 告警阈值 | 说明 |
|---|---|---|
| 导航推理延迟 | > 60ms Warning, > 80ms Critical | 超过延迟预算（边缘端推理预算 ≤50ms，Warning 阈值 60ms 允许 20% 超标余量，Critical 阈值 80ms 对应端到端 P99 < 200ms 的极限值） |
| GPU 温度 | > 80°C Warning, > 90°C Critical | Jetson 散热受限。完整四级阈值与处理策略：75-80°C 主动降频（10fps），80-85°C 被动隔帧推理（7.5fps）+ Warning，85-90°C 暂停导航推理 + Critical，>90°C 暂停所有 GPU 推理（详见下方"边缘端 GPU 温度处理策略"表，详见[01-系统架构设计](01-系统架构设计.md) §1 边缘端推理降级策略对齐） |
| GPU 显存利用率 | > 85% Warning | 边缘端显存有限 |
| 导航健康探测失败 | 连续 3 次 Critical | 即将进入降级模式 |
| 降级模式激活频率 | 24h 内 > 2 次 Warning | 调度服务可能不稳定 |
| 降级模式持续时间 | > 5 分钟 Warning | 后端服务异常 |
| 网络延迟 | > 10ms（P99）Warning | 网络质量劣化 |

**边缘端 GPU 温度处理策略**

| 温度范围 | 处理动作 | 说明 |
|---|---|---|
| 70-75°C | 正常运行，无动作 | Jetson Orin NX 正常工作温度范围 |
| 75-80°C | **主动降频**：导航推理帧率从 15fps 降至 10fps（通过提前降频避免温度频繁触及 80°C 阈值导致的帧率跳变，10fps 仍满足导航实时性——100ms/帧） | 主动降频减少发热，温度曲线更平稳，与 [01-系统架构设计](01-系统架构设计.md) §1 推理帧率规格对齐 |
| 80-85°C | Warning 告警，被动隔帧推理（7.5fps） | 被动降频减少发热，导航标注间隔增大但服务不中断 |
| 85-90°C | Critical 告警，暂停导航推理，降级为仅显示原始超声图像 | 保护硬件，诊断功能不受影响 |
| > 90°C 持续 60s | 紧急降级：暂停所有 GPU 推理（含导航与诊断），前端提示"GPU 过热保护，请转为人工诊断"。**检查状态保存规则**：降级触发时自动保存当前会话的导航历史与已采集帧标注至 PostgreSQL（标记 `gpu_thermal_checkpoint: true`），GPU 温度恢复至 < 80°C 后可从断点继续（而非重新开始），前端提示"GPU 温度已恢复，是否恢复之前的检查进度？"。此机制与[01-系统架构设计](01-系统架构设计.md) §5.8 模型热重载的会话关联策略一致 | 防止硬件损坏，温度恢复至 < 80°C 后自动恢复 |

**GPU 故障检测与自动隔离**（仅 full Profile 多 GPU 环境）：

| 故障类型 | 检测方案 | 处理策略 |
|---|---|---|
| CUDA OOM | 捕获异常 | 释放模型缓存，路由至其他 GPU |
| GPU hang | 推理超时 > 30s | 标记不可用，重启 CUDA 进程 |
| 温度过高 | nvidia-smi 监控 | 降频运行，持续 > 90°C 则隔离 |
| CUDA 错误率升级 | 统计错误率 | > 1% 时隔离该 GPU |

> compact Profile 单 GPU 故障时直接降级为纯人工模式

**compact 模式模型热重载**：GPU 显存碎片化率 >30% 触发热重载时，compact 单 GPU 无其他实例可路由。热重载须与检查会话状态关联——有活跃会话时延迟至会话结束后执行（最多 10 分钟），无活跃会话时立即执行。10 分钟后仍有活跃会话则强制执行，热重载期间新诊断请求排队等待（而非直接拒绝），等待时间计入诊断超时预算。热重载完成后自动恢复接收诊断请求，优先处理排队中的急诊请求。此策略与[01-系统架构设计](01-系统架构设计.md) §5.8 一致。

**compact 模式自动安全熔断**：compact Profile 须实现自动安全熔断机制——严重幻觉率 > 0.5% 时，系统立即触发安全审查（4 小时内完成），审查结论为"暂停 AI 辅助"或"继续运行并加强监控"。**compact 模式采用周统计 + CUSUM 序贯检验双机制**：周统计窗口 350 例，与 full Profile 统计粒度一致，确保熔断规则（连续 3 周出现 ≥1 例或单周 ≥3 例严重幻觉）可直接执行；CUSUM 累积和控制图以 0.5% 为目标值，当累积偏差超过决策阈值 h=3 时触发告警，可在样本量不足时更早检测到异常偏移。

**CUSUM 参数校准标准操作程序（SOP）**：
1. **准备阶段**：收集系统上线前的历史标注数据（至少 300 例，涵盖三器官各 ≥100 例），作为模拟基线数据
2. **参数设置**：设定目标值 p₀=0.5%（基线幻觉率），偏移量 δ（分别模拟 1%、2%、3% 的偏移）
3. **模拟执行**：使用蒙特卡洛模拟生成 1000 次重复实验，每次模拟连续 30 天的日检查量（按 ~50 例/日随机生成）
4. **指标计算**：计算每次模拟的 ARL₀（在 p₀ 下平均运行长度）和 ARL₁（在偏移率下平均运行长度）
5. **判定规则**：
   - ARL₀ < 100（100 天内误报一次）：h 值过低，调整至 h=4 或 h=5
   - ARL₁ > 50（检测延迟超过 50 天）：h 值过高，调整至 h=2
   - ARL₀ ≥ 100 且 ARL₁ ≤ 50：参数适用
6. **记录存档**：校准结果（含 ARL₀、ARL₁、检测延迟、建议 h 值）记录至 Gate 0A 验证报告

校准结果须记录至 Gate 0A 验证报告。周度严重幻觉率 > 0.5% 或 CUSUM 超阈值时自动暂停 AI 辅助功能（触发前通知科室主任确认，主任可在 15 分钟内判断是否为统计波动并取消暂停），避免自动化规则误判导致临床工作中断。高风险病种幻觉率 > 1% 时，立即暂停该病种 AI 辅助。恢复 AI 辅助需系统管理员手动操作并记录审计日志。Critical 告警 15 分钟未确认时，自动通知上级医院运维（告警升级机制）。与 [00-项目总览](00-项目总览与核心指标.md) §2.2 一致。

**模型热重载竞态处理**：GPU 显存碎片化率 > 40% 触发热重载时，若诊断请求持续到达无法找到"两次之间"的窗口，则延迟至当前活跃会话结束后执行（最多 10 分钟）。10 分钟后仍有活跃会话则强制执行热重载，热重载期间新诊断请求排队等待。此策略与[01-系统架构设计](01-系统架构设计.md) §5.8 一致。

**PostgreSQL 熔断器监控**：PostgreSQL 熔断器定义详见[01-系统架构设计](01-系统架构设计.md) §5.9。熔断器状态变更须纳入监控。

| 监控指标 | 告警条件 | 级别 |
|---|---|---|
| PostgreSQL 连接池使用率 | > 80% Warning, > 95% Critical | 资源耗尽风险 |
| PostgreSQL 慢查询（> 3s） | 5 分钟内 > 3 次 Warning | 熔断器即将触发 |
| PostgreSQL 熔断器状态 | 触发熔断 Critical | 系统进入降级模式 |
| PostgreSQL 熔断器降级模式持续时效 | > 5 分钟 Warning | 数据库持续异常 |
| PostgreSQL 只读模式 | 激活 Critical | 写入不可用 |

**compact 模式监控替代方案**：compact Profile 不部署 Grafana，但须提供以下轻量监控能力：

| 方案 | 说明 |
|---|---|
| 轻量 Web 仪表盘 | **集成于主服务进程**（作为 FastAPI 静态文件服务，避免独立进程开销），基于 Prometheus HTTP API 展示关键指标（GPU 健康、幻觉率、延迟 P99、服务可用性）。仪表盘不是安全关键组件，无需进程隔离，集成到主服务可节省独立进程运行时开销（约 50-100MB） |
| 仪表盘资源预测 | **VictoriaMetrics 单机版**作为**独立 Docker 容器**运行（通过 Docker Compose 资源限制 `mem_limit: 200MB` 隔离内存使用，避免与主服务进程竞争内存影响诊断延迟；**OOM 保护**：设置 `oom_score_adj=-500`，确保内存压力下 OOM Killer 不优先杀死 VictoriaMetrics 容器——低于默认值 0 但高于 SafetyGateway 的 -1000，优先级为主服务 > SafetyGateway > VictoriaMetrics > 其他容器）。仪表盘静态文件集成于主服务（资源开销约 5-10MB，可忽略），总内存占用须 <200MB（VictoriaMetrics 约 100-130MB + 仪表盘静态资源约 5-10MB），CPU <0.5 核。VictoriaMetrics 数据持久化至 Docker 挂载卷（`volumes: - vmdata:/victoria-metrics-data`），容器重启后数据可恢复，避免监控数据丢失。**compact 模式监控数据本地备份**：VictoriaMetrics 支持数据快照（`vmbackup`），配置每小时自动备份至本地文件（压缩后约 10-50MB/小时），VictoriaMetrics 恢复后从备份恢复数据。备份文件保留最新 7 天，存储于边缘端本地 SSD（compact 模式审计日志存 PostgreSQL，无 SQLite I/O 竞争；full 模式与审计日志 SQLite 分磁盘，避免 I/O 竞争）。备份失败时触发 Warning 告警。此备份策略与[01-系统架构设计](01-系统架构设计.md) §5.8 compact 部署 Profile 表对齐。VictoriaMetrics 内存占用仅为 Prometheus 的 1/3~1/5，天生适配基层单机内存预算，且完全兼容 Prometheus API（Grafana 仪表盘无需修改，PromQL 查询语法完全兼容），运维迁移成本为零。compact Profile 总内存 64GB，仪表盘占用不超过 0.25%。**Gate 0 须增加 VictoriaMetrics 内存实测验证**——采集指标数量与频率按本节定义配置。**超限检测机制**：VictoriaMetrics 内存占用通过 `process_resident_memory_bytes` 指标监控，持续 5 分钟超过 150MB 触发 Warning 告警，超过 180MB 触发 Critical 告警并自动降低采集频率至 60s |
| AlertManager Webhook | 配置 Prometheus AlertManager 的 Critical 告警推送至飞书/钉钉/企业微信 |
| 告警规则 | 与 full Profile 相同的告警规则，仅展示方式不同 |

**compact 模式告警响应流程**

| 告警级别 | 响应要求 | 升级机制 |
|---|---|---|
| Warning | 基层 IT 人员 4 小时内确认 | 24 小时未确认自动升级至上级医院运维 |
| Critical | 基层 IT 人员 15 分钟内确认 | 15 分钟未确认自动通知上级医院运维，1 小时未确认通知医院行政值班 + 设备供应商技术支持热线 |
| 安全熔断 | 系统自动执行，无需人工确认 | 系统管理员手动恢复 AI 辅助功能并记录审计日志 |

> 告警接收人通过 `ALERT_CONTACTS` 环境变量配置（JSON 格式，含姓名、角色、联系方式、上级医院运维联系方式、医院行政值班联系方式、设备供应商技术支持热线）。上级医院运维联系方式变更时须同步更新配置并验证推送可达性。**告警升级路径务实化说明**：原设计升级至"区域医疗质控中心"，但中国大部分区域医疗质控中心无 7×24 技术告警接收能力，也不具备远程诊断 AI 系统故障的技术能力。因此升级链条第三级改为"医院行政值班 + 设备供应商技术支持热线"——医院行政值班具备行政协调能力，设备供应商技术支持热线具备技术诊断能力，两者组合更实际有效。一期试点前须确认医院行政值班 7×24 可达性及设备供应商技术支持热线的响应 SLA，并在部署文档中记录。**Gate 1 前置条件**：告警升级路径确认须在 Gate 1 前完成——须验证医院行政值班与设备供应商技术支持热线的可达性，否则告警升级链条断裂，Critical 告警可能无法在 1 小时内被响应。

> **告警联系人热更新**：`ALERT_CONTACTS` 配置除通过环境变量初始化外，须支持通过管理 API（`PUT /api/v1/admin/alert-contacts`）热更新，无需重启服务。更新后自动验证推送可达性（发送测试告警），验证失败回滚至旧配置并触发 Warning 告警。一期试点前须确认上级医院运维、医院行政值班和设备供应商技术支持热线的联系渠道与响应 SLA。

## 3. 链路追踪

采用 OpenTelemetry 标准
```
请求入口 → 标准化解析 → 调度分配 → 专科智能体 → 知识检索校验 → 融合 → 脱敏校验 → 输出
   |            |            |            |            |       |      |       |
 trace_id    span_1      span_2      span_3      span_4   span_5  span_6  span_7
```

每个 span 记录：开始时间、结束时间、状态、关键参数、响应路径类型

## 4. 模型版本管理

| 操作 | 流程 | 回滚策略 |
|---|---|---|
| 模型发布 | **compact Profile**：首个检查会话使用新模型 → 至少 10 个会话且至少 24 小时无异常后扩展至 10 个会话 → 至少 10 个会话且至少 24 小时无异常后全量发布。compact 日检查量 ~50 例，纯时间窗口内样本量不足，采用"会话数 + 时间窗口"双重条件确保统计意义（10 个会话样本量过小可能漏检模型缺陷，50 个会话可提供更可靠的异常率基线）。**full Profile**：5% 流量灰度 → 监控 24h → 全量发布 | 一键回退至上一版本 |
| 模型更新 | 灰度发布（5% 流量）→ 监控 24h → 效果达标后全量切换 | 保留最新 3 个版本，秒级回退 |
| 模型下线 | 标记 deprecated → 30 天过渡期 → 下线 | 下线后保留镜像 90 天 |
| **KB + 模型联合升级** | **原子升级（唯一推荐方案）**：KB 和模型通过 Docker Compose 同时重启所有服务（KB 升级 + 模型升级在同一部署批次中完成），消除顺序窗口期风险。详见[02-核心流程与知识库](02-核心流程与知识库.md) §1.3 原子升级方案 | **原子回滚**：升级前自动保存当前版本快照（KB + 模型 Docker 镜像标签），升级失败时同时回滚 KB 和模型至升级前版本，无需顺序判断。详见[02-核心流程与知识库](02-核心流程与知识库.md) §1.3 原子升级方案 |

| 灰度版本用户反馈率 | < 5% | > 5% Warning | 用户体验反馈 |

**灰度发布安全护栏**

| 护栏类型 | 触发条件 | 处理动作 |
|---|---|---|
| 性能护栏 | 灰度版本延迟 P99 > 稳定版本 1.5 倍 | 自动暂停灰度，保持当前流量分配 |
