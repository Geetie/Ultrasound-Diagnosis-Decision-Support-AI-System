## 4. 告警

### 4.1 路由与升级（`config/alertmanager.yml`）

- 分组：`group_by: [alertname, metric]`；`group_wait: 30s`、`group_interval: 5m`、`repeat_interval: 4h`（`:4-8`）；
- 分派：`warning` → webhook + feishu；`critical` → 再加 dingtalk + wecom；`safety_meltdown` → 四通道且 `repeat_interval: 5m`（`:10-54`）。

### 4.2 应用侧升级与去重

| 机制 | 行为 | 出处 |
|---|---|---|
| 升级 | `warning`：confirm 14400s → escalation 86400s；`critical`：confirm 900s → level1 3600s → level2 | `alert_escalation/manager.py:100-132` |
| 重排 | `_pending_webhooks` 队列 + 失败重排 | `:239-271` |
| 出站 webhook | `alert_webhook_url` 默认 `''`；`send_webhook` 5s 超时；**目标缺失静默跳过** | `manager.py:43`、`webhook.py:8-9`、`settings.py:412` |
| 阈值 | 默认见 `settings.py:408-411` | 同左 |

### 4.3 IM 适配器

`observability/webhook_adapter.py:15`：独立 FastAPI，暴露 `/feishu`、`/dingtalk`、`/wecom`；
目标 URL 取自环境变量 `FEISHU_WEBHOOK_URL` / `DINGTALK_WEBHOOK_URL` / `WECOM_WEBHOOK_URL`（`:19-21`）。

### 4.4 告警回调端点（**本次修复**）

**修复前的事实**：`config/alertmanager.yml:59` 与 `docker-compose.dev.yml:247` 都回调
`/api/v1/internal/alerts/webhook`，但**代码里从来没有这个路由** → 回调一直在收 404，
告警实际只依赖 IM 通道；vmbackup 的失败通知也全部丢失。

**修复后**（`app/api/v1/alerts.py`）：

| 项 | 约定 |
|---|---|
| 路径 | `POST /api/v1/internal/alerts/webhook` |
| 兼容载荷 | Alertmanager v4（`version/status/groupKey/alerts[]`，含 `send_resolved` 的 resolved 事件）与 vmbackup 的一行 JSON（`{"type":"vmbackup_failure","message":...}`） |
| 返回 | **永远 200**（除鉴权失败）：对非 2xx Alertmanager 会重试退避，告警风暴下重试风暴比丢一条通知更危险 |
| 鉴权 | `alert_webhook_token` 为空 → 不校验（内网）；**一旦配置即强制校验**（`X-Alert-Token` 或 `Bearer`），失败 401 |
| 埋点 | 落结构化日志 `alertmanager_webhook_received` / `internal_alert_webhook_received`，含 firing/resolved 计数与 alertname 列表 |
