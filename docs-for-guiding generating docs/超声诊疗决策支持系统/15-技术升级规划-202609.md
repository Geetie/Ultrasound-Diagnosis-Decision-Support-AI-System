## 1. 规划总原则

1. **先还债、再升级**。代码实证层反复暴露"能力已实现但未接线"模式（指标导出、告警回调、三层脱敏、追踪、双通道 WS 等），任何新组件接入前必须先闭合既有断点，否则会被同一模式吞掉。
2. **门控不可绕过**。所有升级项沿用既有 Gate 体系（Gate 0A-Tech / 0B / Gate 1 / Gate 2）与量化验收标准（如量化后幻觉增量 ≤0.5%、准确率保留 ≥98%），不因"新技术"降低门槛。
3. **许可先行**。NMPA 注册视角下，凡进入训练/推理链路的模型与数据集，先过许可证审查（ Ultrasound-CLIP 无 license 声明、US-365K 未声明许可、甲状腺无可商用公开数据集——均为 14 号文档已登记红线）。
4. **双 Profile 约束**。compact（基层，llama.cpp/单机）与 full（三甲，vLLM/K8s）的差异必须逐项评估；升级项默认 compact 可降级旁路。
5. **确定性优先**。安全关键路径（禁忌校验、同意校验、脱敏硬规则）保持规则引擎承担，LLM 类组件只做非安全关键的增强层，且必须可降级。

### 4.2 推理服务层

- **vLLM**：~~升级至当前稳定版并固定版本号~~ → **2026-10-01 已切换为官方 OpenAI server**（`python -m vllm.entrypoints.openai.api_server`，替代原自写 `vllm_server.py` 的 `LLM()` 包装——后者无 continuous batching，并发实际串行，官方 server + 大 KV cache 后 780 例评测 3.25h→5min）。待办：**版本号固定**（现仍是浮动版本，违反"27 项精确锁定"）。
- **llama.cpp**：**2026-10-01 弃用**。两层原因：①部署的 llama-b11272 预编译包是 CPU-only 构建（`ldd` 无 CUDA 库，`--n-gpu-layers` 被静默忽略），7B 实际跑在 8 线程 CPU 上（2677 tok/40s）；②双引擎一致率口径随之失效。原 GBNF 约束解码条目作废，P0-2 全部走 vLLM guided decoding（`response_format: json_schema`）。
- **SGLang**（`sgl-project/sglang`）：**观察项，不迁移**。其 RadixAttention 前缀缓存与本系统"固定系统提示 + 专科模板"请求模式契合，但 2026 年各推理框架性能差异 <30%，迁移收益不抵双引擎一致率验证成本；若门控最终决定"统一单一推理框架"（01 §5.7 备选），届时一并决策。

### 4.4 生成质量与安全护栏

- **Langfuse**（`langfuse/langfuse`，MIT，自托管）：新增 LLM 专属可观测旁路——调用链 trace、prompt 版本管理、评测数据集管理（双引擎 ≥700 例测试集、faithfulness 集合直接受益）、灰度期质量看板。与 VictoriaMetrics/Prometheus **互补不替换**；支持 OTLP，可复用 P0-1 接线后的 OTel 管道。**本规划中投入产出比最高的新增组件**。
- **NeMo Guardrails**（`NVIDIA/NeMo-Guardrails`）或 **Llama Guard 3-1B**：作为融合输出之后的语义护栏微服务。红线：禁忌校验、同意校验、脱敏硬规则仍由 SafetyGateway 规则层独立承担（fail-closed，01 §3.4）；LLM 护栏只做对话层语义过滤，必须可降级旁路，不进安全关键路径。
- 国密（SM2/SM3/SM4/TASSL）、Vault Transit、TPM/X.509 设备认证、审计外部公证：**维持文档既定二期节奏**（09 §8/§9/§10），不提前。

## 6. 与文档既定规划的对照结论

- **采纳并具体化**：M³Bind（+新增 OpenUS/USF-MAE 候选）、HanLP 评估（09 §24）、Neo4j（AGE 优先验证）、Kafka、gRPC、联邦学习（补 Flower/Opacus 选型）、Whisper 备选（+Qwen3-ASR）。
- **替代**：Ultrasound-CLIP 许可风险的商业安全替代，从"bge-m3-medical 纯文本降级"（10 §八 v1.1）升级为"Qwen3-VL-Embedding 多模态腿"——保留多模态能力而非丧失；原降级路径仍保留为最后兜底。
- **新增**（文档未提但缺口指向）：约束解码、专用 NLI 判官、Langfuse、RAGFlow DeepDoc、import-linter、Cornerstone3D、依赖库替换（jose/passlib）。
- **明确不做**：替换自研 RAG 管线；迁移 SGLang（仅观察）；一期引入 LLM 护栏进安全关键路径；Mamba（违反 GGUF 硬约束，维持文档结论）。

# 后

### D.3 行为差异与风险核对（已逐一核对）

| 差异点 | 结论 |
|---|---|
| 异常体系 | jose `JWTError` → PyJWT `InvalidTokenError`（基类 `PyJWTError`）；现有双密钥轮换回退逻辑（`auth.py:82-99`）逐 key try/except 结构不变 |
| `options={"verify_exp": True}` | PyJWT 支持同名 option，且默认即为 True，行为不变 |
| aud/iat 校验 | 本系统 token 无 aud claim、iat 为 int —— PyJWT 默认行为不变 |
| `kid` header | 仅用于签发（HSM 侧），验签显式传 public key，不受影响 |
| 存量 token | 验签库更换不影响既有 token 有效性（同一 RSA 公钥、同一 RS256） |
| 存量密码哈希 | bcrypt 库不变（仅脱离 passlib 转直依赖），DB 中 `$2b$` 哈希完全兼容 |
| 环境突变风险 | **jose/passlib 卸载会改变共享 Python 环境** —— pip 操作必须等 T2c 等并行任务结束后执行 |

## 5. 性能专项：端到端延迟优化（2026-09-30 立项，用户要求纳入开发计划）

**现状实测（真机）**：管线单例 12.7~26s，超时窗口外可达 >150s。分解：
fusion 层 19.6s（Self-RAG/CRAG 重试链的**串行 LLM 调用**，占 74%）+
dispatcher 2.9s + 嵌入/检索 ~1s。**GPU 算力过剩，慢在架构**：串行调用链
+ 无前缀缓存 + 每次调用重复处理 ~4000 token 固定前缀。

**方法论（业界权威，2026-09-30 调研）**：
- Continuous batching（Anyscale 实证 23x 吞吐、p50 延迟同步降低）——已迁移
  llama-server 落地 ✓
- **Prefix caching**：固定前缀（系统提示+专科模板+知识格式头）KV 复用，
  诊断 prompt 5943 tokens 中约 4000 为固定前缀——llama-server `--cache-reuse`、
  vLLM `--enable-prefix-caching`，预期 TTFT 降 50%+
- **延迟预算管理**（AWS RAG tuning）：每阶段设 budget（嵌入 50ms/检索
  300ms/rerank 100ms/生成 4s/判官 2s），超预算降级而非重试
- **并行 retrieval + 融合层并发化**（Ailog/Hivenet）：多腿检索并行、
  Self-RAG/CRAG 检查用 asyncio.gather 而非串行链
- **Cut at confidence**：reranker 置信度断崖处截断 chunks——更短 prompt
  直接降低 LLM 时延
- Reranker 超时 fallback 到向量序（防单点拖垮）
- 语义缓存：相似查询（嵌入相似度 >0.95）直接返回缓存结果
