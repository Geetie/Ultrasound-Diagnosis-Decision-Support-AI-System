## 二、P1中风险问题修复（必须在Gate 0A前完成）

### 2.1 完善缓存防护机制

**问题**：缓存穿透、击穿、雪崩防护机制不完善

**修复方案**：新增完整的缓存防护体系

#### 2.1.1 缓存穿透防护

| 防护措施 | 说明 | 配置项 |
|---------|------|--------|
| 布隆过滤器 | 在知识查询前过滤不存在的key | `CACHE_BLOOM_FILTER_SIZE`, `CACHE_BLOOM_FILTER_ERROR_RATE` |
| 空值缓存 | 缓存查询结果为空的key，TTL=5分钟 | `CACHE_NULL_TTL_MINUTES` |

**实施要点**：
- 布隆过滤器在启动时加载所有知识库key
- 空值缓存的key前缀：`cache:null:{key_hash}`
- 查询流程：先查布隆过滤器 → 不存在直接返回空 → 存在查缓存 → 缓存空返回空 → 否则查数据库

#### 2.1.2 缓存击穿防护

| 防护措施 | 说明 | 配置项 |
|---------|------|--------|
| 热点key永不过期 | 高频访问的知识条目（如TI-RADS标准）设置永不过期 | - |
| 互斥锁保护 | key失效时，同一时间只有一个请求去数据库加载 | `CACHE_BREAKDOWN_PROTECTION_ENABLED` |

**实施要点**：
- 热点key列表：系统启动时根据历史访问数据生成Top-N热点key
- 互斥锁使用Redis SET NX EX实现
- 获取锁失败的请求等待100ms后重试，最多3次

#### 2.1.3 缓存雪崩防护

| 防护措施 | 说明 | 配置项 |
|---------|------|--------|
| TTL随机化 | 缓存TTL增加±10%随机偏移，避免同时失效 | `CACHE_TTL_RANDOMIZATION_PERCENT` |
| 缓存预热 | 系统启动时预热Top-N热点知识条目 | `CACHE_WARMUP_TOP_N` |

**实施要点**：
- TTL随机化：`actual_ttl = base_ttl ± (base_ttl * random_percent / 100)`
- 预热在后台异步进行，不阻塞系统启动
- 预热失败记录警告日志，不影响系统启动

### 2.3 明确模块职责边界

**问题**：中央调度智能体与融合层职责边界不清晰

**修复方案**：

| 模块 | 职责 | 不包含 |
|------|------|--------|
| 中央调度智能体 | 任务拆分与分配、负载均衡、多器官协调（任务编排） | 跨器官关联校验逻辑 |
| 融合层 | 结果融合、跨器官关联校验、一致性检查 | 任务分配 |
| 知识查询智能体 | 知识检索、CRAG补充检索、缓存管理 | - |

**CRAG补充检索链路**：
- Self-RAG质检失败（无依据/依据不足）→ 向中央调度发送补充检索请求 → 中央调度路由到知识查询智能体 → 知识查询智能体执行CRAG → 返回结果 → Self-RAG重新生成

### 2.4 统一边缘端WebSocket认证流程

**问题**：边缘端WebSocket认证流程描述不一致

**修复方案**：

| 阶段 | 说明 |
|------|------|
| 连接建立 | WebSocket连接URL：`ws://edge-ip:9100/ws/v1/nav?session_id={session_id}`（session_id非敏感，用于路由） |
| 首条消息认证 | 连接建立后首条消息发送：`{"type": "auth", "device_id": "...", "api_key": "..."}` |
| DICOM通道认证 | DICOM通道复用导航通道签发的短期Token |

**重要原则**：
- API Key禁止通过URL参数传递，只能通过消息体传递
- session_id可以通过URL参数传递（非敏感，仅用于路由）

### 2.5 补充技术选型验证计划

**问题**：缺少技术选型验证计划和备用方案切换机制

**修复方案**：

#### 2.5.1 Ultrasound-CLIP商业授权验证

| 阶段 | 时间 | 验证内容 | 不通过处理 |
|------|------|---------|-----------|
| Gate 0启动前 | - | 启动商业授权谈判 | - |
| Gate 0启动后30天 | T+30d | 确认是否获得商业授权意向 | 自动切换到bge-m3-medical主方案 |

**备用方案切换影响**：
- 纯文本检索召回率目标：≥90% → ≥85%
- 多模态检索I2T@10指标：取消
- Ultrasound-CLIP仍可作为备用方案保留

#### 2.5.2 pynetdicom性能预评估

| 阶段 | 时间 | 验证内容 | 通过标准 |
|------|------|---------|---------|
| 项目立项前 | - | pynetdicom vs python-gdcm性能对比 | - |
| Gate 0A | - | 选定方案在30fps场景下验证 | CPU占用<30%，接收延迟<50ms |

**决策树**：
- 预评估发现python-gdcm性能显著更优 → 直接采用python-gdcm
- 预评估pynetdicom达标 → Gate 0A验证
- Gate 0A验证不通过 → 拆分DICOM SCP为独立进程

#### 2.5.3 分词选型评估

| 评估顺序 | 分词方案 | 通过标准 | 不通过处理 |
|---------|---------|---------|-----------|
| 1 | HanLP轻量版 + UDAF | F1≥94%，维护性S级 | 评估下一方案 |
| 2 | THULAC + UDAF | F1≥92%，维护性S级 | 评估下一方案 |
| 3 | pkuseg-medicine | F1≥96%，Python 3.11+兼容 | Fork维护 |
| 4 | jieba + UDAF | F1≥90% | 运行时故障恢复降级路径 |

**维护性评级标准**：
- S级：社区活跃（近6个月有更新），全Python版本兼容，文档完善
- A级：社区活跃，主流Python版本兼容，文档完善
