# 安全合规

## 1. 数据全生命周期安全

| 阶段 | 安全措施 | 责任方 |
|---|---|---|
| 采集 | 最小必要原则，仅采集诊断所需数据 | 接入层 |
| 传输 | TLS 1.3 加密（一期使用标准 TLS 1.3；国密 SM2/SM3/SM4 支持为二期增强，需引入 TASSL 或 OpenSSL 国密分支，详见 [09-二期规划](09-二期规划与远期增强.md)） | 网络层 |
| 存储 | 静态数据 AES-256 加密，密钥由 HSM 管理（compact Profile 替代方案见 §2.1.1） | 存储层 |
| 处理 | 前置脱敏后处理，患者身份与诊断数据分离 | 标准化层 |
| 边缘端 DICOM 元数据剥离 | 边缘端 DICOM 解码后立即剥离身份标识字段（PatientID、PatientName、PatientBirthDate 等），仅保留诊断必需字段；边缘端日志禁止记录身份标识原始值 | 边缘端预处理层（详见 [01-系统架构设计](01-系统架构设计.md) §1.2） |
| 智能体间传输 | 中间数据经前置脱敏，不含可直接识别患者身份的信息 | 标准化层 |
| 输出 | 融合层输出前强制脱敏校验，防御 LLM 推理中意外生成的身份信息 | 融合层 |
| 销毁 | 门诊 15 年、住院 30 年，到期自动清理 | 运维层 |
| 边缘端设备数据擦除 | 设备注销前须执行远程数据擦除（导航记录缓存、日志、模型配置中的敏感数据）；设备离线时标记为"待擦除"，下次上线时强制执行擦除后方可重新注册 | 运维层 |

**边缘端 API Key 安全管理**：边缘端设备认证使用 API Key + HKDF 派生密钥方案，API Key 的初始配置、定期轮换（180 天）、泄露应急处理、设备注销等生命周期管理规范详见 [01-系统架构设计](01-系统架构设计.md) §2 API Key 生命周期管理规范。API Key 禁止记录到任何日志中，本地加密存储（AES-256），泄露时立即吊销（无过渡期）。

**数据保留策略明细**：

| 数据类型 | 存储位置 | 保留时长 | 法规依据 |
|---|---|---|---|
| 诊断日志（含推理链路） | PostgreSQL + 对象存储 | 门诊 15 年 / 住院 30 年 | 《医疗机构病历管理规定》 |
| 修改日志 | PostgreSQL + 对象存储 | 30 年 | IEC 62304 |
| 操作/访问日志 | Elasticsearch（full）/ PostgreSQL `audit_logs` 表（compact） | 5 年 | 内部合规 |
| 会话热缓存 | Redis（读加速）+ PostgreSQL（主存储，双写） | 最大 4 小时 TTL | 业务需求，与 [01-系统架构设计](01-系统架构设计.md) §4 三阶段模型统一。**注意**：会话状态保留 Redis 双写（查询频率高且对延迟敏感），同意状态已取消 Redis 双写（直写 PostgreSQL，直查 PostgreSQL），两者双写策略不同，详见 [01-系统架构设计](01-系统架构设计.md) §4 |
| 会话温存储 | PostgreSQL | 7 天快速回看 | 供医生回看近期检查会话 |
| 会话合规归档 | PostgreSQL + 对象存储 | 门诊 15 年 / 住院 30 年 | 合规归档，与诊断日志保留期一致 |
| 审计日志 | Elasticsearch（full）/ PostgreSQL `audit_logs` 表（compact）+ 对象存储（冷归档） | 门诊 15 年 / 住院 30 年 | GB/T 35273 |
| 脱敏映射表 | PostgreSQL（加密） | 同诊断日志 | 数据还原需要 |

## 2. 脱敏规则

依据 GB/T 35273-2020 设计：

| 数据类型 | 脱敏方式 | 示例 |
|---|---|---|
| 患者姓名 | 全部替换为匿名令牌 | 张三 → PATIENT_001 |
| 身份证号 | 全部掩码（全星号替换） | \*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\* |
| 手机号 | 仅保留后 4 位 | \*\*\*\*\*\*\*5678 |
| 住址 | 仅保留到市级 | 北京市\*\*\* |
| 出生日期 | 仅保留年份 | 1980-\*\*-\*\* |
| 年龄（整数） | 不脱敏 | 45——年龄为诊断必需的临床信息（如 TI-RADS 分级考虑年龄因素、儿科超声与成人标准不同），不属于直接标识符（无法从整数年龄反推完整出生日期），无需脱敏。`patient_context.age` 字段由前端从 HIS 获取出生日期后计算整数年龄传入，完整出生日期不通过此字段传递 |

> **三重防线说明**：标准化层前置脱敏为第一道防线（在数据分发给智能体之前完成），融合层输出脱敏校验为第二道防线（防御 LLM 推理中意外生成的身份信息，如模型训练数据中的姓名泄露），SafetyGateway 结构化身份模式拦截为第三道防线（快速正则匹配兜底）。三道防线防御目标不同，不可互相替代。**`all_passed` 语义定义**：`all_passed=True` 表示三层安全校验全部通过——第 1/2 层 `modified=True` 属于正常脱敏行为（数据被正确脱敏），不影响 `all_passed` 判定；仅当第 3 层 SafetyGateway 校验 `passed=False` 或系统处于 `degraded_mode` 时，`all_passed=False`，表示存在安全风险。**SafetyGateway 规则异构冗余**：SafetyGateway 的结构化正则模式规则（`desensitization_rules_safety.yaml`）由独立编写的规则集构成，不直接复制主规则源（`desensitization_rules.yaml`）中的正则表达式，实现规则层面的异构冗余，降低同一逻辑缺陷同时击穿三道防线的风险。详见 [01-系统架构设计](01-系统架构设计.md) §3.3 三道防线严格职责分层。

> **双重降级场景脱敏保障**：当融合层脱敏服务超时（第二道防线降级）且 SafetyGateway 不可达（第三道防线降级）同时发生时，系统仅剩标准化层前置脱敏（第一道防线）提供脱敏保障。此场景下系统执行以下策略：（1）输出级别降为仅观察描述（`observations` 白名单字段），过滤所有 `diagnostic_conclusion`；（2）标记 `conclusion_suppressed: true` + `fusion_degraded: true` + `safety_gateway_unavailable: true`；（3）前端强制显示"双重安全校验缺失，请人工核验"红色警告；（4）此场景下输出须由主任级医师人工审核后方可纳入病历。**最低脱敏保障**：即使双重降级，标准化层前置脱敏仍确保患者身份信息（姓名、身份证号、手机号等）在数据进入系统时已被脱敏，`observations` 白名单字段仅包含不含身份信息的医学术语，脱敏保障水平不低于"前置脱敏 + 白名单过滤"双重保障。

### 2.1 脱敏-还原映射表安全

| 安全维度 | 规格 |
|---|---|
| 加密算法 | AES-256-GCM，每条记录独立加密，密钥由 HSM 管理 |
| 密钥管理 | 映射表加密密钥与 JWT 签名密钥分离，使用不同 HSM 密钥槽 |
| 访问控制 | 仅 `DesensitizationRestoreService` 可访问，每次访问记录审计日志 |
| 密钥轮换 | 每 180 天轮换，后台异步重加密，重加密吞吐 ≥ 1000 条/秒，全量重加密在 4 小时内完成（百万级记录）。**密钥版本标识**：映射表每条记录增加 `key_version` 字段，标识该记录使用的加密密钥版本。密钥轮换期间新记录用新密钥（`key_version=N+1`）、旧记录用旧密钥（`key_version=N`），查询时根据 `key_version` 选择对应密钥解密，避免盲尝试双密钥。重加密完成后更新 `key_version` |
| 泄露应急 | 立即全量重新生成令牌 + 重加密 + 通知数据安全官 |
| 容量与性能 | P99 < 10ms（含 HSM 解密），支持百万级记录量 |
| 访问频率监控 | 还原请求频率按部署规模分档监控——compact Profile（日检查量 ≤ 50 例）：单小时超过 100 次触发安全告警；full Profile（日检查量 > 50 例）：单小时超过 200 次触发安全告警。阈值通过 `DESENSITIZATION_RESTORE_RATE_LIMIT` 配置项设置（与 [02-核心流程与知识库](02-核心流程与知识库.md) §5.6 统一）。告警时记录至审计日志，通知数据安全官 |

**HSM 性能保障措施**：

| 措施 | 说明 |
|---|---|
| HSM 连接池 | 维护 HSM 连接池（默认 10 连接），避免频繁建连开销 |
| 本地会话密钥缓存 | 解密后的短期会话密钥缓存至内存（TTL = 5 分钟），减少 HSM 调用次数 |
| 性能验证 | 一期开发阶段须在模拟生产负载下验证 P99 < 10ms 达标；若网络 HSM 延迟过高，评估本地 HSM 或 HSM 代理方案 |

### 2.1.1 Compact Profile 密钥管理方案

Compact Profile 基层部署环境采用以下密钥管理方案：

| 维度 | Compact Profile 方案 | 与 full Profile 的差异 |
|---|---|---|
| 密钥存储 | **默认方案**：USB HSM 令牌（如 YubiHSM 2，成本约 ¥2000-3000）；**临时过渡方案**：SoftHSM（PKCS#11 软件实现）+ 文件系统加密（LUKS/dm-crypt），上线后 90 天内必须替换为硬件 HSM | 基层医院安全能力最弱（通常无专职安全人员、系统补丁更新滞后、USB 接口未禁用），将安全等级最低的 SoftHSM 长期部署在安全能力最弱的环境中是风险叠加，因此硬件 HSM 为默认方案 |
| 密钥轮换周期 | 60 天（full Profile 为 180 天） | 更短轮换周期降低密钥泄露影响窗口 |
| 脱敏映射表加密 | AES-256-GCM，密钥由 HSM（USB HSM 或 SoftHSM）管理 | 与 full Profile 加密算法一致，仅密钥存储方式不同 |
| JWT 签名密钥 | RS256，私钥存储于 HSM（USB HSM 或 SoftHSM） | 与 full Profile 签名算法一致 |
| 访问控制 | USB HSM：硬件防篡改 + PIN 码；SoftHSM：令牌 PIN 码 + 文件系统权限（仅 root 可访问） | USB HSM 安全等级显著高于 SoftHSM |
| 审计增强 | 每次密钥使用记录审计日志（含调用方、时间、操作类型） | 补偿软件密钥存储的审计可见性 |
| 安全评估 | 一期上线前须通过渗透测试验证密钥管理方案安全性 | — |

> **安全风险说明**：SoftHSM 为软件实现，密钥材料存储于磁盘文件，存在被具备 root 权限的攻击者提取的风险。基层医院恰恰是最缺乏 IT 安全能力的环境，SoftHSM 仅作为临时过渡方案（上线后 90 天内必须替换为 USB HSM 令牌），不作为长期生产方案。USB HSM 令牌（如 YubiHSM 2）提供硬件级防篡改保护，成本可控（约 ¥2000-3000），是 compact 模式的默认密钥管理方案。**SoftHSM 超期强制告警机制**：系统启动时检查密钥存储类型，SoftHSM 运行超过 90 天后，每次启动在管理界面弹出不可关闭的警告"SoftHSM 已超过 90 天安全期限，请立即安装 USB HSM"，并每周触发 Critical 告警通知科室主任和上级医院运维。不建议自动降级或阻止系统启动（可能影响临床工作），但通过告警机制确保替换不被遗忘。

> **生产环境 SoftHSM 降级方案**：USB HSM 硬件故障时（基层医院 IT 能力有限，USB 设备松动/损坏风险较高），可临时启用 PKCS#11 SoftHSM 作为降级方案（须运维管理员审批并记录审计日志）。SoftHSM 降级期间安全等级降低（密钥存储于文件系统而非硬件安全模块），须在 72 小时内恢复 USB HSM 或更换设备。SoftHSM 降级期间系统功能限制：暂停新会话创建（已有会话可继续完成）、报告签发附加"密钥降级模式"标记。SoftHSM 密钥文件须存储于加密文件系统（如 LUKS）并设置严格文件权限（root only）。

**HSM 长时间不可用处理**：

| 阶段 | 处理策略 |
|---|---|
| 0-5 分钟 | 降级为本地会话密钥缓存（TTL 5 分钟），触发 Critical 告警 |
| 5-30 分钟 | 系统进入"受限模式"：暂停新会话创建（E4013），已有会话仅输出脱敏后结果（不还原患者信息），报告生成暂停。**应急签发方案**：HSM 不可用超过 5 分钟时，管理员可启用应急签发模式——使用 HSM EMERGENCY_SIGNING 槽位密钥签发报告，报告标记"应急签发，待 HSM 恢复后补验证"。应急签发的报告须在 HSM 恢复后 24 小时内完成补签名验证，未验证的报告标记"待验证"并通知签发医生。应急签发模式须由管理员手动启用（非自动），启用操作记录审计日志 |
| > 30 分钟 | 触发紧急运维响应，评估启动本地 HSM 或 HSM 代理方案；受限模式持续至 HSM 恢复 |

> **HSM 部署建议**：生产环境优先评估本地 HSM（PCIe 卡，如 Thales Luna Network HSM 的本地版本或 AWS CloudHSM 的等价方案），避免网络 HSM 的延迟和可用性风险。本地 HSM 消除网络故障点，P99 延迟更可控。若必须使用网络 HSM，须部署 HSM 代理（如 HashiCorp Vault 的 Transit Engine）作为本地缓存层，减少对远程 HSM 的直接依赖。

> **JWT 签名密钥本地缓存**：JWT 签名验证（公钥）可本地缓存，无需每次请求访问 HSM。JWT 签名操作（私钥）须通过 HSM 执行，但签名请求频率远低于验证频率。一期须在模拟生产负载下验证 HSM 签名 P99 < 5ms，若不达标须评估本地 HSM 方案。

## 3. 审计日志

| 日志类型 | 记录内容 | 保留期限 | 完整性保障 |
|---|---|---|---|
| 操作日志 | 谁、何时、执行了什么操作 | 5 年 | 哈希链签名 |
| 访问日志 | 谁、何时、访问了什么数据 | 5 年 | 哈希链签名 |
| 修改日志 | 谁、何时、修改了什么（含修改前后值） | 30 年 | 哈希链签名 |
| 诊断日志 | 完整推理链路 + 知识库版本号 | 30 年 | 哈希链签名 |

**日志分类判定规则**（与 [05-可观测性与运维](05-可观测性与运维.md) §1 统一）：凡**直接影响诊断结论**的操作一律归入诊断日志（30 年保留），纯系统运维操作归入操作日志（5 年保留）。具体判定标准：

| 操作类型 | 归类 | 判定理由 |
|---|---|---|
| 阈值调整（置信度阈值、分级阈值等） | 诊断日志 | 直接影响诊断结论的生成标准 |
| 模型版本变更（加载、切换、回滚） | 诊断日志 | 模型版本直接决定诊断输出 |
| 知识库更新（新增、修改、删除条目） | 诊断日志 | 知识条目为诊断依据，更新直接影响结论 |
| 脱敏规则更新 | 诊断日志 | 脱敏规则变更可能影响诊断输出内容 |
| 用户登录/登出 | 操作日志 | 不影响诊断结论 |
| 系统配置变更（端口、超时等） | 操作日志 | 不影响诊断结论 |
| 设备注册/注销/隔离/恢复 | 操作日志 | 设备管理操作，不直接影响诊断结论 |
| Redis/PostgreSQL 运维操作 | 操作日志 | 基础设施运维，不直接影响诊断结论 |

**哈希链签名**：每条日志包含前一条日志的 SHA-256 哈希值，形成不可篡改的链式结构。每日自动执行完整性校验，发现哈希链断裂立即触发安全告警。单条日志额外延迟 < 0.1ms。

> **高并发哈希链优化**：哈希链的串行特性在高并发场景下可能成为写入瓶颈。一期采用按 `session_id` 分链策略——每个 `session_id` 维护独立的哈希链，不同会话的日志可并行写入，同一会话内的日志保持串行不可篡改性。全局哈希链通过每日全量日志的 Merkle Tree 根哈希实现，确保跨会话的完整性校验。**跨链校验频率增强**：除每日 Merkle Tree 校验外，增加每小时全量跨链校验（校验所有会话链的哈希连续性），缩短篡改检测窗口至最长 1 小时。关键操作日志（同意状态变更、阈值调整、模型版本变更）除写入会话链外，同时写入全局关键操作链，确保关键操作日志篡改检测窗口 ≤ 1 分钟。**关键操作日志同步写入增强**：关键操作日志在写入全局关键操作链的同时，同步写入独立审计服务（轻量级 HTTP 服务，与主服务同进程但独立存储），将关键操作的篡改检测窗口从 1 分钟缩短至秒级（独立审计服务写入成功即视为已固化，主链断裂时可从独立审计服务恢复）。

**四层校验资源开销评估**：

| 校验层 | 频率 | 预估 CPU 开销 | 预估存储开销 | 说明 |
|---|---|---|---|---|
| 会话链（实时） | 每次写入 | < 0.1ms/次（SHA-256） | 每条日志 + 32B 哈希 | 可忽略 |
| 每小时跨链校验 | 每小时 | ≤ 2s（10 万会话链） | 无额外存储 | compact 模式下会话链数量有限 |
| 每日 Merkle Tree | 每日 | ≤ 30s（百万级日志） | Merkle 树节点约 10MB/日 | compact 模式下日志量远小于 full |
| 关键操作独立审计 | 秒级 | < 1ms/次 | 独立 SQLite 文件，约 1MB/日 | 轻量级服务 |

> compact 模式下四层校验总资源开销预估 < 50MB 内存 + < 100MB/日存储，对 32GB 总内存预算影响可忽略。若实际开销超出预估，可降低跨链校验频率至每 4 小时（`CROSS_CHAIN_VERIFY_INTERVAL_HOURS` 配置项）。**SQLite 写入性能风险与缓解**：关键操作独立审计服务使用 SQLite 存储，高频写入场景下 SQLite WAL 模式可能出现 WAL 文件膨胀和锁竞争。缓解措施：（1）SQLite 配置 WAL 模式 + `synchronous=NORMAL`（平衡安全性与性能，WAL 写入不等待 fsync 完成，但 checkpoint 仍保证数据完整性）；（2）关键操作日志先写入内存环形缓冲区（容量 1000 条），异步刷盘至 SQLite（刷盘间隔 1s），主流程延迟仅受内存写入影响（< 0.1ms）；（3）WAL 文件大小监控：超过 10MB 触发手动 checkpoint，超过 50MB 触发 Warning 告警；（4）独立审计服务启动时从主链恢复最近 1 小时的关键操作日志，确保内存缓冲区中未刷盘的数据不丢失。**SQLite 审计文件存储位置**：compact 模式下 SQLite 审计文件应放置在独立磁盘分区或独立 SSD 分区（首选），避免与 PostgreSQL WAL 产生 I/O 竞争。**禁止使用 tmpfs**——tmpfs 为内存文件系统，系统重启后数据丢失，与"关键操作日志篡改检测窗口 ≤ 1 分钟"的安全目标矛盾。若因性能原因必须使用 tmpfs 加速写入，须增加定时刷盘机制（每 5 秒将 tmpfs 中的 SQLite 数据同步至持久存储），确保重启后数据可恢复。

**哈希链断裂应急处理流程**：

| 步骤 | 操作 | 责任方 |
|---|---|---|
| 1. 隔离 | 断裂点之后的日志条目标记为"待验证"，不删除但暂停依赖这些日志的自动审计 | 系统自动 |
| 2. 定位 | 从断裂点向前回溯，定位最后一条有效日志；向后扫描，定位第一条恢复有效的日志 | 安全运维 |
| 3. 调查 | 分析断裂原因（软件 Bug、存储故障、恶意篡改），检查断裂期间的操作日志和访问日志 | 安全运维 + 数据安全官 |
| 4. 上报 | 若疑似恶意篡改或涉及患者数据，24 小时内上报医院信息安全管理委员会和属地网信部门 | 数据安全官 |
| 5. 修复 | 确认原因后，对断裂段日志重新计算哈希链（保留原始断裂记录作为证据），恢复审计功能 | 安全运维 |
| 6. 归档 | 整个事件过程记录至安全事件档案，保留 30 年 | 安全运维 |

> 外部公证（独立审计服务器/区块链）在合规审计有明确要求时再引入，详见 [09-二期规划](09-二期规划与远期增强.md)。

**日志冷热分层**：

| 阶段 | 存储方式 | 查询性能 | 保留时长 |
|---|---|---|---|
| 热数据 | Elasticsearch（full）/ PostgreSQL `audit_logs` 表（compact） | 秒级查询 | 3 年 |
| 冷数据 | 对象存储（压缩 + 索引，full）/ 本地文件归档（compact） | 分钟级查询 | 至保留期满 |

## 5. 灾难恢复

| 指标 | 目标值 | 实现方式 |
|---|---|---|
| RPO | ≤ 1 小时 | PostgreSQL 每小时增量备份 + WAL 归档；Neo4j 每小时增量备份；Redis AOF（`appendonly yes`，`fsync everysec`）+ 每 6 小时 RDB 快照至对象存储。**安全关键事件（safety_critical 知识更新、同意撤回）同时写入 PostgreSQL `safety_events` 表**，确保 Redis 故障时关键安全事件不丢失（PostgreSQL WAL 保证持久性） |
| 实时导航 RTO | ≤ 15 分钟 | 边缘端降级为仅显示原始图像，后端恢复后自动恢复 |
| 完整诊断 RTO | ≤ 1 小时 | 备用节点自动切换 + 一键重建 |
| 全功能 RTO | ≤ 4 小时 | 完整集群恢复 |
| 备份策略 | 每日全量 + 每小时增量，异地备份 | — |
| 演练频率 | 每季度一次 | 验证 RTO/RPO 达标 |

**Compact Profile 轻量灾难恢复方案**：

compact 模式单机部署下，服务器硬件故障意味着完全不可用，RTO 取决于硬件更换速度。以下轻量方案确保数据安全与快速恢复：

| 维度 | 方案 |
|---|---|
| 每日全量备份 | 每日凌晨 2:00 自动执行 `pg_basebackup` + Redis RDB 快照 + 配置文件导出，加密后传输至 NAS/对象存储 |
| 备用机预配置 | 部署时同步准备一台备用机（预装系统 + 依赖 + 配置），备用机保持关机状态，故障时开机即可恢复 |
| 一键恢复脚本 | `scripts/disaster_recovery.sh`：停止服务 → 恢复全量备份 → 重放增量 WAL → 校验数据完整性 → 启动服务。恢复时间目标 ≤ 1 小时（含硬件更换） |
| 备份验证 | 每月自动在备用机执行恢复演练，验证备份可用性 |
| RTO 评估 | compact 模式实际 RTO = 硬件更换时间 + 数据恢复时间。若医院无备用机，建议与设备供应商签订 4 小时响应 SLA |

**断电保护措施**：

| 维度 | 方案 |
|---|---|
| UPS 建议 | compact 模式建议配置 UPS（不间断电源），支持至少 15 分钟运行时间，确保正常关机流程完成 |
| PostgreSQL 关键写入 | 安全关键事件（同意状态变更、safety_critical 知识更新）写入 PostgreSQL 时使用 `synchronous_commit=on`（默认值），确保 WAL 刷盘后才返回成功，断电不丢失 |
| Redis AOF 策略 | 默认 `fsync everysec`（最多丢失 1 秒数据）。安全关键事件同时写入 PostgreSQL `safety_events` 表（双写），Redis 数据丢失可从 PostgreSQL 恢复 |
| 边缘端断电 | 边缘端 OTA 原子性保障确保断电不影响当前运行模型版本（详见 §5 边缘端备份与恢复） |
| GPU 推理中断电 | GPU 推理为无状态计算，断电仅丢失当前在途请求，不影响已持久化的诊断结果 |

**备份恢复操作规范**：

| 操作 | 步骤 | 验证方法 |
|---|---|---|
| 全量备份 | `pg_basebackup` + Neo4j `dump`；加密后传输至异地存储 | 检查备份文件完整性（SHA-256 校验和） |
| 增量备份 | PostgreSQL WAL 归档 + Neo4j 增量事务日志 | 每日自动校验 WAL 连续性 |
| 数据恢复 | 停止服务 → 恢复最近全量 → 重放增量 WAL → 校验数据完整性 → 启动服务 | 恢复后执行 `pg_checksums` + 抽样查询验证 |
| 异地备份传输 | TLS 加密传输，传输后校验远端文件 SHA-256 | 传输日志 + 校验和比对 |
| 演练记录 | 记录演练时间、RTO/RPO 实测值、发现的问题 | 演练报告归档至审计日志 |

**边缘端备份与恢复**：

| 维度 | 方案 |
|---|---|
| 配置备份 | 存储于后端配置中心，边缘端启动时拉取；本地保留缓存 |
| 模型版本管理 | 后端统一管理，OTA 推送；本地保留最近 2 个版本，秒级回退；空闲时推送 |
| 模型完整性校验 | OTA 推送时附带 SHA-256 校验和 + RSA 签名；边缘端接收后校验校验和与签名，校验失败拒绝加载并告警；校验通过方可激活新模型 |
| OTA 原子性保障 | 新模型完整下载至独立目录并校验通过后，原子性替换当前模型符号链接/引用；更新中断（网络断开、设备断电）不影响当前运行版本；部分下载的临时文件在下次 OTA 启动时自动清理；边缘端始终保留最近 2 个完整版本，确保秒级回退 |
| OTA 失败回退 | 新模型加载后若启动自检失败（推理结果异常），自动回退至上一版本并触发 Warning 告警 |
| 设备恢复 | 硬件故障时更换设备后一键重装，恢复时间 ≤ 30 分钟 |

**边缘端安全增强措施**：

| 维度 | 措施 | 说明 |
|---|---|---|
| 设备身份认证 | 边缘端设备证书 + 双向 TLS | 边缘端与后端通信使用设备证书认证，防止设备伪造 |

| 防火墙规则 | 出站白名单 | 仅允许边缘端访问后端服务 IP/端口，禁止其他出站连接 |

**HSM 应急签发方案增强**：

| 阶段 | 处理策略 | 安全保障 |
|---|---|---|
| 正常模式 | HSM 签名（JWT_SIGNING / DATA_ENCRYPTION 槽位） | 硬件级安全保护 |
| 应急模式 | HSM EMERGENCY_SIGNING 槽位密钥签名 | 独立密钥槽位隔离，仅管理员手动启用，记录审计日志 |

**边缘端时间同步规范**：

| 维度 | 方案 |
|---|---|
| 同步协议 | NTP，同步至医院时间服务器（优先）或公网 NTP 池（降级） |
| 同步频率 | 每 10 分钟同步一次 |
| 偏差告警 | 本地时钟与 NTP 服务器偏差 > 1s 触发 Warning 告警；> 5s 触发 Critical 告警 |
| 偏差降级 | 偏差 > 5s 时，审计日志中标注"时钟偏差超限"，诊断功能不受影响但日志时间戳可信度降低 |
| NTP 不可达 | 连续 3 次同步失败触发 Warning 告警；本地时钟自由运行，日志标注"NTP 不可达" |
| NTP 长时间不可达 | NTP 不可达超过 1 小时触发 Critical 告警，审计日志时间戳可信度降低，IEC 62304 合规风险增加。边缘端应增加 RTC（实时时钟）电池备份，确保短时间 NTP 不可达时时钟仍准确（偏差 < 1s/天） |

| 检查中撤回 | 已生成结论标记"患者已撤回 AI 辅助同意"，前端隐藏 AI 入口，边缘端停止 AI 标注 |

| 检查中撤回-输出拦截 | 融合层在返回诊断结果前独立查询 PostgreSQL 获取最新同意状态（两阶段校验：入口快速拒绝 + 输出前实时校验，详见 [01-系统架构设计](01-系统架构设计.md) §3.4），若已撤回则拦截输出并返回 E1010；此同步校验确保异步事件传播窗口内无诊断结果逃逸。**安全窗口说明**：从融合层输出前校验通过到前端展示之间存在时间窗口（通常 < 500ms），在此窗口内撤回事件可能尚未被前端感知。安全防线完全由后端 SafetyGateway 保障——SafetyGateway 输出前直查 PostgreSQL 获取同意状态快照（`consent_status_at_output` 字段），前端信任后端判断即可。撤回事件通过 WebSocket `session_terminated` 推送处理——前端收到撤回事件后立即隐藏诊断结论区域并显示提示"患者已撤回 AI 辅助同意，诊断结果不可用"（与 [01-系统架构设计](01-系统架构设计.md) §3.4 及 [08-前端交互](08-前端交互与使用指南.md) §2.2 一致） |
| 检查中撤回-前端展示层同意状态处理 | 诊断结果到达前端后，前端根据后端响应中的 `consent_status_at_output` 字段（SafetyGateway 输出前直查 PostgreSQL 获取的同意状态快照）决定是否展示诊断结论区域，**无需额外调用** `GET /api/v1/consent/{patient_id}`。后端 SafetyGateway 已确认同意状态为 granted 方输出结果，前端信任后端判断即可。撤回事件通过 WebSocket `session_terminated` 推送处理——前端收到撤回事件后立即隐藏诊断结论区域并显示提示"患者已撤回 AI 辅助同意，诊断结果不可用"。此设计减少不必要的 API 调用和 PostgreSQL 查询负载，安全防线完全由后端 SafetyGateway 保障（与 [01-系统架构设计](01-系统架构设计.md) §3.4 输出前同步同意状态校验及 [08-前端交互](08-前端交互与使用指南.md) §2.2 一致） |
| 检查后撤回 | 已生成报告保留，标记 AI 辅助部分为"患者事后撤回同意"；**HIS/PACS 同步**：已推送至 HIS/PACS 的报告，撤回后须向 HIS 推送撤回通知消息（FHIR Communication 资源或 HL7 v2 ACK 消息，与原始报告推送方式一致），确保 HIS 端医生能看到撤回标记。PACS 中已存储的 DICOM SR 报告无法远程修改，但撤回通知须包含报告唯一标识（StudyInstanceUID）与撤回时间戳，供 PACS 端人工标注 |
| 后端拦截 | 撤回后诊断请求接口返回 HTTP 403 + E1010（已撤回）；未签署同意返回 HTTP 403 + E1008（未签署） |
