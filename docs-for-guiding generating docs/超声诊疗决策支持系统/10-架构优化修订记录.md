## 修订版本：v1.1 (2026-05-06)

### 一、Redis降级路径简化（高风险问题1）

#### 1.1 问题分析
原设计存在5层Redis降级路径，组合验证复杂度极高，一期集成测试难以全面覆盖。

#### 1.2 优化方案
**一期强制采用简化方案**，将Redis定位为"性能加速层"而非"核心依赖"：

| 组件 | 一期简化方案 | 原设计 | 优化效果 |
|---|---|---|---|
| 调度租约 | compact: 直接使用PG Advisory Lock<br/>full: Redis SET NX EX + PG降级 | Redis SET NX EX + PG Advisory Lock降级 | compact模式消除降级切换 |
| 消息队列 | compact: 直接使用PG轮询<br/>full: Redis Streams | Redis Streams + PG轮询降级 | compact模式消除降级切换 |
| 安全关键事件 | 双写PG + Redis，Redis不可用时轮询PG `safety_events`表 | 同左 | 保持不变 |
| 会话状态 | 写入时顺序双写PG+Redis，Redis不可用时直查PG | 同左 | 保持不变 |
| 同意状态 | 直写PG，Redis仅作只读缓存(TTL 60s) | 同左 | 保持不变 |

#### 1.3 实施要求
- **配置项默认值调整**：
  - compact模式：`SCHEDULING_LEASE_BACKEND=pg_advisory_lock`（默认值）
  - compact模式：`MESSAGE_QUEUE_BACKEND=pg_polling`（新增配置项）
  - compact模式：`REDIS_ROLE=performance_accelerator`（新增配置项，明确Redis定位）
  
- **RedisDegradationManager职责简化**：
  - compact模式：仅负责检测Redis可用性并切换缓存读取策略，不涉及数据写入路径切换
  - full模式：保持原设计的完整降级能力

- **测试覆盖要求**：
  - compact模式Redis宕机端到端测试简化为：验证PostgreSQL降级路径的正确性，无需验证组合降级
  - full模式保持原测试要求

### 二、边缘端导航标注安全窗口强化（高风险问题2）

#### 2.1 问题分析
二期直推模式下存在~50ms安全窗口，窗口期内医生可能看到未校验的导航标注。

#### 2.2 优化方案
**一期强制采用后端中转模式**，消除安全窗口：

| 配置项 | 一期强制值 | 说明 |
|---|---|---|
| `EDGE_DIRECT_WS_ENABLED` | `false` | 禁止启用直推模式 |
| `EDGE_NAV_SECURITY_WINDOW_MS` | `0` | 安全窗口为0（后端中转模式） |

**二期直推模式启用前置条件**（强制满足方可启用）：
1. 边缘端导航标注完整性校验已实现（设备私钥签名）
2. 边缘端标签白名单与后端实体校验规则一致性验证通过（移除率<5%）
3. Gate 1集成测试覆盖直推模式所有安全场景
4. 科室主任审批并记录审计日志

#### 2.3 实施要求
- **一期部署检查清单**：启动时强制校验`EDGE_DIRECT_WS_ENABLED=false`，若为true则拒绝启动并触发Critical告警
- **二期启用流程**：配置变更→安全评估→科室主任审批→Gate 1验证→灰度发布

### 三、Ultrasound-CLIP商业许可风险缓解（高风险问题3）

#### 3.1 问题分析
Ultrasound-CLIP为非商业许可，与NMPA注册后的商业化部署存在潜在冲突。

#### 3.2 优化方案
**强化并行备选策略**，确保切换成本可控：

| 时间节点 | 强制要求 | 责任方 |
|---|---|---|
| 项目立项前 | 启动商业授权谈判 | 项目经理 |
| Gate 0启动后30天 | 获得商业授权意向书面确认 | 项目经理 |
| Gate 0A阶段 | 完成bge-m3-medical方案架构适配验证 | 技术负责人 |
| Gate 0A阶段 | 完成Ultrasound-CLIP与bge-m3-medical端到端对比验证 | 技术负责人 |

**并行备选策略实施要求**：
1. **代码层面**：`EmbeddingService`接口须同时支持`dim=768`（Ultrasound-CLIP）和`dim=1024`（bge-m3-medical），Gate 0A验证时须同时通过两种维度的单元测试
2. **数据层面**：Gate 0A阶段须使用bge-m3-medical构建小规模（≥500条）对比索引，验证端到端检索链路可切换性
3. **时间线影响评估**：若30天截止日期内未获得商业授权确认，切换至bge-m3-medical主方案后，Gate 0A时间线最多延长1周

#### 3.3 商业过渡路径决策树
```
Gate 0启动后30天内
├─ 获得商业授权意向确认
│  └─ 继续Ultrasound-CLIP主方案
│     └─ Gate 1前完成正式商业授权协议签署
└─ 未获得商业授权意向确认
   └─ 自动切换bge-m3-medical主方案
      ├─ 纯文本检索模式
      │  ├─ 混合检索召回率目标调整：≥90% → ≥85%
      │  └─ 多模态检索I2T@10指标取消
      └─ 或：bge-m3-medical + 超声领域LoRA适配层
         ├─ 保留纯文本检索能力
         └─ 目标：端到端诊断准确率差距≤5%
```

### 四、GPU显存预算管理强化（高风险问题4）

#### 4.1 问题分析
compact模式下RTX 3060 12GB显存预算紧张，显存碎片化可能导致OOM。

#### 4.2 优化方案
**强化Gate 0A验证要求**，确保显存管理策略可行：

| 验证项 | 强制要求 | 不通过处理 |
|---|---|---|
| 各模型实际显存占用 | 实测各模型稳态显存占用 | 调整模型配置或升级硬件 |
| TensorRT Engine加载峰值 | 串行加载，峰值<12GB | 优化加载策略或减少模型 |
| 多器官切换显存峰值 | 切换峰值<12GB | 优化切换策略或限制并发 |
| 显存碎片化率 | 碎片化率<40% | 定期热重载或优化显存管理 |

**显存管理策略**：
1. **串行加载策略**：系统启动时按Ultrasound-CLIP → Cross-Encoder → bge-m3-medical顺序依次加载TensorRT Engine，每个Engine加载完成后确认显存回收再加载下一个
2. **器官切换策略**：多器官串行切换时，严格按卸载→确认回收→加载→预热顺序执行，Gate 0A验证切换峰值
3. **碎片化监控**：显存碎片化率>30%触发Warning告警，>40%触发模型热重载
4. **热重载策略**：仅在无活跃检查会话时立即执行；有活跃会话时延迟至会话结束后执行，最长延迟10分钟

#### 4.3 compact模式显存预算明细（llama.cpp默认）

| 组件 | 预估显存占用 | 实测要求 |
|---|---|---|
| llama.cpp GGUF Q4_K_M（7B模型权重） | ~3GB | Gate 0A实测 |
| Ultrasound-CLIP TensorRT Engine | 200-500MB | Gate 0A实测 |
| Cross-Encoder TensorRT Engine | 100-300MB | Gate 0A实测 |
| bge-m3-medical | 200-400MB | Gate 0A实测 |
| **合计（GPU）** | **~3.5-4.2GB** | **Gate 0A实测验证** |
| **剩余显存** | **~7.8-8.5GB** | **供KV Cache按需分配** |

### 五、SafetyGateway独立进程价值明确（中风险问题5）

#### 5.1 问题分析

### 十一、知识库版本管理简化（中风险问题11）

#### 11.1 问题分析

**简化为2层决策机制**，消除复杂性：

| 优先级 | 机制 | 触发条件 | 处理动作 |
|---|---|---|---|
| 1（最高） | safety_critical即时失效 | 知识更新标记`safety_critical=true` | 立即终止所有活跃会话，已完成结论保留并标记"基于旧版KB，建议复审" |

2. **会话KB版本锁定检查**：若当前会话启用版本锁定，直接返回锁定版本缓存
3. **stale标记检查**：若缓存条目被标记为stale且2分钟容忍窗口已过，拒绝返回
4. **TTL过期检查**：若缓存条目TTL已过期，拒绝返回

**SQLite写入性能风险缓解**：
1. SQLite配置WAL模式 + `synchronous=NORMAL`
2. 关键操作日志先写入内存环形缓冲区（容量1000条），异步刷盘至SQLite（刷盘间隔1s）
3. WAL文件大小监控：超过10MB触发手动checkpoint，超过50MB触发Warning告警
4. 独立审计服务启动时从主链恢复最近1小时的关键操作日志

#### 16.3 实施要求
- **资源开销验证**：Gate 0A验证四层校验总资源开销<50MB内存+<100MB/日存储
- **SQLite审计文件存储位置**：compact模式下SQLite审计文件应放置在独立磁盘分区或独立SSD分区，避免与PostgreSQL WAL产生I/O竞争

### 双引擎架构定位修订：双引擎 = 部署档位等价性验证（T0b/T2 实测结论）

#### 修订背景

原架构将 llama.cpp 与 vLLM 双推理引擎描述为"热备/冗余"关系。2026-09-29/30
三轮真机评测（780 例 × 3 轮一致性 + T2 端到端）给出了需要修订定位的实证：

1. **基座规模无净收益**（780 例 A3 轮）：1.5B→7B 一致率持平
   （80.38% vs 80.51%），剩余 ~19.6% 分歧来自边界模糊用例的设计内行为，
   而非引擎差异或模型能力。
2. **格式统一贡献全部主要收益**（A2 轮 23.33%→80.51%，+57pt）：
   结构化输出指令 + 统一 chat 端点 + 相同解码参数，才是可复制的达标路径。
3. **管线吞吐与响应契约缺口**（T2c，51 例）：端到端单例 26s（门控 P99<5s
   不可达），且 completed 响应不含结论文本——双引擎的"等价性"在
   用户可感知层面目前不成立。

#### 修订内容

| 项 | 原口径 | 修订后口径 |
|---|---|---|
| 双引擎关系 | 热备/冗余切换 | **compact（llama.cpp）/ full（vLLM）部署档位等价性验证**：两档位须通过同套门控，而非互为备份 |
| 一致性门控 | 全体 780 例 ≥95% | **分层口径**（管理决策项，待项目组确认）：常规+高风险用例与边界模糊用例分开统计；verification_config 的 semantic_grading_consistency_rate 等替代指标作为边界口径 |
| 达标主路径 | 换更大基座 | **约束解码**（vLLM guided decoding/xgrammar、llama.cpp GBNF）固化 A2 经验为 schema 级约束 + 统一解码参数 |
| 前置缺口 | 未识别 | 响应契约须先装载结论文本（patient_explanation 等，T2c 实测全 null）；管线 P99 性能专项 |
