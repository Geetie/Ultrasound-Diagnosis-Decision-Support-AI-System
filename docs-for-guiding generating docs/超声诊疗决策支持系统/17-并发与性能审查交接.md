## 2. 系统并发拓扑（审查前必须理解）

```
客户端（浏览器/edge 设备）
   │ HTTP + WebSocket
   ▼
18000 主服务（FastAPI/uvicorn）           9001 安全网关 SG（独立 uvicorn 进程）
   ├─ 诊断主链路                              ├─ 同意状态直查 PG
   │  diagnosis_pipeline（编排）               ├─ 禁忌规则/阈值校验
   │  ├─ RAG 检索（bge-m3 嵌入 → PG/Qdrant）   └─ 输出过滤（FORBIDDEN_GRADING_TERMS）
   │  ├─ 多器官编排 multi_organ_orchestrator
   │  ├─ 专科智能体（knowledge agent 双层缓存）
   │  └─ 融合层 fusion（consistency / conflict / self-rag / crag）
   ├─ WS /api/v1/realtime/nav（ConnectionManager 全局连接字典 + Redis 订阅）
   ├─ 后台消费者：diagnosis_worker（Streams）、consent_withdrawal_consumer
   ├─ 周期任务：alert_escalation、audit_service 周期校验、cache monitor、decay
   └─ 写库 → PG(15432) + Redis(16379)
                     │
                     ▼ 下游推理
        8002 主生成 vLLM ｜ 8003 嵌入 + T2a/T2b ｜ 8006 判官 vLLM
```

**要点**：单进程内既有 WS 长连接、Streams 消费者、周期任务，又有同步的 DB/Redis/文件 IO——异步阻塞是本审查的头号风险面。

## 3. 六项审查清单（每项都要给"文件:行 + 是否成立 + 证据"）

### 3.1 阻塞调用进事件循环（最高危）
在 `async def` 内出现同步阻塞动作，单人可用、十人并发即全卡。
- `time.sleep` / `requests.*` / `subprocess.run` / 同步 open-read / `torch.load`+同步推理
- 同步 DB 驱动（psycopg2/pymysql）、同步 Redis 客户端
- 大文件读写（KB 构建、冷归档、审计链全量扫描）
- CPU 密集计算（difflib、大 JSON 解析、大 base64）未进线程池

### 3.2 并发无上限（过载即雪崩）
- `asyncio.gather(...)` 无 `Semaphore`
- 无限并发 HTTP 客户端调用（httpx.AsyncClient 连接池默认限制？）
- `asyncio.Queue()` 无 `maxsize`、批量 insert 无分批
- 请求入口无并发闸门（FastAPI 依赖里限流？）

### 3.3 共享可变状态竞争
- 模块级 dict/set/list 被多请求并发读写（WS 连接表、registry、单例 cache）
- **进程内缓存与多 worker 的一致性**：`app/agents/knowledge.py` 的 L1（进程内 LRU+TTL）/L2（Redis）双层缓存，在 uvicorn 多 worker 下各自一份
- `app/services/diagnosis_pipeline.py` 的模块级脱敏缓存 `_desens_l1_cache/_desens_l2_cache/_desens_l3_done`——**无界增长 = 内存泄漏**
- `app/observability/` 指标收集器在多线程下的累加

### 3.4 任务泄漏与生命周期
- `asyncio.create_task` 无引用保存、无 done callback、异常被吞
- 轮询循环（`while True` + sleep）退出条件是否可靠
- 线程池/连接池在 shutdown 时关闭（lifespan 已接哪些？）
- 已知：`app/services/diagnosis_worker.py` 的 fire-and-forget 与 DLQ 只写不读

### 3.5 重复计算与 N+1
- 循环内 `await`（逐条 DB/Redis/LLM 调用）——主链路最贵
- 同一请求内重复检索/重复 embedding/重复脱敏
- `@lru_cache` 缺失导致的重复解析（prompt 渲染、KB 元数据加载）

### 3.6 资源上限
- PG/Redis 连接池 size/max_overflow、HTTP 客户端超时与连接回收
- 文件句柄、临时文件、并发下载
- vLLM 并发上限与排队策略（超时预算 `pipeline_sg_budget_s` 等）

## 4. 已知嫌疑点（我们此前注意到，优先核实）

| 嫌疑 | 位置 | 备注 |
|---|---|---|
| DLQ 只写不读 | `app/services/diagnosis_worker.py` | 死信无出口 |
| WS 连接表锁粒度 | `app/api/websocket/nav.py` ConnectionManager | 全局字典的锁是每操作还是批量 |
| Redis 后端令牌单例 | `app/security/refresh_token.py` RedisRefreshTokenStore | pipeline 事务一致性、家族撤销竞态 |
| 进程内缓存多 worker 不一致 | `app/agents/knowledge.py` L1/L2 | 与"击穿锁"（key_lock）在多 worker 下失效 |
| 模块级无界缓存 | `diagnosis_pipeline._desens_*` | 审查内存增长 |
| 消费者异常处理 | `consent_withdrawal_consumer`、`diagnosis_worker` | 异常是否导致消费循环静默退出 |
| 周期任务停机 | `alert_escalation` / `audit_service` | lifespan 已接线，确认 stop 路径与重入 |
