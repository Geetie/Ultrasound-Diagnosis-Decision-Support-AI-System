### 2.5 多器官联合诊断（`services/multi_organ_orchestrator.py`）

- 编码：会话 `target_organs` + `organ_statuses`；**每器官独立 `request_id`**；
- 顺序：`ORGAN_ORDER=(THYROID, LIVER, CARDIAC)` **串行执行**（`:51,211-250`）；
- 失败隔离：单器官超时只标记该器官（`:298-308`）；全局预算耗尽标 `skipped`（`:213-223`）；
- 汇总 `_aggregate_session_status`（`:438-458`）→ completed / needs_review / partial / failed；进度经 WS `organ_switching` 推送（`:490-513`）。

### 2.6 MonitorAgent 与 CUSUM 的关系（**不要混淆**）

- `MonitorAgent`（`agents/monitor.py`）：**单次诊断的内存滑动窗口**规则——低置信度 <0.3（`:226`）、时延 >5000ms（`:237`）、同器官连续 10 次失败（`:202-217`）；
- CUSUM（`observability/cusum/monitor.py:39`）与 `AISafetyCircuitBreaker`：**统计漂移与熔断**，经 `HallucinationCUSUMBridge`（`cusum/bridge.py:12`）桥接幻觉检测；
- **两者相互独立**：MonitorAgent **不喂** CUSUM。

## 3. 融合层

### 3.1 组件与三层校验

`conflict.py`（冲突检测 4 类）、`consistency.py`（一致性）、`self_rag.py`（LLM 自评）、`crag.py`（补充检索）、
`layered_validator.py`（编排）、`service.py`（`FusionEngineImpl`）、`desensitization.py`（纵深脱敏）。

`LayeredValidator.validate`（`layered_validator.py:77-166`）顺序：
**Layer1 冲突**（`:89-111`，有冲突置 `needs_review=True` 但**不中断**）
→ **Layer2 一致性**（`:113-137`，CRITICAL 置 `review_reason="consistency_failed"`）
→ **Layer3 Self-RAG**（`:139-163`，仅 `use_self_rag` 时）。

### 3.2 `FusionEngineImpl.fuse` 步骤（`service.py:102-221`）

1. 空输入 → 占位结果（`needs_review=True`，reason `no_specialist_responded`）；
2. `LayeredValidator.validate`；
3. 选 `final_response` = 最高 confidence（并列取第一个，`:245-260`）；
4. **CRAG 触发条件**（`:156-162`）：`use_crag and self_rag_passed is False and crag_handler and rag_service and not crag_triggered`；
   恢复成功 → 替换响应并**清掉 `self_rag_failed`**（`:171-180`），失败/异常 → 保留 `needs_review`（`:181-194`）；
5. 合并 specialist 的 `needs_review` → `specialist_flagged`（`:196-205`）。

### 3.3 `review_reason` 全量取值来源

| 取值 | 设置处 |
|---|---|
| `conflict_detected` | `layered_validator.py:105` |
| `consistency_failed` | `layered_validator.py:133` |
| `self_rag_failed` | `layered_validator.py:151` |
| `no_specialist_responded` | `fusion/service.py:125` |
| `specialist_flagged` | `fusion/service.py:205` |
| `validation_failed: <Type>` | `fusion/service.py:145` |
| `fusion_layer_failed` | `diagnosis_pipeline.py:615` |
| `safety_gateway_unavailable` | `diagnosis_pipeline.py:504` |
| `consent_withdrawn` | `diagnosis_pipeline.py:471` |

⚠️ 允许集声明于 `fusion/protocols.py:240-251`，其中 `all_specialists_unavailable`、`below_confidence_threshold`
**无写入方（孤儿取值）**。

### 3.4 一致性检查的实现方式（**不是 LLM**）

`consistency.py` 用**规则 + RAG 检索**：既往对比用置信度差（0.3/0.5）与分级码差（1/2）阈值（`:64-71`）；
指南对比经 RAG 检索 top_k=3 做关键字级比对（`:74`）；跨器官用 UDT 层级匹配 + 7 条规则（`:90-161`），
触发跨器官规则须达 `min(器官阈值+0.10, 0.95)`（`:79`）。

### 5.3 安全网关为何独立进程 / 为何强制单 worker

- **独立进程**：作为 api 之外的第 3 层防线，api 经 HTTP 调用（`services/safety_gateway_client.py:141-151`）；
- **强制单 worker**：启动时检测 `UVICORN_WORKERS`/`WEB_CONCURRENCY` ≠1 即 raise，并用 `psutil` 复核实际子进程数（`safety_gateway/main.py:142-150,194-212`）；
- ⚠️ **代码注释只写"not designed for multi-worker deployment"，未记录具体架构理由**——文档不编造。
  实际后果：**SG 是单点，无法水平扩容**（HA 受限）。

## 6. 横切机制

### 6.1 失败安全策略（两类并存，必须区分）

**Fail-closed**（拒绝服务而非给错误结论）：SG 不可达 → 返回 E4005 拒诊；同意撤回/未签 → 强阻断；SG 内存或 P99 超限 → 拒请求。

**Fail-open**（不阻塞主流程，仅记录/降级）：灰度路由异常仍放行（`diagnosis_pipeline.py:121`）；路由判定异常返回 None 不阻断（`:96-109`）；
观测与埋点全程吞异常；融合层异常 → `needs_review` 而非抛错（`fusion/service.py:22-29`）。

### 6.2 降级矩阵

| 依赖不可用 | 降级行为 | 位置 |
|---|---|---|
| Qdrant → pgvector | 健康检查失败自动切（延迟 3–5×） | `embedding/index_factory.py:88-156` |
| SG → 熔断 | 连续失败 ≥ 阈值 fast-fail 跳发 | `safety_gateway_client.py:119-120,196-202` |
| Redis → 内存队列 | worker 降级 `asyncio.Queue`（仅单实例） | `diagnosis_worker.py:48-53` |
| Redis → 缓存 miss | 视为 L1 miss，走 L2 / 真实检索 | `agents/knowledge.py:34-35` |
| inference 缺失 | specialist 用占位智能体 | `specialist/factory.py:161-174` |
| RAG 缺失 | `knowledge_agent` 抛 `RuntimeError`，CRAG 跳过 | `main.py:309-319,426-435` |
| 边缘引擎缺失 | `NullNavBackend` 空标注 | `edge/nav_backend.py:369-385` |
| PG 不可用 | 器官阈值降级为硬编码 | `specialist/factory.py:109-119` |

### 6.3 版本兼容

唯一取源 `config/validator.py:check_version_compatibility`（`:167-177`），启动期 `validate_version_compatibility`（`:140-162`）
被 `validate_config`（`:135`）调用、`main.py:42` raise；结果接口写真实值（`api/v1/diagnosis.py:581`，此前硬编码 `"compatible"`，见 `validator.py:171-175` 注释）。
兼容矩阵在 `knowledge/version.py:134-164`（model v1↔kb v1/v2；model v2↔kb v2）。**升级顺序：KB 先于模型**（`validator.py:160-162`）。
