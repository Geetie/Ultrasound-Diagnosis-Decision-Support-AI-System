**失败模式分析**（报告 failure_analysis，587 例分级失败）：

3. **61 例分级提取失败**：正则 `TI-RADS/LI-RADS/LVEF` 覆盖不了引擎的自由表述

   约束输出格式（如强制 JSON 字段）。

**过程中拔出三颗"实现了但从未接线/从未跑通"的钉子**：
1. `knowledge_chunks.embedding` ORM 硬编码 `Vector(768)`（Ultrasound-CLIP 时代），

   `"meta"` 当键——`set_` 字符串键是**数据库列名**（物理列 `metadata`）→ 首次建库
   即 `column "meta" does not exist`（该路径此前从未真机跑通）。已修复并抽
   `build_upsert_statement()` 加编译级回归守卫（`test_hybrid_indexer_upsert.py`）；
3. **接线缺口**：`init_knowledge_base.py` 只写 `knowledge_chunks`，而生产检索器

### A.6 T1c：第一轮检索调优 + faithfulness 生成评测基线（2026-09-29）

**T2c 结果与根因（第一轮全量 51 例：completed=6，44 例超时，wall=118 分钟）**：
超时不是"单例慢"而是**四颗叠加的钉子**（逐一定位，全部修复）：

1. **DB 会话跨整条管线**（致命）：`diagnosis_pipeline.py` 的
   `async with AsyncSessionLocal()` 包住 dispatcher/fusion 的分钟级 LLM
   调用——事务空闲连接被 `idle_in_transaction_session_timeout` 掐断，
   结果写库抛 `underlying connection is closed` → 请求永远 processing
   → 轮询 404 → 评测超时。`pool_pre_ping` 只在借出时检测，救不了事务
   中途断连。修复：session 只包读段（request/患者ID/路由判定），LLM 段
   无 DB 上下文，写库走独立短会话。
2. **fusion 层串行 LLM 链**：Layer 2（一致性校验）与 Layer 3（Self-RAG）
   串行 await，二者输入相同输出独立 → `asyncio.gather` 并行（170 既有
   单测全绿，语义不变）。
3. **llama.cpp `--cache-reuse 256` × `--parallel 4` 分片 KV 死锁**：
   prefix caching 实验（TTFT 28s→5.9s 串行 4.8x）在并发多 slot 下
   （kv_unified=false）引发请求排队风暴——单请求生成 40s+、90s 引擎
   超时×2 重试=181s。回滚该参数；prefix caching 正确姿势是 vLLM
   （原生 continuous batching + prefix caching，见 15 号性能专项）。
4. **评测轮询路由口径**：真实路由是 `/diagnosis/result/{request_id}`
   （排查中 probe 曾用错 `/requests/`，评测脚本本身正确）。

**修复后端到端实测**：单例 **10 秒 completed**（此前 >120s 挂死）；
fusion 层并行化 + DB 会话治理使管线在真实 KB 检索注入（prompt ~6k
tokens）下稳定出终态。completed 响应含 routing/rollout/脱敏全字段。

**T2c 评测结论（口径注记）**：support=0 的直接原因是响应结论文本字段

真实 caption 输入下的 completed 率与时延（修复前 12% → 修复后见
`t2c_e2e_report_after_perf.json`）。


**修复后复测（同口径 9 例，`t2c_e2e_report_after_perf.json`）**：
- **单例端到端 10 秒 completed**（修复前单例 >120s 挂死）——DB 会话
  治理 + fusion 并行化 + cache-reuse 回滚的组合效果，管线可用性从
  "评测不可用"恢复到健康。
- **并发 6 时 avg_proc=124s、completed=1/9**——并发排队退化：llama.cpp

  吞吐 ~10x）是 P1 首项，非可选项。
- 结论口径：管线**正确性**修复完成（终态必达、结果必落库）；管线
  **容量**问题移交性能专项（15 号 §5 措施 #2），T2c 的 faithfulness
  结论维持以 T1c QA 集 136 例为准（56.3%）。

### A.22.1 并发审查第二批：登录限流双维度 + 报告链路限流 + DLQ 出口（同日续做）

**背景**：A.22 首批只修"零语义风险"项，把 8 项残留按"能不能靠代码解决"分诊。本批把其中
**5 项直接修掉**，并**订正 1 项我自己写错的发现**。

**① P1-12 登录限流双维度（真机实测问题）**

原实现：限流桶键 `f"{client_ip}:{user_id}:{path}"`，而登录请求无 token → `user_id` 落回
client_ip → **同一医院出口 NAT 下的所有医生共享一个 5/min 桶**。真机压测准备 10 个账号时
被逼退避重试，第 6 个账号起 429；交接班/查房后集中登录必然复现。

现为两个正交桶（**缺一道就是安全降级**）：
- **IP 桶 30/min**（中间件自动）：挡单主机洪水；
- **用户名桶 5/min**（`enforce_login_rate_limit`，在两个登录端点内、`authenticate_user`
  **之前**调用）：挡针对单个账号的撞库/暴破——攻击者换 IP 也一样被挡。用户名只以
  `sha256[:16]` 参与桶键，不落库、不进日志，也**不引入 X-Forwarded-For 信任边界**。
  放在 bcrypt 之前是刻意的：否则每次暴力尝试都要白付 200~400ms CPU（P0-1 的 offload
  让它不再卡事件循环，但 CPU 还是要付）。
安全侧断言同步更新（`TestP1_5_AuthRateLimiting` 4 例，钉住"两道防线都在"）。

**② P2-1 报告链路限流 + 一个隐性缺陷**

`/api/v1/report`（草稿）、`/report/{id}/sign`（HSM 签名）、`/report/{id}/push`（PACS 推送）
原先完全无限流。修的过程中发现**更根本的问题**：限流中间件只做**字面量**路径匹配，而它拿到
的是**已展开的真实路径**——所以带路径参数的端点即使写进 `RATE_LIMITS` 也只是死条目。
新增 `resolve_rate_limit_config()`：精确 → fnmatch 通配（`*`）→ 最具体优先（`/` 段数多者胜）。

**③ P2-2 全局并发闸门（默认不启用）**

#### A.26.2 真机验证跨进程互斥（真实 Redis，非 Fake）

单测 `test_refresh_token_rotate_cross_process.py` 用 `FakeAsyncRedis`（单进程字典），
能证明"代码会去抢锁"，**证明不了真实 Redis 的 `SET NX EX` 在两个 OS 进程间是原子的**——
而这正是该修复的全部意义（受害者是多 worker 进程，单进程内复现不了）。故补真机探针
（6 个 spawn 子进程，各自独立连接与单例，`multiprocessing.Barrier` 同步起跑）：

```
[probe] redis 目标核对：redis://***@127.0.0.1:16379/0
[probe] elapsed=0.39s ok=1 err=5 uniq_ok=1
[probe] err-sample: ValueError: Refresh token has already been used, family WZz8B7... revoked
[probe] replay old token -> rejected:RuntimeError
[probe] PASS
```

**结论：6 进程并发下恰好 1 个成功，旧 token 重放被拒，互斥在真实 Redis 上成立。**

探针本身踩了三个坑（都是"判据写错导致假失败"，值得记）：
1. 未加载 `~/uai/.env` → 连到 **`localhost:6379`（别人的 Redis）** 报 `Error 111`。
   铁律 #3 的现实版：脚本必须显式加载环境文件，否则会静默连错实例。
2. 判据用 `verify_refresh_token(...) is None` → **报假 FAIL**。该方法是**查存在性**而非
   查可用性，rotate 后 token_data 仍在库里。准确判据是"旧 token 二次 rotate 必须抛错"。
3. `create_refresh_token` 是 **async** 且签名含必填 `user_info`，返回 `str` 而非 dict。

#### A.26.3 新发现缺陷（已登记 feature_list: refresh-token-grace-period）

真机同时实测到失败原因为 `family XXX revoked` —— 任何 reuse 都**撤销整个会话族**。
查证这是 `revoking_entire_family` 的**设计意图**（OAuth2 Security BCP 的标准取舍，
防窃取宁可误伤），**不是 bug**；但它有一个真实可用性代价：

> 医生在同一账号开多个标签页、或双击刷新等**合法并发**，会被判为 token 窃取，
> 全设备被踢下线。

正确解法是加**旋转宽限期**（旧 token 在短窗口内可再换一次、返回同一个新 token），
**不可**放松 reuse 检测（那等于把 7 天令牌变成无限续期）。需产品决策宽限期时长。
已登记为 `planned`，并写进 18 号手册限制 ⑦ 与钉子 7。
