**失败模式分析**（报告 failure_analysis，587 例分级失败）：

3. **61 例分级提取失败**：正则 `TI-RADS/LI-RADS/LVEF` 覆盖不了引擎的自由表述

   约束输出格式（如强制 JSON 字段）。

**过程中拔出三颗"实现了但从未接线/从未跑通"的钉子**：
1. `knowledge_chunks.embedding` ORM 硬编码 `Vector(768)`（Ultrasound-CLIP 时代），

   `"meta"` 当键——`set_` 字符串键是**数据库列名**（物理列 `metadata`）→ 首次建库
   即 `column "meta" does not exist`（该路径此前从未真机跑通）。已修复并抽
   `build_upsert_statement()` 加编译级回归守卫（`test_hybrid_indexer_upsert.py`）；
3. **接线缺口**：`init_knowledge_base.py` 只写 `knowledge_chunks`，而生产检索器

### A.6 T1c：第一轮检索调优 + faithfulness 生成评测基线（2026-09-29）

**T2c 结果与根因（第一轮全量 51 例：completed=6，44 例超时，wall=118 分钟）**：
超时不是"单例慢"而是**四颗叠加的钉子**（逐一定位，全部修复）：

1. **DB 会话跨整条管线**（致命）：`diagnosis_pipeline.py` 的
   `async with AsyncSessionLocal()` 包住 dispatcher/fusion 的分钟级 LLM
   调用——事务空闲连接被 `idle_in_transaction_session_timeout` 掐断，
   结果写库抛 `underlying connection is closed` → 请求永远 processing
   → 轮询 404 → 评测超时。`pool_pre_ping` 只在借出时检测，救不了事务
   中途断连。修复：session 只包读段（request/患者ID/路由判定），LLM 段
   无 DB 上下文，写库走独立短会话。
2. **fusion 层串行 LLM 链**：Layer 2（一致性校验）与 Layer 3（Self-RAG）
   串行 await，二者输入相同输出独立 → `asyncio.gather` 并行（170 既有
   单测全绿，语义不变）。
3. **llama.cpp `--cache-reuse 256` × `--parallel 4` 分片 KV 死锁**：
   prefix caching 实验（TTFT 28s→5.9s 串行 4.8x）在并发多 slot 下
   （kv_unified=false）引发请求排队风暴——单请求生成 40s+、90s 引擎
   超时×2 重试=181s。回滚该参数；prefix caching 正确姿势是 vLLM
   （原生 continuous batching + prefix caching，见 15 号性能专项）。
4. **评测轮询路由口径**：真实路由是 `/diagnosis/result/{request_id}`
   （排查中 probe 曾用错 `/requests/`，评测脚本本身正确）。

**修复后端到端实测**：单例 **10 秒 completed**（此前 >120s 挂死）；
fusion 层并行化 + DB 会话治理使管线在真实 KB 检索注入（prompt ~6k
tokens）下稳定出终态。completed 响应含 routing/rollout/脱敏全字段。

**T2c 评测结论（口径注记）**：support=0 的直接原因是响应结论文本字段

真实 caption 输入下的 completed 率与时延（修复前 12% → 修复后见
`t2c_e2e_report_after_perf.json`）。


**修复后复测（同口径 9 例，`t2c_e2e_report_after_perf.json`）**：
- **单例端到端 10 秒 completed**（修复前单例 >120s 挂死）——DB 会话
  治理 + fusion 并行化 + cache-reuse 回滚的组合效果，管线可用性从
  "评测不可用"恢复到健康。
- **并发 6 时 avg_proc=124s、completed=1/9**——并发排队退化：llama.cpp

  吞吐 ~10x）是 P1 首项，非可选项。
- 结论口径：管线**正确性**修复完成（终态必达、结果必落库）；管线
  **容量**问题移交性能专项（15 号 §5 措施 #2），T2c 的 faithfulness
  结论维持以 T1c QA 集 136 例为准（56.3%）。
