## 2. 需修正（原表述或定性有误）

### M-01 报告签发「补一次 `review_l3` 校验」的可行性要提高，但**后端当前完全不强制权限位**

- 事实：`RoleChecker` 机制**已存在且已在 5 个端点组使用**——`alert_admin.py:11`、`auth.py:277,319`、`consent.py:30,59`、`device.py:30`、`security.py:10,11`。缺口**恰好只在业务主链**。
  → 表述应由「架构缺口」改为：**角色校验能力齐备、已用于管理与同意面，主链是唯一漏点**。§7-C1/C2「一个校验点 + 一个条件渲染」的判断成立，且成本比原估更低（仓内已有范式可抄）。
- **但**：`check_permission()`（`auth.py:155-163`）**除被 `app/api/v1/auth.py:18` import 外无任何调用点** → `PERMISSIONS` 粒度**从未被强制执行**。
  → 因此「前端按服务端返回的权限位条件渲染」在**前端可行**（`auth.py:306-312` 确有 `GET /auth/permissions`），但**后端不构成第二道防线**。设计文档必须写明：**这是提示性渲染，不是强制**。

### M-02 复核原因：声明集确实是 7 个，但**实际写入的字符串超过 12 个**

- `_ALLOWED_REVIEW_REASONS`（`fusion/protocols.py:242-253`）= `conflict_detected` / `consistency_failed` / `self_rag_failed` / `no_specialist_responded` / `all_specialists_unavailable` / `below_confidence_threshold` / `specialist_flagged` → **恰好 7 个，「7 种枚举」的原表述正确**。
- **修正点**：管线另写入未在集合内的自由字符串——`dispatcher_failed`（`diagnosis_pipeline.py:11`）、`consent_withdrawn`（`:16`）、`safety_gateway_unavailable`（`:390`）、`fusion_layer_failed`（`:497`）、`validation_failed: <ExcName>`（`fusion/service.py:149`）；且该 validator **故意不抛错**（`protocols.py:234-238`），允许任意扩展。
  → 设计的「原因人话化」**必须带兜底分支**（未知取值 → 统一中性文案），否则新增取值会直接露成英文下划线串给医生。

### M-03 `OrganStatus` 是 **6 值**，不是 4 值

- `schemas.py:18-24`：`pending` / `in_progress` / `completed` / `failed` / `skipped` / `needs_review`；`SessionStatus`（`:8-15`）另有 7 值。
  → v3 §2.5 的「4 状态」是子集。部位指示条要么做全 6 态映射，要么明确**归并规则**（如 `failed`+`skipped` → 「未完成」），不能默默丢掉。

### M-04 「多部位」上限是 **3**，且 `image_ids` 为必填

- `DiagnosisRequest`（`schemas.py:118-128`）：`image_ids: List[str]`（**必填**）、`target_organ: Organ`（**必填枚举**，`schemas.py:53-56` 仅 `thyroid` / `liver` / `cardiac`）、`idempotency_key` 可选。
  → 「部位自动补全」只能在 3 个枚举内扩展；§2.6「多部位」实为**最多 3 个**。且判读请求**必须带 image_ids**，空数组也能发（`ExaminationPage.tsx:51` 就是 `imageId ? [imageId] : []`）——**这会产出无影像锚点的判读**，与「冻结帧 = 审计锚点最清晰」的设计前提相悖。

### M-05 主题/导航的实际基数比原估更差

- 真实侧边栏 **8 项**（`components/layout/Sidebar.tsx`）：检查主界面 / 诊断结果 / 知情同意 / 反馈提交 / 新建会话 / 质控报告 / 知识库管理 / 设置。
  → 原表述「v1 是 5 项导航」不准，**实际 8 项**；且**质控报告与知识库管理已经躺在医生侧边栏里**（并非「按角色出现」）。v3「导航收敛为 2 项」实际要砍掉 6 项，其中 `/diagnosis` 需明确去留（见 N-02）。
- 视觉：侧边栏品牌字用 **Orbitron + `#00d4ff` 青色发光**（`Sidebar.tsx`），属典型「AI 霓虹紫蓝」套路，**与 §4.1 的 ISO 标准色体系直接冲突**——这是新增的、可验证的视觉问题。

## 3. 被推翻的判断

### ✗ X-01 「前端 `diagnosisService` 属静默失真」——定性过重，不成立

- 事实：`diagnosisService.ts:26-35` 定义 `DiagnosisStageEvent.estimated`，注释明确写「true 表示该阶段由'档位期望耗时'推算而来……**UI 必须如实标注为预计阶段，不得伪装成真实遥测**」；`resolveStage()` 恒返回 `estimated: true`（`:87`）；另单独提供 `extractStageTimings()`（`:108-123`）取后端真实值。
  → 代码**把预计与真实显式分开了**，并写下了义务。这不是静默失真。
- 正确表述：**风险点在于 UI 是否遵守 `estimated` 标志**（值得写进设计规则），而不是既有实现说谎。v3 §5.2 的**设计结论不变**（只显示已完成的真实阶段 + 当前阶段名），但**依据要改写**。

### ✗ X-02 「后端六阶段埋点已可支撑真实阶段展示」——不成立

- 事实：前端 `TIMING_KEY_MAP`（`diagnosisService.ts:102-106`）只有 3 项，且**键名对不上**：
  - `['retrieval', 'dispatch']` → 后端实际写的是 `dispatcher.invoke_ms` → **恒取不到**
  - `['fusion', 'fusion.fuse_ms']` ✓
  - `['safety', 'sg.check_output_ms']` ✓
  - `reasoning` 阶段**没有映射**；`db_read_ms` / `db_write_ms` **无人读取**
  → 6 个阶段里**只有 2 个阶段 + 总耗时**能真正取到。**「真实阶段展示」目前不可用**，必须先修映射。
- 设计影响：§5.2 的「真实阶段展示」需**重新界定为**——后端 6 个埋点中有 3 个（fusion / safety / total）可立即使用；`dispatcher.invoke_ms` 与 `db_*` 需补映射或明确不展示。**这是可验证、可选型、且成本极低的一项**。

## 4. 新增发现（原设计完全未纳入）

### N-01 ★ 结果接口把大量不确定性字段**硬编码**——设计的可视化前提被抽空

`diagnosis.py:489-514` 构造 `DiagnosisResult` 时，以下字段是**写死的常量**，与管线真实结果无关：

| 字段 | 硬编码值 | 设计中原定用途 |
|---|---|---|
| `consistency_flag` | `CONSISTENT` | §3.2 一致性校验 |
| `fusion_status` | `NORMAL` | §3.2 融合层状态 |
| `quality_control.self_rag_passed` | `False` | §3.2 Self-RAG |
| `quality_control.consistency_check_passed` | `True` | §3.2 一致性 |
| `ai_diagnosis_failed` | `False` | 降级提示 |
| `hallucination_severity` | **`None`** | §3.1 严重幻觉 → 强制勾选核验 |

- 更关键：**融合层的复核信号不达前端**。管线把 `needs_review` / `review_reason` 写进 `findings`（`diagnosis_pipeline.py:401-409, 424`），而 `GET /diagnosis/result` **不读**它们——`review_reason` 仅在安全网关失败时取 `sg_result.message`（`diagnosis.py:439-447`），否则为 `None`。
- 连带**状态不自洽**：管线在 `fusion_result.needs_review=True` 时把 `status` 置为 `"needs_review"`（`:401-406`），该 status 原样透传；但 `requires_manual_review` **只看安全网关**（`diagnosis.py:438-447`）→ 出现 **`status == "needs_review"` 而 `requires_manual_review == False`** 的组合。
- 设计影响（最重要）：§3.1 把「冲突 / 一致性 / Self-RAG / 幻觉严重度」列为**现有可支撑的一级/二级产物**，前提**不成立**。必须二选一：
  1. **列入后端改造清单**（把 `findings` 里的融合信号映射到响应字段）——推荐，因为数据已在库里；
  2. 或从设计清单降级为「设计前瞻」，不得标注为现有数据可支撑。

### N-02 结果页其实已经建得相当完整——v3 与之存在功能重叠

`DiagnosisPage.tsx` 具备：`LoadingPhase = idle / requesting / polling / completed / timeout / error`（**错误态与超时态已存在**）、`useProgressiveDiagnosis`（结论先落地、警示/质控/证据链分块补齐）、`reviewAcknowledged`（**「已人工核验」勾选已实现**）、`HallucinationWarning` / `QualityControlBadge` / `EvidenceTrace` / `ProgressiveBlock` 组件齐备。
- → 由于 N-01，`HallucinationWarning` 与 `QualityControlBadge` 目前拿到的是常量（`None` / 硬编码）→ **组件已成，数据是假的**。
- → v3 说「结果查看与反馈合并进结论区」，但已有 `/diagnosis` 独立页。**必须裁定：改造复用，还是废弃合并**——不能两个都留（单一真相源）。

### N-03 「按部位去重」已有现成机制，**无需后端改动**

- 后端幂等：`diagnosis.py:99-123` + `IDEMPOTENCY_TTL_SECONDS = 600`；命中时若结果已完成则**直接回放整份结果**（`X-Idempotent-Replay: true`）。
- 前端现成函数：`utils/idGenerator.ts:10-12` `generateIdempotencyKey(organ)`，`ExaminationPage.tsx:48` 已在用。
- **但当前实现等于没有幂等**：`generateIdempotencyKey` = `idem_{organ}_{Date.now()}_{uuid12}` → **每次调用都是新键**，缓存永不命中。
- → 改为**确定性键**即可实现「同部位只保留一份」：`idem_{sessionId}_{organ}_{floor(ts/60s)}`。语义上返回**首次结果**而非重算，与 v3「静默替换为最新一次」略有差异——**若要"最新"需改用覆盖式键（不含时间桶）并由前端自行丢弃旧结果**。
- 另有第二层可用的去重钩子：`check_rate_limit(..., dedup_key=f"{request.session_id}")`（`diagnosis.py:94`），`rate_limit.py:173-189 / 260-289` 实现了**同键在桶周期内只放行一次**。→ 会话级抑制已有基础设施。

### N-04 结果缓存的写入序列化不一致（后端缺陷，影响「错误态」设计）

- 同一个 Redis 键 `RedisKey.diagnosis_result(...)` 被两处写入：
  - 管线写 `str(findings)`（Python `dict` 的 repr，用单引号）——`diagnosis_pipeline.py:450-454`；
  - 接口写 `json.dumps(...)`——`diagnosis.py:521-531`。
- 读取侧 `diagnosis.py:415-420` 直接 `json.loads(raw)` 且**无 try/except**。
- → **推断**：管线写入后的 30s 窗口内被读到，`json.loads` 会抛 `JSONDecodeError` → 未处理 → 500。这会直接触发前端 `error` 态。**建议纳入后端缺陷清单**（本报告未运行代码验证，标为推断）。

### N-05 会话/器官状态已在前端存好，v3 可直接复用

`stores/sessionStore.ts` 已有 `organStatuses`、`currentOrgan`（注释：「顶栏选择器与语音指令共用同一处状态」）、`ttlRemainingMs`、`clearSession`；`hooks/useSession.ts` 已有 TTL 倒计时与 `visibilitychange` 处理。
- → v3 §2.5 部位指示条、§2.8「切患者即清屏」（`clearSession` 已存在）、§5.7 TTL 提示，**均有现成状态**，无需新建 store。
