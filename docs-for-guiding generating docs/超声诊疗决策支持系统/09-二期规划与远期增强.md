# 二期规划与远期增强

> 本文档汇集所有未纳入一期 MVP 的功能规划、技术路线和架构增强方案。一期文档中涉及二期功能时，仅用一句话概述并指向本文档。

## 1. 更多器官扩展

### 1.1 新器官智能体接入

- 二期按临床优先级逐步接入胰腺、脾脏、血管等器官专科智能体，遵循 [01-系统架构设计](01-系统架构设计.md) 2.4 节接入规范
- 各器官需积累 ≥ 100 例验证集，按上线阶梯（基础辅助 → 灰度验证 → 全量上线）逐步推进
- 新器官的高风险病种须在接入时同步审定

### 1.2 一期三器官增强

- 一期已实现的甲状腺、肝脏、心脏智能体在二期持续优化：补充更多病种级阈值、优化专科模型精度
- 跨器官关联规则随临床数据积累持续扩充

## 2. 多租户 SaaS 化部署

### 2.1 数据隔离

| 隔离维度 | 方案 |
|---|---|
| 会话隔离 | 每个会话绑定 `hospital_id`，所有数据读写增加过滤 |
| 知识库隔离 | 各医院独立知识库版本（`kb_v{major}.{minor}.{patch}~{hospital_id}`），共享基础指南。**版本解析兼容性**：多租户版本号格式 `kb_v{major}.{minor}.{patch}~{hospital_id}` 的解析须遵循统一规范——先按 `~` 分割去除 hospital_id 后缀，再按 `.` 分割，第一段去除 `kb_v` 前缀后得到 major，第二段为 minor，第三段为 patch（与 [02-核心流程与知识库](02-核心流程与知识库.md) §1.3 `parse_kb_version` 解析规范一致，使用 `~` 作为分隔符，避免 `+` 在 URL 编码中被解析为空格导致版本号解析错误）。一期 CI 静态检查规则继续适用——禁止代码中直接比较 `knowledge_base_version` 字符串，必须通过 `parse_kb_version` 函数解析
| 模型隔离 | 联邦学习场景下各医院模型参数独立 |
| 配置隔离 | 各医院独立配置，按 `hospital_id` 命名空间隔离 |
| 脱敏映射隔离 | 各医院令牌-身份映射表独立存储 |

> 一期 `HOSPITAL_ID` 固定为 `default`，不加 `hospital_id` 过滤。二期引入时需数据迁移。

**多租户数据迁移方案**：

| 步骤 | 操作 | 验证方法 |
|---|---|---|
| 1. 数据盘点 | 统计一期所有数据表记录数，识别需添加 `hospital_id` 的表（sessions、diagnoses、reports、consent_records、feedbacks；**compact Profile 审计日志已存储于 PostgreSQL `audit_logs` + `app_runtime_logs` 表，二期多租户改造时需为审计日志表增加 `hospital_id` 字段**） | 记录数与迁移前一致 |
| 2. Schema 变更 | 各表增加 `hospital_id` 列（默认值 `default`），创建 `hospital_id` 索引 | DDL 执行成功，索引创建完成 |
| 3. 数据回填 | `UPDATE` 语句将所有现有记录的 `hospital_id` 设为 `default` | 全量数据 `hospital_id` 非空 |
| 4. 查询改造 | 所有数据读写 SQL 增加 `WHERE hospital_id = ?` 过滤条件 | 回归测试通过，无跨租户数据泄露 |
| 5. 应用层改造 | 会话创建时从 JWT Token 提取 `hospital_id`，注入所有后续操作 | 多租户集成测试通过 |
| 6. 知识库拆分 | 一期共享知识库保留为基础版本，各医院差异化知识作为增量补丁（`kb_v{major}.{minor}.{patch}~{hospital_id}`） | 各医院知识库版本独立管理 |
| 7. 迁移验证 | 在预发布环境执行完整迁移演练，验证数据完整性 + 功能正确性 + 性能无退化 | 迁移演练报告归档 |

> 迁移窗口建议：在维护窗口内执行（预计 2-4 小时，取决于数据量），迁移期间系统只读。

### 2.2 多租户版本兼容性

各医院知识库版本可能不同步，兼容性判定仅基于 `{major}.{minor}.{patch}` 部分。管理页面须展示各医院版本状态与兼容性状态。

**多租户升级编排方案**：多租户 SaaS 化部署时，各医院知识库版本可能不同步，升级部署顺序约束（须先升级 KB 再升级模型，与 [02-核心流程与知识库](02-核心流程与知识库.md) §1.3 兼容性矩阵一致）在多租户场景下须按医院维度分别执行。升级编排策略如下：

| 编排策略 | 说明 |
|---|---|
| 分批升级 | 按医院分批执行 KB→模型升级，每批 1-3 家医院，避免全量升级时故障爆炸半径过大 |
| 升级窗口期 | 升级期间目标医院进入只读模式（不接受新诊断请求，已有会话继续完成），只读窗口 ≤ 30 分钟 |
| 回滚策略 | 升级失败时按医院维度回滚至上一版本组合（KB + 模型同步回滚），回滚操作须在 10 分钟内完成 |
| 版本兼容性校验 | 升级前自动校验目标版本组合的兼容性矩阵，不兼容的组合拒绝升级并提示运维 |
| 升级状态看板 | 管理页面展示各医院当前版本、升级进度、升级状态（待升级/升级中/已完成/回滚） |

## 3. 边缘端自治导航模式

当中央调度不可达时，边缘端可增强为自治导航模式，替代一期降级方案（一期中转模式下后端不可达时导航标注不可用，前端显示"导航服务不可用"；二期直推模式下后端不可达时导航标注直推前端展示，附加"未经安全校验"警告标记）。一期边缘端 TensorRT 模型仅用于图像预处理与特征提取加速，导航推理依赖后端执行；二期在边缘端部署本地轻量导航模型实现自治：

| 维度 | 远期方案 |
|---|---|
| 自治行为 | 边缘端调用本地轻量导航模型（TensorRT 预编译），执行图像识别 + 缓存知识匹配 + 最小安全校验 |
| 输出标记 | 所有自治导航结果标记 `dispatch_bypassed` |
| 安全底线 | 自治模式置信度阈值 = 器官级阈值 × `EDGE_AUTONOMY_MULTIPLIER`（初始值 1.15-1.25，与 [01-系统架构设计](01-系统架构设计.md) §3.5 跨器官关联乘数定义对齐），低于该阈值的标注不显示 |
| 最长持续时间 | 自治模式持续超过 30 分钟时，自动降级为"仅显示原始图像" |
| 安全校验 | 边缘端跳过实体校验与禁忌校验，后端恢复后对自治期间记录补做校验 |
| **本地同意状态缓存** | 边缘端启动时从 PostgreSQL 同意状态表同步当前会话的同意状态至本地缓存（TTL 与会话 TTL 一致，最大 4 小时），自治模式下查询本地缓存确认患者已签署 AI 辅助诊断知情同意。本地缓存未命中（如边缘端重启后会话信息丢失）时，自治模式拒绝输出任何 AI 标注，前端提示"无法确认患者同意状态，请转为人工操作"。后端恢复后边缘端从 PostgreSQL 重新同步同意状态。此机制确保自治模式下同意状态校验不缺失，与 [01-系统架构设计](01-系统架构设计.md) §3.4 SafetyGateway 同意状态查询策略对齐 |
| **基础脱敏规则本地副本** | 边缘端维护脱敏规则子集的本地副本（从核心组 Redis `desensitization_rules_update` channel 同步，与 [01-系统架构设计](01-系统架构设计.md) §3.3 脱敏规则同步规范对齐），覆盖结构化身份模式拦截规则（电话号码、身份证号、地址等正则匹配）。自治模式下导航标注仅含坐标+标签+置信度（不含自由文本），脱敏规则主要防御标注标签中的身份信息泄露。本地脱敏规则与 SafetyGateway 规则从同一主规则源自动生成（异构冗余体现在执行引擎而非规则定义，详见 [01-系统架构设计](01-系统架构设计.md) §3.3），规则更新通过安全关键事件 Redis Streams 传播 |

引入自治模式时，置信度阈值乘数增加"边缘端自治模式"行（`EDGE_AUTONOMY_MULTIPLIER`，初始值 1.15-1.25，与 [01-系统架构设计](01-系统架构设计.md) §3.5 定义对齐）。乘数设计理由——自治模式下后端安全校验（含 SafetyGateway）不可用，须提高阈值以补偿安全防线缺失，乘数须高于跨器官关联乘数（1.15-1.20，仅跳过逻辑校验）以反映更严重的安全防线缺失。乘数值须在 Gate 0B 临床验证中基于实际病例数据校准，详见 [00-项目总览](00-项目总览与核心指标.md) 2.5 节。

## 4. 知识查询智能体高可用

### 4.1 主备热备模式

当并发需求超过 50 时，知识查询智能体升级为主备热备：

| 维度 | 方案 |
|---|---|
| 运行模式 | 主实例处理查询，备实例热备 |
| 故障切换 | 备实例通过 Redis 租约机制自动接管（TTL 10s，每 5s 续期），切换时间 < 3s |
| 缓存一致性 | 两实例共享 Redis 查询缓存层 |

### 4.2 多读副本模式（推荐替代方案）

对于读多写少的知识查询场景，多读副本比主备热备更高效：

| 维度 | 方案 |
|---|---|
| 运行模式 | 多个实例同时服务查询请求 |
| 一致性 | 通过共享 Redis 缓存层保证 |
| 扩展性 | 按并发需求水平扩展读副本数量 |

## 5. 幻觉率二维监控矩阵

上线 6 个月后且每格子月均样本量 ≥ 30 例时，启用二维监控矩阵：

| 风险等级 \ 严重度 | 严重幻觉 | 中度幻觉 | 轻微幻觉 |
|---|---|---|---|
| 高风险病种 | ≤ 0.3% | ≤ 1% | ≤ 3% |
| 中风险病种 | ≤ 0.5% | ≤ 2% | ≤ 5% |
| 低风险病种 | ≤ 1% | ≤ 3% | ≤ 5% |

启用后，一维阈值作为整体安全红线与二维矩阵并行运行。整体幻觉率 = 严重 × 3 + 中度 × 2 + 轻微 × 1（加权综合）。

## 6. 知识库条目时间衰减

知识库运行满 6 个月后，启用基于时间的置信度衰减：

| 衰减触发条件 | 衰减规则 | 处理方式 |
|---|---|---|
| 条目连续 90 天未被任何诊断引用 | 置信度评分 × 0.9 | 标记"低频引用，建议复审" |

与一期已实现的反馈驱动衰减（被质疑 ≥ 2 次 × 0.7）并行运行。

## 7. AI修正率检测增强

数据积累充足后，增加以下检测维度：

| 检测维度 | 统计方法 | 告警阈值 |
|---|---|---|
| 分级偏差方向 | 按 AI 偏高 vs AI 偏低统计 | 单方向偏差 > 20% |
| 医生个体维度 | 按医生统计AI修正率 | 单医生 > 50% 且其他 < 20% 标记为个体差异 |

## 8. 边缘端设备认证增强

多租户 SaaS 化部署时引入完整设备认证体系。一期边缘端 API Key 加密采用 HKDF 派生密钥方案（详见 [01-系统架构设计](01-系统架构设计.md) 2.2 节），远期增强为硬件密钥 + 设备证书：

| 维度 | 远期方案 |
|---|---|
| 硬件密钥 | 选配支持 SE 硬件安全模块或 TPM 的边缘硬件，密钥与设备硬件绑定 |
| 设备证书 | X.509 设备证书 + 内部 CA |
| 传输认证 | mTLS（双向 TLS） |
| 证书轮换 | OTA 推送证书更新 |
| CA 根证书 | HSM 存储 |

## 9. 国密算法支持

一期使用标准 TLS 1.3，二期引入国密算法支持：

| 维度 | 二期方案 |
|---|---|
| TLS 传输 | 引入 TASSL 或 OpenSSL 国密分支，支持 SM2/SM3/SM4 |
| 数据加密 | 存储加密增加 SM4 选项 |
| 数字签名 | JWT 签名增加 SM2 选项 |
| 兼容性 | 标准算法与国密算法可配置切换，默认使用国密 |

## 10. 审计日志外部公证

合规审计有明确要求时引入：

| 方案 | 说明 |
|---|---|
| 独立审计服务器 | 每 1000 条日志（或每 1 小时）计算根哈希，写入独立审计服务器 |
| 区块链公证 | 作为备选方案 |

## 11. 规则引擎抽象层

一期已采用 JSON/YAML 声明式规则定义 + 专用解释器执行（仅支持条件判断、算术运算与逻辑比较），详见 [01-系统架构设计](01-系统架构设计.md) 5.6 节。当规则数量超过 500 条且专用解释器性能成为瓶颈时：

| 维度 | 方案 |
|---|---|
| 规则定义格式 | 一期 JSON/YAML 声明式定义（不变） |
| 执行引擎适配层 | `RuleEngine` Protocol 抽象接口（一期已定义） |
| 引擎切换 | durable-rules 或其他高性能引擎，切换后需 ≥ 200 条规则 × 1000 条输入验证一致性 |

## 12. 图查询抽象层增强

一期仅定义 `GraphQueryAdapter` Protocol 接口（约 20 行代码），一期默认使用纯 PGVector + 递归 CTE 方案（详见 [01-系统架构设计](01-系统架构设计.md) 5.5 节与 [02-核心流程与知识库](02-核心流程与知识库.md) 1.1 节）。二期完整实现 Neo4j Cypher 适配器，随更多器官接入和图谱复杂度增加，需增强：

| 维度 | 二期增强方案 |
|---|---|
| 查询优化 | 按引擎特性分别优化查询计划（Neo4j 使用 APOC 存储过程，AGE 使用原生 openCypher） |
| 联合查询 | 跨图谱+向量的联合查询抽象，屏蔽底层存储差异 |
| 性能基准 | 每种查询在两种引擎上的 P99 延迟基准，差异 > 50% 时优化慢引擎实现 |
| 纯 PGVector 降级 | 若 Apache AGE 生产稳定性仍不足，compact Profile 继续使用纯 PGVector + 递归 CTE 方案（一期已验证可行性）；full Profile 可选引入 Neo4j |
| 向量检索引擎 | 一期已将知识库向量检索从 PGVector 剥离至 Qdrant 单机版（详见 [01-系统架构设计](01-系统架构设计.md) §5.4）。二期 full Profile 可选升级为 Qdrant 集群模式以支持更高并发和更大向量规模 |

## 15. Mamba 模型研究

| 阶段 | 方案 | 交付阶段 |

| PoC 步骤 | 通过标准 |

| 阶段 | 要求 |
|---|---|
| 准入 | 最低数据量 ≥ 500 例/器官（联邦学习参与方准入门槛）；**数据质量准入标准**（与 [07-数据标注与模型评估](07-数据标注与模型评估.md) §2 标注质量控制指标对齐）：标注一致率（Cohen's Kappa）≥ 0.85、金标准覆盖率 ≥ 90%、严重标注错误率 ≤ 1%；网络带宽 ≥ 10 Mbps。**与一期灰度发布数据量的关系**：一期单医院需积累 ≥ 667 例/器官方可全量发布，联邦学习准入门槛（≥ 500 例/器官）低于全量发布要求——新参与方达到 500 例即可参与联邦学习训练，但其本地模型仍处于灰度验证阶段（未全量发布），联邦聚合后的全局模型需在各参与方本地验证通过后方可全量发布。**⚠️ 500 例准入门槛与 667 例全量发布门槛的统计合理性说明**：500 例与 667 例之间的差距（167 例）基于以下统计论证——（1）联邦学习参与方仅需提供梯度（模型更新方向），梯度质量取决于数据分布的代表性而非绝对数量；500 例在 3 类器官 × 5 种常见病种场景下，每类约 33 例，足以估计梯度方向（梯度方向的估计精度与样本量的平方根成正比，33 例 vs 44 例的精度差异约 15%，在联邦聚合中由多参与方平均后进一步缩小）；（2）全量发布要求 667 例基于单医院独立诊断准确率验证的统计功效要求（95% 置信区间宽度 ≤ 5%，需约 667 例），此要求不适用于联邦学习参与方（参与方不独立发布，而是通过联邦聚合间接贡献全局模型）；（3）**异常梯度检测在 500 例数据量下的可靠性**：梯度范数偏离聚合均值 > 3σ 的判定标准在 500 例数据量下可能因样本量不足导致梯度方差估计不准确。缓解措施：联邦聚合时采用 Robust Aggregation（如 Krum 算法或修剪均值），对异常梯度具有更强的鲁棒性，不依赖精确的方差估计。**数据质量准入的必要性**：新参与方在 500-667 例期间，其本地数据已参与联邦聚合（影响全局模型），若数据质量未经验证（仅达到数量门槛但质量不达标），其梯度可能污染全局模型。"连续 5 轮异常梯度临时剔除"机制可缓解，但"异常梯度"的判定标准须量化——梯度范数偏离聚合均值 > 3σ 或本地验证指标（准确率/召回率）低于聚合均值 10% 以上视为异常。**⚠️ IID 假设声明**：500 例与 667 例门槛基于参与方数据分布与全局分布相近（IID 假设），若数据分布显著偏离（non-IID），梯度估计偏差可能影响门槛适用性，须提高准入门槛或引入数据分布校验机制 |
| 运行 | 每轮上报梯度 + 本地验证指标；连续 5 轮异常梯度临时剔除 |
| 退出 | 完成当前轮次 → 停止上报 → 保留已聚合模型使用权 |
| 新参与方冷启动 | 从最新聚合权重开始，前 3 轮梯度不参与聚合（预热期） |
| 协调方 | 牵头医院担任，审批准入/退出、管理聚合服务器 |

## 17. 调度层水平分片

> **§14 与 §17 升级编排**：并发 > 50 时消息队列升级（§14）与调度层分片（§17）须同步执行——调度层分片依赖消息队列的持久化能力（Kafka）保证分片间状态一致性。升级顺序：先升级消息队列至 Kafka（§14），验证稳定后再执行调度层分片（§17）。

## 26. 知识库版本控制架构重构

一期版本控制采用3层优先级决策矩阵（safety_critical 即时失效 > 会话级版本锁定 [含串行多器官自动触发与手动 SESSION_KB_VERSION_LOCK 两种变体] > 单次诊断请求粒度切换）+ safety_critical 更新分级处理（词条修复类热加载 + 逻辑规则类新会话生效），二期**替代**为一期3层优先级机制的升级方案——灰度发布 + 会话隔离架构。一期3层优先级代码在二期重构时替换，一期实现时须为二期重构预留接口（`CacheReadPolicy` 类须抽象为策略模式，二期替换策略实现即可切换版本控制机制，无需修改调用方代码）。**⚠️ 一期接口预留与二期架构的适配性说明**：一期 `CacheReadPolicy` 策略模式抽象覆盖"缓存读取判定"维度（safety_critical 即时失效 → 会话 KB 版本锁定 → stale 标记 → TTL 过期），二期灰度发布+会话隔离架构新增"版本分发策略"维度（灰度路由：1-2 个会话使用新版本知识库），两者为不同维度的问题。一期 `CacheReadPolicy` 策略模式可直接复用，二期新增 `VersionRoutingPolicy` 策略模式处理灰度路由逻辑，两个策略模式组合使用而非将灰度路由逻辑塞入 `CacheReadPolicy`，避免违反单一职责原则。**⚠️ 策略组合交互规则**：`CacheReadPolicy` 与 `VersionRoutingPolicy` 组合使用时，`VersionRoutingPolicy` 优先级高于 `CacheReadPolicy`——版本路由决定使用哪个版本的知识库，缓存读取仅在版本确定后生效。例如 `CacheReadPolicy` 判定使用新版本缓存，但 `VersionRoutingPolicy` 判定当前会话应使用旧版本（灰度路由未命中），则最终使用旧版本。此优先级规则确保灰度发布的版本控制不受缓存策略干扰。**⚠️ 一期接口预留原则**：一期接口预留须遵循"最小必要抽象"原则——仅对已明确二期方案的模块预留接口（如 `CacheReadPolicy` 策略模式、`InferenceEngine` Protocol、gRPC Protocol/ABC），对二期方案尚不明确的模块（如知识库版本控制的灰度发布架构细节）仅定义当前实现，不预留抽象层。过多的一期接口预留增加实现复杂度，且二期架构方向调整时预留的接口可能不适用。

| 维度 | 二期方案 |
|---|---|
| 版本类型与触发规则 | major：架构破坏/数据结构变更（必要时强制结束会话）；minor：功能逻辑/诊断规则更新（不强制结束会话，新会话使用新版本）；hotfix/patch：safety_critical 安全修复（不强制结束会话，热加载生效） |
| 灰度发布 | 安全更新先灰度小范围验证（1-2 个会话），无问题再全量发布，旧会话不迁移、不打断 |
| 安全更新人工复核 | 12h 是处理时限，发布前增加临床/安全工程师复核，避免无意义高频更新 |
| 效果 | 从根源上杜绝"安全更新→频繁踢用户"的逻辑；完全符合医疗设备软件的版本管理、临床可用性合规要求 |
