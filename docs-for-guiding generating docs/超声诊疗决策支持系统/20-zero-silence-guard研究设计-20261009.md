# 20-zero-silence-guard 研究设计（2026-10-09）

## 一、问题定义
"静默失败"= 系统内部异常被 except 吞掉/降级为占位，而医生界面看起来一切正常。
事故史：A.10.1 评测器 UnboundLocalError 被吞（59 处清查）；A.35 影像层三处
catch 链吞掉 chunk 求值失败，影像空白存活 3 天。**ongoing 的含义**：只要还在
写代码就可能引入新静默路径，清查不可能一次性终结。

## 二、静默失败面分类学（研究产出 1）
| 面 | 现有守卫 | 盲区 |
|---|---|---|
| 后端管线 | fail-fast/预检/熔断（评测器） | except Exception 泛捕获仍存在 |
| 前端网络 | 0 非豁免 console error（走查） | catch 后渲染占位（无错误也无数据） |
| 前端渲染 | DOM 断言 | **降级可见性**：占位与真实数据在截图像素级难辨 |
| 模型输出 | SG/Self-RAG | LLM 反向索要输入（要求医生复述影像特征）曾无守卫 |

## 三、三层守卫设计（研究产出 2）
1. **约定层**：catch 必须带 `console.error` + 用户可见降级（禁止裸 catch）；
   eslint 自定义规则进 lint。
2. **渲染层**：走查脚本增加"降级可见性断言"——影像区/结论区在 15s 内必须
   出现真实数据特征（canvas 像素方差 > 阈值 或 非占位文案），杜绝"白屏也算过"。
3. **语义层**：LLM 输出若含"请提供/无法获取"类索要短语 → 守卫判红（输入缺失
   的自动暴露），本轮已在真实数据走查中人工触发。

## 四、路线
P1：eslint 裸 catch 规则 + 走查断言②（1 周）；P2：LLM 索要短语守卫（3 天）；
P3：全仓 except 审计自动化（ast 扫描 except: pass）。

## 五、验收
A.35 形态的缺陷（chunk 失败静默）在新守卫下必然判红；全绿门禁 + 走查 20/20
保持不回退。
