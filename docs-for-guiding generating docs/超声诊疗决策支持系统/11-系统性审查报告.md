### 2.1 高风险问题（6个）

#### 🔴 问题1：Ultrasound-CLIP商业许可与NMPA注册冲突风险

**问题描述**：
Ultrasound-CLIP为非商业许可，与NMPA注册后的商业化部署存在潜在冲突。Gate 0启动后30个自然日内须获得商业授权意向书面确认，逾期未确认则自动切换为bge-m3-medical主方案。

**影响范围**：
- 系统架构设计（多模态检索层）
- NMPA注册流程
- 商业部署

**修复方案**：
1. **强化并行备选策略**：
   - 项目立项前：启动商业授权谈判
   - Gate 0启动后30天：获得商业授权意向书面确认
   - Gate 0A阶段：完成bge-m3-medical方案架构适配验证

2. **决策树定义**（已在`10-架构优化修订记录.md`中定义）：
   ```
   Gate 0启动后30天内
   ├─ 获得商业授权意向确认 → 继续Ultrasound-CLIP主方案
   └─ 未获得确认 → 自动切换bge-m3-medical主方案
   ```

3. **指标调整**：
   - 纯文本检索模式下，混合检索召回率目标从≥90%下调至≥85%
   - 多模态检索I2T@10指标取消

**涉及文档**：
- `00-项目总览与核心指标.md` §2
- `01-系统架构设计.md` §5.5
- `07-数据标注与模型评估.md` §5.5

#### 🔴 问题3：compact模式GPU显存预算紧张风险

**问题描述**：
compact模式下RTX 3060 12GB显存预算紧张，显存碎片化可能导致OOM。文档中虽然提到了预算，但未提供实测验证要求。

**影响范围**：
- 系统稳定性
- GPU资源管理

**修复方案**：
1. **Gate 0A强制验证要求**：
   | 验证项 | 通过标准 |
   |---|---|
   | 各模型实际显存占用 | Gate 0A实测 |
   | TensorRT Engine加载峰值 | <12GB |
   | 多器官切换显存峰值 | <12GB |
   | 显存碎片化率 | <40% |

2. **显存管理策略**：
   - 串行加载策略：Ultrasound-CLIP → Cross-Encoder → bge-m3-medical
   - 器官切换时严格按卸载→确认回收→加载→预热顺序执行
   - 显存碎片化率>30%触发Warning告警，>40%触发模型热重载

3. **compact模式显存预算明细（llama.cpp默认）**：
   - llama.cpp GGUF Q4_K_M（7B模型权重）：~3GB
   - Ultrasound-CLIP TensorRT Engine：200-500MB
   - Cross-Encoder TensorRT Engine：100-300MB
   - bge-m3-medical：200-400MB
   - **合计（GPU）**：~3.5-4.2GB
   - **剩余显存**：~7.8-8.5GB（供KV Cache按需分配）

**涉及文档**：
- `01-系统架构设计.md` §4
- `06-开发环境与进度规划.md` §2

#### 🔴 问题4：Redis降级路径复杂度过高风险

**问题描述**：
原设计存在5层Redis降级路径，组合验证复杂度极高，一期集成测试难以全面覆盖。compact模式下Redis定位不明确，导致降级策略过于复杂。

**影响范围**：
- 系统稳定性
- 测试覆盖难度

**修复方案**：
1. **一期强制采用简化方案**：
   | 组件 | compact模式简化方案 |
   |---|---|
   | 调度租约 | 直接使用PG Advisory Lock |
   | 消息队列 | 直接使用PG轮询 |
   | 安全关键事件 | 双写PG+Redis，Redis不可用时轮询PG |
   | 会话状态 | 顺序双写PostgreSQL+Redis，Redis不可用时直查PG |
   | 同意状态 | 直写PostgreSQL，Redis仅作只读缓存（TTL 60s） |

2. **Redis定位明确**：
   - compact模式：`REDIS_ROLE=performance_accelerator`（新增配置项）
   - 仅作为性能加速层，不作为核心依赖

#### 🔴 问题5：compact/full模式临床一致性标准未定义

**问题描述**：
compact模式默认llama.cpp，full模式默认vLLM，两个推理框架的输出一致性未明确定义标准，NMPA注册需要明确的一致性声明。

**影响范围**：
- 临床一致性
- NMPA注册
- 医生信任

**修复方案**：
1. **明确定义一致性标准**：
   | 指标 | 一期标准 |
   |---|---|
   | 分级一致率 | ≥95% |
   | 临床决策边界差异率 | ≤1% |
   | 幻觉率差异 | ≤0.5% |

2. **Gate 0A强制验证**：
   - 使用≥500条超声术语测试集验证一致性
   - 边界病例样本量≥300例，覆盖甲状腺/肝脏/心脏各≥100例

3. **条件性门控规则**：
   - 分级一致率≥95%且边界差异率≤1% → Gate 0A通过
   - 分级一致率90%-95%或边界差异率1%-2% → Gate 0A通过但须在NMPA注册材料中特别声明偏差率
   - 分级一致率<90%或边界差异率>2% → Gate 0A不通过，须统一使用单一推理框架（compact=llama.cpp，full=vLLM）

**涉及文档**：
- `00-项目总览与核心指标.md` §2

#### 🔴 问题6：多器官串行切换容错机制不完善

**问题描述**：
compact模式下多器官串行切换复杂度高，切换失败可能导致系统不可用。切换过程中的容错和降级策略未明确定义。

**影响范围**：
- 系统可用性
- 多器官诊断流程

**修复方案**：
1. **强化切换容错机制**：
   | 切换阶段 | 容错机制 | 失败处理 |
   |---|---|---|
   | 卸载旧模型 | 超时5s | 强制卸载，记录Warning日志 |
   | 确认显存回收 | 超时2s，重试3次 | 触发GPU热重载 |
   | 加载新模型 | 超时10s | 回退至旧模型，记录Error日志 |
   | 预热推理 | 超时3s | 跳过预热，首次诊断延迟增加 |

2. **切换期间诊断请求处理**：
   - 切换期间诊断请求排队等待，不拒绝
   - 急诊请求可中断切换流程（切换中状态），优先处理
   - 切换失败回退期间，诊断请求继续排队等待
   - 回退失败触发进程重启，重启期间拒绝所有诊断输出（E4005）

3. **监控指标**：
   - `organ_switch_success_rate`：切换成功率，目标≥99%
   - `organ_switch_rollback_rate`：回退率，目标≤1%
   - `organ_switch_failure_restart_rate`：回退失败重启率，目标≤0.1%

**涉及文档**：
- `01-系统架构设计.md` §4

### 2.2 中风险问题（12个）

#### 🟡 问题7：知识库版本管理多层机制复杂性过高

**问题描述**：
知识库版本管理涉及3层决策机制，交互规则复杂，组合状态空间3×2×2=12种，测试覆盖难度大。

**影响范围**：
- 知识库更新逻辑
- 集成测试复杂度

**修复方案**：
1. **简化为2层决策机制**：
   | 优先级 | 机制 | 触发条件 | 处理动作 |
   |---|---|---|---|
   | 1（最高） | safety_critical即时失效 | 知识更新标记`safety_critical=true` | 立即终止所有活跃会话，已完成结论保留并标记"基于旧版KB，建议复审" |
   | 2（默认） | 会话级版本锁定 | `SESSION_KB_VERSION_LOCK=true`或串行多器官自动触发 | 会话期间不刷新知识也不标记stale，持续使用锁定版本直至会话结束 |

2. **缓存读取判定优先级链**（4步，严格按顺序执行）：
   1. **safety_critical即时失效检查**
   2. **会话KB版本锁定检查**
   3. **stale标记检查**
   4. **TTL过期检查**

3. **测试矩阵简化**：
   - 组合状态空间从12种缩减为4种
   - 集成测试强制覆盖核心场景

- `02-核心流程与知识库.md` §2.4

#### 🟡 问题13：pynetdicom性能风险未验证

**问题描述**：
pynetdicom为纯Python实现，GIL限制下无法利用多核，在高帧率场景下（30fps）可能成为性能瓶颈。项目立项前未完成pynetdicom vs python-gdcm基准对比测试。

**影响范围**：
- 边缘端DICOM接收性能
- 实时导航帧率

**修复方案**：
1. **强制性能预评估**：
   | 时间节点 | 验证内容 | 通过标准 | 不通过处理 |
   |---|---|---|---|
   | 项目立项前 | pynetdicom vs python-gdcm基准对比 | CPU占用<30%，接收延迟<50ms | 采用python-gdcm |
   | Gate 0A | 选定方案在30fps场景下验证 | CPU占用<30%，接收延迟<50ms | 拆分DICOM SCP为独立进程 |

2. **备选方案决策树**：
   ```
   项目立项前性能预评估
   ├─ python-gdcm性能显著优于pynetdicom → 采用python-gdcm
   └─ pynetdicom性能达标 → Gate 0A验证
      ├─ 通过 → 采用pynetdicom
      └─ 不通过 → 拆分DICOM SCP为独立进程
   ```

## 七、Redis使用现状分析

### 7.1 Redis实例数量与分布

| Profile | Redis实例数 | 部署模式 | 用途 |
|---------|------------|---------|------|
| compact | 1 | 单实例（Sentinel） | 性能加速层 |
| full | 1-2 | 主从复制 | 性能加速层 + 高可用 |

### 7.2 Redis使用场景汇总

| 场景 | 数据结构 | TTL策略 | 读写频率 | 备注 |
|------|---------|---------|---------|------|
| 调度租约(compact) | - | - | - | 直接使用PG Advisory Lock，无Redis依赖 |
| 调度租约(full) | String (SET NX EX) | 30s | 高频 | Redis SET NX EX + PG Advisory Lock降级 |
| 消息队列(compact) | - | - | - | 直接使用PG轮询，无Redis依赖 |
| 消息队列(full) | Stream | 7天 | 中频 | Redis Streams + PG轮询降级 |
| 会话状态缓存 | Hash | 24h | 高频 | 顺序双写PostgreSQL+Redis |
| 知识条目缓存 | Hash | 7天 | 中频 | 热数据缓存，加速检索 |
| 安全关键事件 | List | 永久 | 低频 | 双写PG+Redis，Redis不可用时轮询PG |
| 同意状态缓存 | String | 60s(仅只读) | 低频 | 直写PG，Redis仅作只读缓存，TTL 60s |
| 诊断结果缓存 | String (JSON) | 1h | 中频 | 基于查询hash缓存诊断结果 |
| 脱敏规则缓存 | Hash | 1h | 低频 | 三道防线各自维护独立规则缓存 |
| NER模型缓存 | String | - | 低频 | NER模型路径缓存 |
| 导航标注缓存 | Sorted Set | 5s | 高频 | 实时导航标注缓存，滑动窗口 |
| 降级判定标记 | String | 5s | 低频 | 降级状态标记 |

### 7.3 键值设计规范

| 键前缀 | 数据结构 | 说明 |
|--------|---------|------|
| `session:{session_id}` | Hash | 会话状态缓存 |
| `kb:entry:{entry_id}:v{kb_version}` | Hash | 知识条目缓存（KB 版本号嵌入键名实现自然过期失效，与 01-系统架构设计.md §2.3 一致） |
| `kb:local:{entry_id}` | Hash | 专科智能体本地知识缓存（L2，通过版本号校验与 L1 保持一致） |
| `consent:{patient_id}` | String | 同意状态（仅作只读缓存，TTL 60s，权威源为 PostgreSQL） |
| `diag:result:{session_id}:{organ_code}:v{kb_version}` | String | 诊断结果缓存（支持按会话和器官精确失效，知识库更新时自然过期；与 01-系统架构设计.md §2.3 缓存键格式设计原则一致——版本号嵌入键名） |
| `graph:result:{organ_code}:{history_codes_hash}` | String | 图谱查询结果缓存（TTL = 10 分钟，与 01-系统架构设计.md §5.6 图谱查询异步预执行一致） |
| `desens:rule:{version}` | Hash | 脱敏规则缓存 |
| `ner:model:path` | String | NER模型路径缓存 |
| `nav:annotation:{device_id}` | Sorted Set | 导航标注缓存 |
| `degrade:status:{component}` | String | 降级状态标记 |
| `safety:event:{event_id}` | List | 安全关键事件列表 |

### 7.4 缓存策略总结

| 状态类型 | compact模式 | full模式 | 统一策略 |
|---------|------------|---------|---------|
| 调度租约 | PG Advisory Lock | Redis SET NX EX + PG降级 | Redis作为可选组件，非强制依赖 |
| 消息队列 | PG轮询 | Redis Streams + PG降级 | Redis作为可选组件，非强制依赖 |
| 会话状态 | 顺序双写PG+Redis | 顺序双写PG+Redis | 高频读取场景，Redis缓存有价值 |
| 同意状态 | 直写PG，Redis只读缓存(TTL 60s) | 直写PG，Redis只读缓存(TTL 60s) | 安全关键，强一致要求 |
| 知识条目 | Redis缓存 | Redis缓存 | 中频读取，缓存加速 |
| 诊断结果 | 基于查询hash缓存 | 基于查询hash缓存 | 查询结果幂等性保证 |

### 7.5 Redis安全措施

1. **认证**：生产环境必须配置`requirepass`
2. **网络隔离**：Redis仅允许内网访问，不对外暴露
3. **数据加密**：传输层TLS加密（full模式）
4. **持久化**：RDB + AOF混合持久化
5. **备份**：每日全量备份，保留7天
6. **监控**：内存使用率、连接数、命令执行时间

### 7.6 潜在风险点

| 风险 | 描述 | 缓解措施 |
|-----|------|---------|
| Redis单点故障 | compact模式单实例存在单点故障风险 | Redis Sentinel自动切换 |
| 内存压力 | compact模式内存受限 | `REDIS_SINGLE_INSTANCE=true`，Redis仅作缓存 |
| 键空间膨胀 | 大量短TTL键导致内存碎片 | 定期内存碎片整理 |
| 连接耗尽 | 高并发场景连接池耗尽 | 连接池大小可配置`REDIS_POOL_SIZE` |

#### 🔴 CC-03：会话状态枚举冲突

**冲突描述**：
会话整体状态（session status）在不同文档中定义了不同的枚举值集合，且语义不兼容。

| 文档 | 会话状态枚举 |
|---|---|
| [03-接口规范](03-接口规范.md) §4 | `pending`, `partial`, `completed`, `terminated` |

- `pending`（03/00a）vs `active`（02）：同一语义（会话已创建/进行中），命名不同

**修复建议**：
1. 合并两套枚举为统一集合：`pending`, `active`, `partial`, `completed`, `needs_review`, `failed`, `terminated`
2. 明确状态转换规则（如 `partial` → `needs_review` 仅在 `safety_critical_termination=true` 时发生）

#### 🔴 CC-08：SafetyGateway 降级输出策略描述分散且存在内部矛盾

**冲突描述**：
01-系统架构设计.md 中 SafetyGateway 降级输出策略分散在至少三处，且描述存在重叠与矛盾：

| 位置 | 描述内容 |
|---|---|
| 01 §3.4 SafetyGateway 故障处理表 | 定义 SafetyGateway 不可达时的降级行为：保留 observations + 过滤 diagnostic_conclusion + 附加 fusion_bypassed |

1. 将 SafetyGateway 降级输出策略合并为单一章节，消除重复描述

#### ✅ CC-09：诊断结果缓存键格式与 Redis 键空间规范不一致（已修复）

**冲突描述**：
01-系统架构设计.md §4 提到诊断结果缓存键格式为 `diag_result:{session_id}:{organ_code}:kb_v{version}`，包含知识库版本号。但 11-系统性审查报告.md §7.3（Redis 键空间设计规范）中定义的键前缀为 `diag:result:{query_hash}`，基于查询 hash 而非 session_id + organ_code。

| 来源 | 键格式 | 键结构 |
|---|---|---|
| 01 §4 | `diag_result:{session_id}:{organ_code}:kb_v{version}` | session_id + organ_code + kb_version |
| 11 §7.3 | `diag:result:{query_hash}` | query_hash |

**修复方案**（v1.2 已实施）：
统一为 `diag:result:{session_id}:{organ_code}:v{kb_version}` 格式，理由：（1）支持按会话和器官精确失效（知识库更新时），与 01-系统架构设计.md §2.3 缓存键格式设计原则一致（版本号嵌入键名实现自然过期失效）；（2）会话级缓存已覆盖查询幂等性需求——同一会话内相同器官的诊断结果自然去重；（3）11 §7.3 Redis 键空间规范已同步更新，与 01 保持一致。

#### 🔴 CC-14：知识查询智能体与专科智能体的知识缓存职责边界模糊

**冲突描述**：

### 11.3 关键结论

5. **配置项管理需要系统性治理**：端口冲突（CC-01）、命名不一致（CC-06）、约束关系未定义（DI-10）三个问题叠加，需要建立配置项的单一权威来源和交叉验证机制
