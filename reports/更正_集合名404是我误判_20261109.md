## 一、错误是什么

我在 `98e59fa` 里说：

> `settings.rag_collection` 默认值 `knowledge_chunks`，而 Qdrant 里只有
> `ultrasound_knowledge_chunks` → **dense 腿查 404 集合，一直空转，靠 BM25 兜底**

我用 curl 直接打 Qdrant 验证：
```
GET /collections/knowledge_chunks            → 404
GET /collections/ultrasound_knowledge_chunks → 200
```

**但我绕过了代码。** 真实路径经过 `QdrantVectorIndex`：

```python
# app/embedding/qdrant_client.py:91-95
def _collection_name(self, collection: str) -> str:
    if collection.startswith(self._prefix):
        return collection
    return f"{self._prefix}{collection}"
```

实测：
```
_prefix = 'ultrasound_'
'knowledge_chunks'            → 'ultrasound_knowledge_chunks'   ← 自动补齐
'ultrasound_knowledge_chunks' → 'ultrasound_knowledge_chunks'
```

**两种入参完全等价 → dense 腿从未断过。**

## 二、这连带作废了什么

我在 `98e59fa` 的 commit message 里写的因果链：

> 「BM25 融合能大幅提分（hit@10 +8.6pt）—— 因为 sparse 腿本来在独力支撑」

**这条作废。** BM25 融合的收益是真实的，但**不是因为 dense 腿坏了**。
真实原因是「稀疏+稠密互补」，与"哪条腿坏了"无关。

## 四、新纪律

**验证系统行为时，必须经过系统自己的入口，不能用裸 HTTP 探测替代。**

具体到本项目：
- 查 Qdrant 集合 → 必须经 `QdrantVectorIndex._collection_name()`
- 查检索结果 → 必须经 `Retriever.retrieve()`，不能自己拼 filter
- 查 KB 内容 → 必须经应用层的查询，不能直接 `psql`（除非明确知道字段含义）

**裸 HTTP / 裸 SQL 只能用来"发现线索"，不能用来"下结论"。**
