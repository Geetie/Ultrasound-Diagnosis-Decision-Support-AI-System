## 1. RAGAS 四指标：精确定义与计算方式

> 依据：`ragas` 官方源码（`src/ragas/metrics/_faithfulness.py`、`_answer_relevance.py`、
> `_context_precision.py`、`_context_recall.py`，main 分支）与 `docs.ragas.io`。
> **以源码为准**，文档措辞与实现不一致时按实现写。

### 1.1 Faithfulness（忠实度）

**定义**：答案中能被给定 context **直接推断**的断言占比。

**计算（官方实现，两步）**：

1. **断句/拆断言**（`StatementGeneratorPrompt`）：
   `instruction = "Given a question and an answer, analyze the complexity of each
   sentence in the answer. Break down each sentence into one or more fully
   understandable statements. Ensure that no pronouns are used in any statement."`
   —— 关键约束是**不许留代词**（每条断言必须自足）。

2. **NLI 判定**（`NLIStatementPrompt`）：
   `"judge ... return verdict as 1 if the statement can be directly inferred
   based on the context or 0 if ... can not"`。
   对**每一条**断言给 0/1。

3. **打分**：`score = faithful_statements / num_statements`。
   **断言数为 0 时返回 `np.nan`**（不是 1.0，也不是 0.0）——
   这一点本项目曾在 `p44` 里显式实现为 `faith=None`，是对的。

**本项目必须注意的三个口径陷阱（全部真实踩过）**：

| 陷阱 | 本项目实况 | 后果 |
|---|---|---|
| context 是**列表**，直接 f-string 会渲染成 `['...','...']` | `p44` 首版即如此 | 复算得 0.0304 而非 0.0906 |
| 结论 = **影像所见 + 知识建议**，影像所见永不在 KB 里 | 实测知识断言只占约一半 | faithfulness 天然被压到 0.05~0.15 |
| 判官语言错配（中文答案喂英文 prompt 且要求英文输出） | 已在 `p44` 要求**中文输出** | 否则分数被压死 |

> **本项目结论**：faithfulness 0.0514（n=61 样本/21 输入）**不是"系统不忠实"的证据**，
> 而是"指标语义与结论结构不匹配"的证据。见 §7 未做到。

### 1.2 Answer Relevancy（答案相关性）

**定义**：由答案**反推**出的若干问题，与**原问题**的语义相似度均值；
答案若是"回避型"（noncommittal）则整体归零。

**计算（官方实现）**：

1. 对**答案**（不含问题）生成 `strictness=3` 个候选问题，
   同时判 `noncommittal ∈ {0,1}`；
   `noncommittal=1` 的判据是"evasive, vague, or ambiguous"，例：`"I don't know"`。
2. `cosine_sim = cos(embed(原问题), embed(生成问题))`，取 3 个的均值。
3. `score = mean_cosine × int(not all_noncommittal)`
   —— **3 个里全部 noncommittal 才归零**（`np.all`），不是任意一个。

**本项目注意**：
- 用 `bge-m3` 做嵌入时，**中文问题对中文答案是可行的**，但"反推问题"这一步小模型
  经常生成不了合规 JSON → 官方实现里 `if all(q == "" for q in gen_questions): score = np.nan`。
  本项目 `answer_relevancy 0.3788` 的成因之一是**判官大面积测不到**（返回空），
  不是"答案不相关"。**"测不到"必须报成 NaN/None，不能记 0** —— 否则看起来像"很差"。

### 1.3 Context Precision（上下文精确率）

**定义**：检索到的 context 里，**对得出该答案有用**的那些，是否排得靠前。
官方名 `llm_context_precision_with_reference`，需要 `reference`（参考答案）。

**计算**：对每个 retrieved context 逐条问判官 "这段 context 对推出该 answer 有用吗"（0/1），
然后算 **Average Precision**：

```
cumsum = 0; numerator = 0
for i, v in enumerate(verdicts):        # i 从 0 开始，即排名
    cumsum += v
    if v: numerator += cumsum / (i + 1)
score = numerator / (cumsum + 1e-10)
```

注意分母是 `cumsum + 1e-10`（**命中数**），不是 `len(verdicts)`。
这是标准 AP 而非"精确率"，**一个有用 context 都没命中时分母趋 0 → 分数会爆**，
官方靠 `1e-10` 兜住（返回一个巨大的数）。**这是个需要注意的边界**：
本项目若要接这一段，必须显式处理"零命中"，不要照抄 `1e-10` 兜底。

### 1.4 Context Recall（上下文召回率）

**定义**：参考答案（`reference`）里的每一条断言，能否被 retrieved contexts 归因。

**计算**：把 `reference` 拆句，对每句判 `attributed ∈ {0,1}`，
`score = 归因数 / 总句数`。**分母是参考答案的句子数**（不是检索条数）。

**与 Context Precision 的分母差别（最容易搞混）**：
- Precision 分母 = 检索到的条数里"有用的"占比 → 关心**检索结果干不干净**；
- Recall 分母 = 参考答案里的断言有多少被覆盖 → 关心**答案的依据够不够**。

> 本项目 B2 有 chunk 级 gold，所以 **检索段不需要用 RAGAS 的 LLM 版
> context precision/recall** —— 用 ID 级的 `recall@k` 更准也更便宜。
> RAGAS 这两个指标只在"有参考答案、没有 gold chunk"时才有必要。

### 1.5 RAGAS 四指标与本项目的映射

| RAGAS 指标 | 本项目对应 | 状态 |
|---|---|---|
| faithfulness | `p44`/`p108` 知识断言支持率 | 有实现，**n 太小 + 语义错配** |
| answer_relevancy | `p44` 同批复算 | 有实现，**判官大面积测不到** → NaN 比例高 |
| context_precision | **不需要**：B2 有 chunk 级 gold，用 NDCG/AP | 用 ID 级指标替代 |
| context_recall | **不需要**：同上，用 `recall@k` | 用 ID 级指标替代 |

## 2. TruLens / DeepEval / Phoenix：评估维度对比

| 维度 | TruLens | DeepEval | Phoenix (Arize) | 本项目是否需要 |
|---|---|---|---|---|
| **RAG 三腿范式** | ✅ 明确提 **Context Relevance / Groundedness / Answer Relevance** 三腿（"RAG triad"） | 以 metric 集合为主，无固定范式 | 以 tracing + evals 为主 | ✅ 三腿划分值得抄 |
| 忠实度 | Groundedness（可选 NLI 或 LLM） | `FaithfulnessMetric`（拆断言 + NLI，同 RAGAS） | `Hallucination` evaluator | ✅ 已有 |
| 上下文相关 | Context Relevance（**chunk 级打分**，比 RAGAS 更细） | `ContextualPrecision/Recall/Relevancy` | `QA Correctness`（需 reference） | ⚠️ 用 ID 级替代 |
| 答案相关 | Answer Relevance | `AnswerRelevancyMetric`（同 RAGAS 反推问题） | — | ⚠️ 判官不稳 |
| **检索指标** | ❌ 无内置 hit@k/NDCG | ❌ 无 | ❌ 无（有 retrieval 但非 IR 指标） | ✅ **必须自建**（正是本轮做的） |
| **延迟/成本** | ✅ 有 | 有 | ✅ 强（tracing） | 部分（本项目有 p14/P99 线） |
| **门禁/CI 集成** | 有 feedback functions | ✅ `deepeval test run` 真当 pytest 用 | 弱（偏观测） | ✅ 参考 DeepEval 的"当测试跑" |
| **judge 校准** | 弱 | 有 `GEval` + 可对齐人类 | 弱 | ⚠️ 本轮补功效分析 |

**对本项目的三条可抄结论**：

1. **TruLens 的 RAG triad** 是最该抄的结构：它把"检索给的对不对"（context relevance）
   和"答案有没有依据"（groundedness）分开问。本项目的五阶段分层是它的细化版。
2. **DeepEval 把评估当 pytest 跑**这个形态值得抄 —— 本轮 `p115` 门禁就是这个思路。
3. **三家都没有 IR 指标（hit@k / MRR / NDCG）**。这说明"RAG 评估框架"和"检索评估"
   是两个社区：前者源自 LLM 评测，后者源自 TREC。**本项目必须两边都要**，
   不能指望装一个框架就全套齐活。

## 3. TREC / BEIR / MTEB：检索评估标准，与 NDCG 的正确算法

### 3.1 三个基准各自考什么（别混用）

| 基准 | 考什么 | gold 粒度 | 本项目能用吗 |
|---|---|---|---|
| **TREC**（Deep Learning / Robust 等） | 池化（pooling）+ 人工相关性判定，评 **MAP / nDCG@10 / Recall@100** | doc 级、**分级相关性**（0/1/2） | 方法论可抄，数据不可用 |
| **BEIR** | **零样本跨域**检索泛化，18 个数据集统一成 "query→doc" | doc 级、二值 | 中英文医学集少，且多为英文 |
| **MTEB** | **嵌入模型**的通用能力（分类/聚类/检索/重排…共 8 类任务） | 任务各异 | 用来选嵌入模型，**不是**评系统 |

**关键区分**：MTEB 得分高 ≠ 你的 RAG 检索好。MTEB 测的是"这个嵌入模型在它的
测试集上把相似的东西放得近不近"；你的检索好不好还取决于**分块、过滤、融合、
是否多版本并存**。本项目 2026-11-08 那次"语料翻倍 → hit@10 从 0.75 掉到 0.54"
就是纯系统侧问题，与嵌入模型无关。

### 3.2 NDCG 的正确算法（本项目的核心事故点）

**标准定义**（Järvelin & Kekäläinen 2002；TREC 实践）：

```
DCG@k  = Σ_{i=1..k}  rel_i / log2(i + 1)
IDCG@k = Σ_{i=1..min(|REL|, k)}  1 / log2(i + 1)      # 理想排序：所有相关项排最前
NDCG@k = DCG@k / IDCG@k                                # ∈ [0, 1]
```

其中 `rel_i` 是**第 i 个位置上的文档**的相关性。

**三条必须同时成立的性质**：

1. **每个文档在每个位置只出现一次**。同一文档在排名里出现多次时，
   只有**首次出现**的位置计入 —— 因为 `rel_i` 是"该位置上的文档"的标签，
   而列表里同一文档的重复项不携带新信息。
2. **IDCG 的项数 = min(|REL|, k)**，与 DCG 的项数上界一致。
3. **NDCG ≤ 1 恒成立**，因为 DCG 是"把 |REL| 个 1 放在递增折损下的最优值"的一半以下。

**本项目出过的错**：第 1 条没做（按命中次数累加），第 2 条做了 →
DCG 项数 > IDCG 项数 → NDCG > 1。**修法就是加 `seen` 去重**。

### 3.3 为什么"静默 clamp 到 1"是错的

2026-11-09 审查发现生产代码 `rag_quality.ndcg_at_k` 有 `min(dcg/idcg, 1.0)`。
它"不会报错"，但把 `["x","a","a"]` 对 gold `{a}` 的**正确值 0.6309 抬成了 1.0**。
这是比崩溃更危险的形态：**数字看起来正常，但系统性偏高**。

> 纪律：**越界要暴露，不要 clamp**。本轮 `app/evaluation/retrieval_metrics.py`
> 返回 `(value, violation)`，`violation=True` 会让门禁失败；生产侧保留 clamp 但
> 是因为它受"观测不许抛异常"的既有契约约束 —— 两处的选择在 docstring 里都写明了理由。

### 3.4 分层报（stratified）是强制项，不是可选项

本项目 B2 的三个器官分层差异极大（本轮真机实测）：

| 器官 | n | hit@1 | hit@10 |
|---|---|---|---|
| cardiac | 35 | 0.6000 | 0.9143 |
| liver | 36 | 0.6111 | 0.8333 |
| thyroid | 46 | **0.4348** | **0.7826** |

**总平均 0.5385 掩盖了 thyroid 比 cardiac 低 16.5pt 这个事实**。
只报总数会让"甲状腺检索弱"这件事在报告里彻底消失。

## 4. 医疗 RAG 评估的行业基准

### 4.1 主流基准与它们的"考什么"

| 基准 | 构成 | 评什么 | 对本项目的适用性 |
|---|---|---|---|
| **MedQA / MedMCQA** | 医师资格考试选择题（中/英） | 知识问答准确率 | ⚠️ 考"背知识点"，与"从 KB 检索"不同源 |
| **PubMedQA** | 摘要 + 是否/可能/否 三分类 | 证据推理 | ⚠️ 英文、二分类，粒度粗 |
| **MedRAG / MIRAGE** | 把上述多个集统一包装，**比较不同检索语料**对准确率的影响 | RAG 的"检索语料"变量 | ✅ **方法论最该抄**：同一模型换语料，看检索段的边际贡献 |
| **CMedQA / CMedQA2** | 中文医疗问答对（社区问答） | 答句匹配（BLEU/Recall@k） | ⚠️ 句子级匹配，与"结论式输出"不同 |
| **CMB / CMExam** | 中文医学综合基准 | 中文医学知识 | ⚠️ 同上，偏考试 |
| **MedHallu / 中文医学幻觉集** | 人工构造的幻觉对照 | 幻觉检测 | ✅ 思路可抄（本项目幻觉检测是自建的） |

**关键洞察（MIRAGE / MedRAG 的做法）**：
它们把"检索语料"当作**自变量**做对照实验，而不是只报一个总分。
这正好对应本项目 2026-11-08 的教训 —— "语料翻倍导致 hit@10 下降"如果只报总分，
看起来像退步；分语料报才知道是**任务变难了**。

### 4.2 医疗场景特有的三个评估维度（通用 RAG 框架不覆盖）

1. **拒答/转人工的正确性**。医疗 RAG 的"不知道"比"编一个"更有价值。
   本项目 B2 里有 3 条 `answerable:false`，**这就是拒答率的种子**，但当前
   `p94` 的 docstring 宣称要算"拒答率"而代码里**一个字没算**（见 §5 BUG-4）。
2. **数值/分级的精确性**。医疗里"4a 类"和"4b 类"差一档就是穿刺与否的区别。
   通用 faithfulness 只判"能不能推出"，判不出"数字对不对"。
3. **多权威语料冲突时的并列义务**。不同指南给出不同阈值时，**系统不该二选一**。
   这是本项目独有的"增强层"评估点（见 §6 阶段 4）。

> **诚实声明**：本项目的 CMedQA-RAG / 中文医疗 RAG 专用基准**没有落地**。
> 只在公开资源调研（`reports/B1B4_公开资源可行性_穷尽调研_20261108.md`）里评过可用性。
> 本轮的评估集仍然是自造的 B2（120 条手写），**不是行业公认基准**，
> 因此任何"达到行业水平"的说法都缺乏依据。

## 5. LLM-as-Judge 的已知偏差与缓解

### 5.1 三个已证实的偏差（Zheng et al., MT-Bench, NeurIPS 2023, arXiv:2306.05685）

| 偏差 | 表现 | 本项目是否受影响 |
|---|---|---|
| **位置偏差**（position bias） | 交换 A/B 顺序后判定改变 | ✅ **本项目当前不受影响**：`p44`/`p108` 的 faithfulness 是**单条判定**（不比较两条），`p107` 是**同一输入重复采样比一致性**（也不是两两比 A/B）。这个偏差要等"两套系统答案互比"时才出现 —— 一旦引入对话式 A/B，必须做双向交换 |
| **冗长偏差**（verbosity bias） | 更长/更啰嗦的答案被判更好 | ✅ **高度受影响**：本项目结论含大量派生推导（分级/总分/置信度），越长越长，判官容易给"看起来有据"的印象分 |
| **自我偏好**（self-enhancement） | 判官偏好自己（同族模型）生成的文本 | ✅ **受影响**：判官 8006 是 Qwen3-8B，生成是 Qwen2.5-7B/II-Medical-8B，**同源** |
| **推理能力有限** | 多步推理/数学判定常错 | ✅ 受影响：判"`≥7 分` 是否与 KB 的 `TR5 分档表` 一致"属多步 |

**官方给出的缓解手段**（论文 §4）：
1. **交换顺序**（swap augmentation）—— 两次判定取一致的那次，不一致就判平局；
2. **参考基准答案**（few-shot judge with reference）；
3. **Chain-of-thought + 强制先给理由再给结论**；
4. **限制评判粒度**（只判单一维度，不要一次判"好不好"）。

### 5.2 本项目应采取的具体缓解（按性价比排序）

| # | 措施 | 成本 | 为什么值得 |
|---|---|---|---|
| 1 | **判官输出强制"理由→判定"**，理由为空即判为"没测到"而非给 0 | 低 | 已有 `judge_eval_set` 的"仪器自检"雏形，应固化 |
| 2 | **未来引入 A/B 互比时做双向交换**（当前无此形态，属预防） | 中（判官调用翻倍） | 位置偏差是**已知系统性偏差**，一旦做互比不处理等于不可辩护 |
| 3 | **判官与被测模型换族**（判官用非 Qwen 系） | 中（要装新模型） | 消除自我偏好；当前 8006 与生成同源是硬伤 |
| 4 | **判官校准集**：人工标 50~100 条，算判官与人的一致率（Cohen's κ） | 高（要人工） | **没有 κ 的 judge 分数不能对外报**，这是本轮最缺的一环 |
| 5 | **禁止跨口径比较**（如"我们用 8B 判官，论文用 GPT-4 判官，所以我们分数低"） | 零 | 判官不同 = 尺子不同 |

### 5.3 判官可靠性的"最低可接受线"

- **Cohen's κ ≥ 0.6**（substantial agreement）才允许把判官分数用于**门禁**；
- **κ ∈ [0.4, 0.6)** 只能用于**趋势观察**，报告里必须标"判官未充分校准"；
- **κ < 0.4** 视为判官不可用，**只能报"测不到"**。

> 本项目当前状态：**没有任何判官 κ 数据**。所以 `faithfulness 0.0514` 与
> `answer_relevancy 0.3788` 都属于"κ 未知"档，**不应进任何门禁**。
> 本轮 `p115` 因此**没有**把这两项做成阻断门禁 —— 这是刻意的，不是漏做。

## 6. 统计显著性检验与功效分析（本轮核心交付之一）

### 6.1 三个检验的适用面（用错会让结论全错）

| 检验 | 前提 | 本项目对应场景 | 常见误用 |
|---|---|---|---|
| **McNemar 精确检验** | 同一批样本、两个**二分类**系统 | hit@k 的 A/B（同一 120 条 query 换检索配置） | ❌ 拿两独立比例检验代替 → n 需求高一个数量级 |
| **配对 bootstrap** | 同一批样本、连续量 | NDCG/MRR 的均值差 CI | ❌ 用独立 bootstrap（重采样不配对） |
| **paired t-test** | 配对、近似正态 | 同上，但 n 小时正态假设不成立 | ❌ n=20 就用 t 检验 |

**本项目的正确选择**：
- hit@k 是二值 → **McNemar 精确**（`b` = A 命中 B 未命中，`c` = 反之）；
- NDCG/MRR 是 [0,1] 连续且有大量 0/1 堆积（不接近正态）→ **配对 bootstrap**；
- **不要**用两独立比例：那假设两组是不同的 query，而我们是同一批 query。

### 6.2 功效分析：n 多小就判不动（精确实测）

**方法**：配对 McNemar，`b ~ Bin(n, (d+δ)/2)`、`c ~ Bin(n, (d−δ)/2)`，
其中 `d` = 不一致率（b+c 占总样本的比例）、`δ` = 要判的绝对差。
对 (b,c) 联合分布求和得到**精确功效**（不用正态近似），二分搜索找最小 n。

**表 A：判定 5pt 绝对差所需的 n（80% power, α=0.05，精确解）**

| 不一致率 d | 所需 n | 闭式近似给的 n | 闭式低估 |
|---|---|---|---|
| 6% | 191 | — | — |
| 8% | 262 | — | — |
| **10%** | **333** | 312 | −21（−6.3%） |
| **15%** | **487** | 469 | −18（−3.7%） |
| **20%** | **640** | 626 | −14（−2.2%） |
| 25% | 787 | 783 | −4（−0.5%） |
| 30% | 932 | — | — |

> **闭式解系统性偏乐观**（方向是"让你以为样本够了"）。所以
> `app/evaluation/statistics.required_n_for_delta` 只给方向，
> **对外报数一律用 `required_n_for_delta_exact`**，两者都被单测钉住。

**表 B：固定 n 时能判定的最小绝对差（80% power，精确解）**

| n | d=10% | d=15% | d=20% | d=25% |
|---|---|---|---|---|
| 50 | 判不动 | 判不动 | 17.5pt | 19.7pt |
| 100 | 8.8pt | 10.9pt | 12.7pt | 14.2pt |
| **117（当前 B2）** | **8.2pt** | **10.1pt** | **11.8pt** | **13.2pt** |
| 200 | 6.4pt | 7.9pt | 9.0pt | 10.0pt |
| 300 | 5.3pt | 6.4pt | 7.3pt | 8.2pt |
| 400 | 4.5pt | 5.5pt | 6.4pt | 7.1pt |
| **487** | 4.1pt | **5.0pt** | 5.7pt | 6.4pt |
| 800 | 3.2pt | 3.9pt | 4.5pt | 5.0pt |
| 1000 | 2.9pt | 3.5pt | 4.0pt | 4.4pt |

> 读法：**n=117、不一致率 15% 时，要 ≥10.1pt 的差才判得动**。
> "判不动"= 即便把 δ 取到不一致率上限也达不到 80% 功效。

### 6.3 结论：要多少 n 才能判定 5pt

**直接回答用户的问题**：

> **在 n = 487 时（不一致率 15%），能以 80% power 判定 5pt 绝对差。**
> 不一致率越低（两套系统越像）需要越多，10% 时需 333，20% 时需 640。
>
> **当前 B2 的 n=117 只能判 ≈10pt 以上的差异** ——
> 这就是为什么"n=117 时多数差异 p>0.1，5-7pt 的差异无法判定"。

**实操建议**：
1. **短期（不改数据集）**：任何 <10pt 的检索差异，报告里一律写"**判不动**"，
   不写"提升/下降"。这是最省力也最诚实的做法。
2. **中期**：把 B2 从 120 扩到 **≥500 条**（按器官 1:1:1 分层，thyroid 需要补最多，
   因为它是当前最弱的一层）。扩到 500 后可在 d=15% 下判 5pt。
3. **长期**：如果有配对设计（同一批 query 跑 A/B），保持 n≥500；
   若必须用独立设计（两套系统在不同集上），n 需求会涨到 **每组 1500+**（见 §6.4）。

### 6.4 独立设计 vs 配对设计（差一个数量级，别用错）

| 设计 | 场景 | 判 5pt（基线 60%）所需 n |
|---|---|---|
| **配对**（同批 query） | 本项目 A/B 调参 | **487**（每套系统各跑 487 条同一批 query） |
| **独立**（两份不同测试集） | 与外部系统对比 | **1534 / 组** |

> 差 3 倍。如果误用独立设计的公式，会把需求从 487 估到 1534，从而得出
> "样本量要求不可行"的错误结论。

### 6.5 多重比较

同时比 7 个指标（hit@1/5/10、MRR、NDCG、precision、recall）时：
- **不校正** → 族错误率 ≈ `1 − 0.95^7 ≈ 30%`，即 7 次里约 1/3 概率至少一次假阳性；
- **Bonferroni** → 单检验阈值 `0.05/7 ≈ 0.0071`，功效随之下降；
- **推荐**：**先定一个主指标**（本项目建议 **NDCG@10**，它同时吃"找没找到"和"排得靠不靠前"），
  其余作为**次要观察**并明确标注"未校正"。

> 本轮 `p115` 门禁**没有**做多重比较校正 —— 因为它判的是"是否跌破固定基线"，
> 不是"是否显著优于"，两者语义不同。这一点在门禁 docstring 里写明了。

### 7.3 两个新的真实发现（本轮挖出，此前无人报过）

**发现 1：表格结构在分块环节大面积丢失（管道符保留率 17%）**

- 源文档 2993 份里，含 `|` 的行保留到 chunk 里的比例只有 **17.04%**；
- 后果：表格被拍平成裸数字流。本项目已在 `app/rag/source_conflict.py` 的注释里
  记录了同源现象 —— "4a/4c 的风险区间在 C-TIRADS 原文里是**表 1 的裸数字**
  （`2~10`、`50~90`，% 号只在表头），带 % 的检索式查不到"；
- **这不是新 bug，是已知问题的量化**。此前只知道"表格有问题"，
  现在知道量级：**约 83% 的表行没了**。
- 修起来贵（要改 PDF 解析 + 重建索引），所以本轮**只测量不修**。

**发现 2：只有 32.7% 的 chunk 以完整句子结尾**

- 分块 p50 = 973 字（约 486 token），**紧贴 bge-m3 的 512 token 上限**；
- 67.3% 的块从句子中间断开 → 检索命中它时，模型拿到的是半截话；
- 这是"hit@10 看起来还行但答不准"的一个可能来源；
- 同样只测不修（重建索引成本高，且当前语料仍在变）。
