## 0. 先纠正一条前提（重要，影响后续所有验证口径）

任务书里给的验证项 **`TR2/TR3/TR4/TR5` 在 KB 里 > 0 条** 与 **`85%～100%` > 0 条**，
经逐文件实测，**前者不可能通过任何分块改造达成**，后者是**探测串写错**造成的假缺陷：

### 0.1 `TR1–TR5` 在源语料里出现 **0 次**

【本项目实测】对 `~/uai/data/corpus/raw/*.pdf` + `raw_v15/*.pdf` 共 25 份 PDF 逐份抽取正文，
用 `\bTR\s?-?\s?[1-5]\b`（含全角连字符变体）统计：

| 文件 | `TRn` | `TI-RADS` | `C-TIRADS` | `LR-n` |
|---|---:|---:|---:|---:|
| ctirads_2021 | **0** | 113 | 49 | 0 |
| acr_ceus_tra_2024_core | **0** | 0 | 0 | 8 |
| thyroid_cancer_norm_2018 | **0** | 3 | 0 | 0 |
| 其余 22 份 | **0** | … | … | … |
| **合计（25 份）** | **0** | 122 | — | — |

- C-TIRADS 2021 用的是**中文分类**：`1 无结节 / 2 良性 / 3 良性可能 / 4A / 4B / 4C / 5 / 6`，
  原文表 1 表头是「结节｜分值｜恶性率 %｜C-TIRADS分类」——**没有 TR 编号**。
- `TR1–TR5` 是 **ACR TI-RADS** 的编号体系，本项目 25 份语料里**没有任何一份 ACR TI-RADS 白皮书**。
- 结论：这项验收指标**不是分块问题，是语料缺口**。要达成只能补 ACR TI-RADS 语料。
  把它报成"改造后 >0"就是编数字，**不做**。

### 0.2 `85%～100%` 的 0 条是**字符问题**，不是分块问题

【本项目实测】KB 里查 `85%～100%`（全角 `～` U+FF5E）= **0 条**；
但查 `85%~100%`（半角 `~` U+007E）= **17 条**（v1.5.0 内 3 条）。原因：

- 源文件 `thyroid_cancer_norm_2018` 的**原文**就写的是半角：`5%~85%`、`50%~85%`、`85%~100%`
  （`~/uai/data/corpus/markdown/thyroid_cancer_norm_2018.md:127,130,131`，
  码位实测 `SEP = '~' U+007E`）。
- 旧探测脚本用全角串去匹配半角原文 → 恒 0。**缺陷在探测脚本，不在分块器。**

### 0.3 但**表格确实有真缺陷**（这才是要修的）

【本项目实测】`knowledge_chunks` v1.4.0（1297 块）：

| 指标 | v1.4.0 | v1.5.0（3745 块） |
|---|---:|---:|
| 含 `|` 的块 | 38 | 38 |
| **以 `|` 开头、无 `|---|` 分隔行的"孤儿表格块"** | **12** | **12** |
| 带表题（`表N`/`Table N`）的块 | 33 | 234 |

典型孤儿块（零语义、检索必挂）：

```
pdf_cardiac_cardiac_echo_measurement_2016_0013
  ||下限|上限|下限|上限|下限|上限|…          ← 纯数字矩阵，无表头无表题
pdf_thyroid_thyroid_cancer_guideline_2022_0003
  |4a||具有1 种恶性征象|5%～<br>10%|          ← 半张表，<br> 切断数值
```

另一方面，C-TIRADS 表 1 在 v1.4.0 里**其实是完整的**
（`kb_v1.4.0:pdf_thyroid_ctirads_2021_0010#0000`，921 字符，含 `3~4|50~90|4C` 等全部行）——
所以"表 1 被切碎"这个描述本身也不准确：**被切碎的是其他表**。

### 0.4 因此本报告采用的验证口径（可复现、有源可查）

| 编号 | 指标 | 定义 |
|---|---|---|
| A | **孤儿表格块数** | 以 `\|` 开头且无 `---` 分隔行的 chunk 数 → 目标 **12 → 0** |

## 1. Anthropic《Contextual Retrieval》（2024-09）

来源：<https://www.anthropic.com/news/contextual-retrieval>

### 1.1 核心结论（原文数字）

| 方法 | top-20 检索**失败率** | 相对降幅 |
|---|---:|---:|
| 基线（embedding + BM25） | 5.7% | — |
| **+ Contextual Embeddings** | 3.7% | **−35%** |
| **+ Contextual Embeddings + Contextual BM25** | 2.9% | **−49%** |
| **+ 上述 + Reranking**（Cohere） | 1.9% | **−67%** |

其他可直接用的参数：

- 上下文文本 **50–100 tokens**，**前置**（prepend）到 chunk 再算 embedding **和** BM25 索引；
- 生成上下文用 **Claude 3 Haiku** + **prompt caching**：800 tok chunk / 8k tok 文档 /
  50 tok 指令 / 100 tok 上下文 → **一次性成本 $1.02 / 百万文档 token**；
- 检索 **top-20** 优于 top-10 / top-5（他们试了 5/10/20）；
- Rerank 流程：先取 **top-150** → reranker → **top-20**；
- 明确否掉的两条（"我们试了，收益很小"）：给 chunk 加**通用文档摘要**、
  **summary-based indexing**。这两条对本项目有直接参考价值（别去搞文档摘要索引）。

### 1.2 对本项目的适用性

- ✅ **值得做**：本项目 chunk 里大量 `(1)…(2)…` 片段脱离标题后不可读（实测孤儿块就是极端例子）。
- ⚠️ **成本约束**：本项目 6606 个 chunk（v2 全量）× 每个一次 LLM 调用，用本地 Qwen2.5-7B
  可行但慢；且 LLM 生成上下文**必须抽检**（本项目有 A.70"提示词示例照抄"前科）。
- ⚠️ **不能替代分块改造**：它解决"块缺上下文"，不解决"表格被切碎"。
- 【本项目实测】本轮**未启用** contextual chunk（LLM 生成需 GPU 窗口 + 抽检流程，
  超出本轮范围），已列为后续项。

## 2. Pinecone《Chunking Strategies》

来源：<https://www.pinecone.io/learn/chunking-strategies/>

### 2.1 五类的取舍（原文要点）

| 策略 | 适用 | 代价 |
|---|---|---|
| **Fixed-size** | "大多数情况的最佳起点" | 忽略结构 |
| **Content-aware**（句子/段落） | 需要边界干净 | 依赖分句器质量 |
| **Recursive**（`RecursiveCharacterTextSplitter`） | **"瑞士军刀"、作者首选** | 仍是启发式 |
| **Document structure-based**（PDF/Markdown/LaTeX 标题） | 长文档有 `#`/章节 | 需要结构化解析 |
| **Semantic**（Kamradt） | 主题漂移处切 | 需嵌入计算、效果争议（见 §5、§7） |
| **Contextual**（Anthropic） | 块脱离文档不可读 | LLM 成本 |

其他要点：

- **"如果一个 chunk 脱离上下文对人来说讲得通，对 LLM 也一样讲得通"** —— 这是最实用的判据，
  本轮的"整表成块"正是按它决定的。
- **chunk expansion（后处理扩邻块）** 被单独推荐：检索小块、返回时扩成邻块/整页。
  这就是父子块思想的轻量版。
- 明确提 **lost-in-the-middle**（Liu et al. 2023, arXiv:2307.03172）：上下文塞太长反而掉召回。
  → 支持"父块有上限"，不能无限大。
- 明确**没有**给 overlap 的具体数字（这是本文最弱的点，见 §8）。

### 2.2 对本项目

- ✅ 采用 **Document structure-based**（用 MinerU 的 `#`/`##`/`###`，不正则猜）
- ✅ 采用 **chunk expansion**（父子块，§4）
- ❌ 不采用纯 Semantic（见 §7 的实测反证）
- ❌ 不采用 fixed-size 作为默认（旧代码的 `FixedWindowChunker` 保留作兜底）

## 3. 父子块（Small-to-Big / Parent Document Retriever）

来源（厂商文档与实现）：
- LangChain `ParentDocumentRetriever`（<https://reference.langchain.com/python/langchain/retrievers/parent_document_retriever>）
- LlamaIndex `AutoMergingRetriever`（<https://developers.llamaindex.ai/python/framework/integrations/retrievers/auto_merging_retriever/>）

### 3.1 共同做法

两条路线本质一致：**用小块建索引做检索，命中后按父子关系把更大的原文交给 LLM。**

| | LangChain `ParentDocumentRetriever` | LlamaIndex `AutoMergingRetriever` |
|---|---|---|
| 索引单元 | **child**（`child_splitter`） | **leaf** 节点 |
| 返回单元 | **parent**（`parent_splitter`，存 docstore） | 命中叶子的**父节点**；同父下叶子命中比例 ≥ 阈值时**自动合并**为父 |
| 关键参数 | `child_splitter` / `parent_splitter` / `id_key` | `simple_ratio_thresh`（默认 **0.5**） |

### 3.2 为什么"小块检索、大块喂 LLM"优于单一粒度

- **检索侧要小**：向量是单点压缩，块越长语义越"过压缩"（Late Chunking 论文同结论，§4）。
- **生成侧要大**：LLM 需要表头、前提、"本段属于哪一节"（Anthropic §1 的同一动机）。
- **单一粒度必然二选一**：选小则喂不全，选大则检索糊。
- 【本项目实测】`bge-m3` 对同一张表的两种形态做 query 相似度（见 §8.1）：
  **整表原样 0.6241 / 管道化 0.6077** —— 说明"检索单元"对表示形式敏感，
  但**没有**证明"小块一定更好"。所以父子块在本项目是**设计选择**，不是实测结论。

### 3.3 本项目的落地

- 父块 = 一个标题小节（上限 1600 tok）；子块 = 400 tok 内的段/表/列表。
- **单块小节不生成父块**（避免索引膨胀一倍：实测 1215 源文档 → 1222 父 + 5384 子）。
- 回填在 `Retriever._expand_parent_chunks`：**replace 内容、保留分数与排名** →
  对 hit@k 这类 chunk 级召回指标**无影响**（这是它安全的根本原因），收益在生成侧。
- 开关 `rag_use_parent_expansion`（默认 True），有唯一读取点（硬规则 #17）。

> ⚠️ **诚实标注**：父子块的**生成侧收益本轮未实测**（需要跑生成质量评测，
> 涉及 GPU 窗口与判官）。本轮只证明它**不破坏检索指标**且**表/节完整性提升**。

## 4. Late Chunking（Jina AI, 2024）

来源：Günther, Mohr, Williams, Wang, Xiao.《Late Chunking: Contextual Chunk Embeddings
Using Long-Context Embedding Models》arXiv:**2409.04701**（v1 2024-09-07，v3 2025-07-07）

### 4.1 方法

**先编码全文、后切分**：把整篇文档喂进长上下文嵌入模型 → 得到**token 级**表示 →
**再**按 chunk 边界做 mean pooling。切分发生在 transformer **之后**、pooling **之前**
（"late" 由此得名）。无需额外训练。

### 4.2 关键数字

- 示例（`jina-embeddings-v2-small`，查 "Berlin" 的相似度）：

| 句子 | 朴素切分 | Late Chunking |
|---|---:|---:|
| "Berlin is the capital…" | 0.8486 | 0.8495 |
| "Its more than 3.85 million inhabitants…" | 0.7084 | **0.8249** |
| "The city is also one of the states…" | 0.7535 | **0.8498** |

→ 不含实体的句子相似度**大幅提升**（0.708→0.825），因为编码时看到了 "Berlin"。

- 评测设置：BeIR 小数据集子集；三种切分（**256 token 固定 / 5 句 / 语义句**）；
  三个嵌入模型；`nDCG@10`。
- **Long Late Chunking**：文档超过模型上下文时，切 macro-chunk（`l_max`）并带
  **overlap ω** 个 token 作为补充上下文，再在 macro 内做 late chunking。

### 4.3 对本项目的适用性（关键限制）

- ❌ **本项目当前用不了**：late chunking 要求**能拿到 token 级表示**。我们的嵌入服务是
  `http://127.0.0.1:8004/v1/embeddings`（bge-m3），**只返回池化后的 1024 维向量**，
  不暴露 token embeddings。要做必须自建推理（改服务）→ 超出本轮。
- ⚠️ **理论收益方向与我们的问题不重合**：late chunking 解决"块内指代丢失"
  （"its"/"the city"），我们的主要缺陷是**表格被切碎**与**表头丢失**——
  后者是**解析/切分**问题，late chunking 不解决。
- ✅ **可借用的一条**：它证明"**上下文信息应该在编码时可见**"，这支持把
  **表题 + 表头**放进同一个 chunk（而不是靠 overlap 事后补）。

## 5. 语义分块：Greg Kamradt《5 Levels of Text Splitting》

来源：<https://github.com/FullStackRetrieval-com/RetrievalTutorials>
（`tutorials/LevelsOfTextSplitting/5_Levels_Of_Text_Splitting.ipynb`）

### 5.1 五级

| 级别 | 做法 | 原文评价 |
|---|---|---|
| 1 | **Character splitting** | "不推荐任何应用"，只是教学起点 |
| 2 | **Recursive character**（分隔符 `\n\n`→`\n`→` `→``） | "瑞士军刀、mock 首选" |
| 3 | **Document specific**（PDF / Markdown / Python 各自的结构） | 按文档类型用结构 |
| 4 | **Semantic**（嵌入相似度找断点） | 实验性 |
| 5 | **Agentic**（让 agent 决定切点） | 实验性，赌 token 会趋零 |
| Bonus | **Alternative representation**（摘要/命题等派生表示用于索引） | 与索引策略配合 |

**The Chunking Commandment**（原文）："你的目标不是为切分而切分，而是把数据变成
**以后能被检索出价值**的形式。"

### 5.2 语义分块的原始实现细节（Chroma 复现时用的默认值）

- 按句切 → 对**滑动窗口**的句子算嵌入 → 找相邻窗口余弦距离的**不连续点**；
- **默认阈值 = 所有相邻距离的 95 分位**（相对阈值 → 语料越大块越大）；
- LlamaIndex 的 `SemanticSplitterNodeParser` 系同一思路。

### 5.3 对本项目的适用性

- ✅ Level 3（document-specific）正是本轮采用的做法（MinerU 给了真结构）。
- ❌ Level 4 semantic：见 §7 的**实测反证**（本项目实测语义切分不划算）。
- 现有 `SemanticChunker` 与 Kamradt 的算法**无关**——它只认
  `TI-RADS+数字 / LI-RADS+数字 / Category N / N类` 正则，是"标题正则"而非"语义断点"。
  对 C-TIRADS 2021（用中文 `4A/4B/4C`）**完全失效**（这也是它在本项目几乎没用的原因）。

## 7. 补充查证：医疗文档 / 表格 / overlap 的实测数据

### 7.1 语义分块到底值不值？（**这是本轮最重要的一条反证**）

来源：Qu, Tu, Bao.《Is Semantic Chunking Worth the Computational Cost?》arXiv:**2410.13070**（2024-10）

> 摘要原文结论：*"results show that the computational costs associated with semantic
> chunking are not justified by consistent performance gains"* ——
> 在 **document retrieval / evidence retrieval / retrieval-based answer generation**
> 三类任务上，语义分块的**额外算力没有被稳定增益所抵消**。

→ 对本项目：`SemanticChunker` 既不是真语义（是标题正则），又没有实测增益证据，
**本轮不作为默认**，保留但明确标注为"实验性"。

### 7.2 切分策略的 token 级实测（Chroma 2024，**本项目可直接引用的最好数据**）

来源：Smith & Troynikov.《Evaluating Chunking Strategies for Retrieval》Chroma Technical
Report, 2024-07-03（<https://www.trychroma.com/research/evaluating-chunking>）

评测：token 级 Recall / Precision / IoU，5 个语料，`text-embedding-3-large`，
**取回 n=5 块**。

| Chunking | Size | **Overlap** | Recall | Precision | IoU |
|---|---|---:|---:|---:|---:|
| Recursive | 800 | 400 | 85.4 | 1.5 | 1.5 |
| Recursive | 400 | 200 | 88.1 | 3.3 | 3.3 |
| Recursive | 400 | **0** | **89.5** | **3.6** | **3.6** |
| Recursive | 200 | **0** | 88.1 | **7.0** | 6.9 |
| TokenText | 200 | 0 | 87.0 | 5.2 | 5.1 |
| Kamradt（语义，默认） | ~660 | 0 | 83.6 | 1.5 | 1.5 |
| KamradtMod（★，二分搜阈值） | ~397 | 0 | 87.1 | 2.1 | 2.1 |
| Cluster（★，聚类最优） | 400 | 0 | **91.3** | 4.5 | 4.5 |
| Cluster | 200 | 0 | 87.3 | **8.0** | **8.0** |
| LLM（GPT-4o） | ~240 | 0 | **91.9** | 3.9 | 3.9 |

同一个表在 `all-MiniLM-L6-v2` 上：

| Chunking | Size | Overlap | Recall |
|---|---|---:|---:|
| TokenText | 250 | **125** | **82.4** |
| TokenText | 250 | **0** | 77.1 |
| Recursive | 250 | 125 | 78.7 |
| Recursive | 250 | 0 | 78.5 |

**关于 overlap 的结论（这是任务要的"实测数据"）**：

1. **`text-embedding-3-large` 上 overlap 有害**：400/200 = 88.1 vs 400/0 = **89.5** recall；
   IoU 3.3 vs 3.6。原文：*"reducing chunk overlap improves IoU scores, as this metric
   penalizes redundant information"*。
2. **小模型（MiniLM）上 overlap 有益**：250/125 = 82.4 vs 250/0 = **77.1** recall，
   **+5.3pp**。原文：*"for smaller context, overlapping chunks are necessary for high recall"*。
3. → **overlap 是有益还是有害，取决于嵌入模型上下文容量**，没有普适数字。
4. 原文另注：OpenAI Assistants 默认 **800/400** 是"明显低于平均的 recall + 全部指标最差"的配置。

**关于"语义/智能切分是否值得"**：
- `Kamradt` 默认（95 分位阈值）**低于平均**（recall 83.6）；
- ★`KamradtModified`（改成二分搜阈值以满足指定长度）+3.5pp → 87.1；
- ★`Cluster`（全局最优，DP）换来 **最高 IoU**（8.0）但要重算全局；
- ★`LLM` 切分 recall **最高**（91.9）但其它指标平庸 —— **LLM 会切，但不会让人检索更省 token**。

### 7.3 医疗文档分块的特殊性

> ⚠️ **诚实标注**：这一节**没有找到**针对"超声/影像指南"分块的同行评议实测论文。
> 以下是从本轮读到的语料结构里归纳的**观察**，标 `【本项目观察】`，属工程判断而非文献结论。

【本项目观察】医疗指南（本项目 25 份）的结构特点，决定了通用切分器会失败：

1. **决策表是核心知识载体**，且**表意强依赖表头**：C-TIRADS 计数表若丢掉
   「结节｜分值｜恶性率 %」表头，剩下 `4A 低度可疑恶性` 单独成块就没有"4A 对应几分"的信息。
2. **参考值区间以"区间"为单位**：`50~90`、`2~10`、`5%~85%`。
   切分器若在 `~` 处断行（pypdf 的 `<br>` 就干这个），区间变成两个数 → **数值语义被破坏**。
3. **同一概念多套权威并存**：C-TIRADS 2021（中华医学会）与甲状腺癌诊疗规范 2018（国家卫健委）
   在 4A 类 FNA 阈值上**一个是 >15 mm、一个是 >1 cm**（本项目 v1.5.0 实测两块原文都命中）。
   → 分块必须带 `source_authority`，否则冲突检测做不到（本轮的元数据改造正是为此）。
4. **列表即规则**：`(1)…(2)…(3)…` 的编号列表常是处理建议的完整链条，断在中间会让
   "建议 FNA" 与"阈值 15mm"分离。

### 7.4 表格怎么切成可检索 chunk（任务问题）——本轮有实测

【本项目实测】同一张 C-TIRADS 计数表，5 种表示形态 vs 10 条真实问句的相似度
（bge-m3，1024 维，余弦；问句取自本项目的检索集风格）：

| 表示 | mean | min |
|---|---:|---:|
| **aligned_raw**（MinerU 原样：空白对齐） | **0.6241** | **0.5474** |
| verbalized（逐行转自然语言："有结节，分值3~4，恶性率50~90%，C-TIRADS分类4C（高度可疑恶性）"） | 0.6184 | 0.5550 |
| aligned + 表题（`表1 基于计数法的C-TIRADS` 前置） | 0.6169 | 0.5412 |
| pipe（转 Markdown 管道表） | 0.6077 | 0.5368 |
| pipe + 表题 | 0.6100 | 0.5426 |

**结论（反直觉，但这是实测）**：

1. **转成管道表反而降 1.6pp**（0.6241 → 0.6077）——`|` 和 `---` 是检索噪声。
2. **逐行转自然语言没有提升**（0.6184，仍在噪声内），虽然它的 min 最高。
3. **加表题没有提升**（0.6169），但**加表题不损害**，且对"人读得懂"有明确价值。
4. → 因此本轮的实现是：**整表成块 + 保留表题 + 转管道表（为了结构可读与可校验）**，
   并**明确记录**"管道化对向量相似度略负"这一实测事实，不宣称它提升了检索。

> 这与"表格切成可检索 chunk"的常见建议（表头重复到每一行）**没有矛盾**：
> 重复表头的目的是**行级切分**时保留语义；本轮选择**整表不切**，所以不需要重复表头。
> 若将来表超大（>1600 tok）需要行级切分，则应重复表头 —— 但本轮 186 个表格块里
> 没有触发这个上限。

|---|---:|---:|---:|---:|---:|---:|

### 10.4 变差的原因分析（可验证，不是辩解）

1. **块数膨胀 1.5–2 倍稀释 Top-k**：5279 vs 1297 个检索单元，同一 query 的 Top-10 里
   每个名额的"信息量"下降。Chroma 实测也显示小块的 Recall 靠更多块换来（§7.2）。
2. **父子块对 chunk 级指标无帮助**：父块回填是 **replace 内容、不换排名**（§3.3 的设计），
   所以 hit@k 只看 child 排名 → 父子块在这类指标上**结构性地不可能加分**。
   它的收益本应在生成侧，而生成侧本轮**没测**（§13）。
3. **块变小 → 金句更容易跨块边界**：金句命中要求整句落在**同一个** chunk；
   child 中位 346 tok 时，长金句（60–120 字）更易被切在两个块之间。这是**度量口径**
   对新方案不利的地方，但也是真实代价：向量检索按块打分，跨块信息本就难被完整召回。
4. **表格整表成块反而"稀释"**：一张 704 tok（最大 2423 tok）的表作为一个向量点，
   单点语义被压缩（正是 Late Chunking 论文 §4 指出的"语义过压缩"）。

> 因此 §3.3 里"父子块不破坏检索指标"的说法**被本轮实测推翻**：它确实不改变排名，
> 但**整体方案**（含结构细切）显著变差。已在 §9.2 更正。

### 10.5 决策

- **不切生产**：`RAG_KB_VERSION` 仍为 `kb_v1.4.0`。
- **开关收紧**：`rag_use_parent_expansion` 默认值改为 **`False`**
  （`app/config/settings.py:558`），字段注释写明"改默认值前必须先补出生成侧正收益证据"。
  这样即使有人误切到 `kb_v2.0.0`，也不会自动触发未验证的回填行为。
- **默认策略不变**：`init_knowledge_base.py --strategy` 默认仍是 `sentence_boundary`，
  `md_structure` 只是**可选**值。
- `kb_v2.0.0` 保留在库里作为实验对象（6477 块，含 1198 父块），可复查。
