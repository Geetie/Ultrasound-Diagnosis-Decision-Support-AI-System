# 更正：我此前关于「表格缺陷」的两处误判（2026-11-09）

> 触发：阶段1 Agent 反驳我的两条验证目标，我用 pymupdf 实测后确认**它是对的，我错了**。

## 误判 1：`TR2/TR3/TR4/TR5` 在 KB 里 0 条 ≠ 分块缺陷

**我说过的**：「`TR2/TR3/TR4/TR5` 在 KB 各 0 条 → 表格被切碎」（并把它列进 Agent 的验收目标）

**实测（pymupdf 扫 25 份源 PDF）**：
```
含 TR1-5 的文件：**0 个**
```
**C-TIRADS 2021 用的是中文分类**：`1 无结节 / 2 良性 / 3 良性可能 / 4A / 4B / 4C / 5 / 6`，
**根本没有 TR 编号**。`TR1–TR5` 是 ACR 体系的写法，本项目语料里不存在。

**所以**：
- 「TR 在 KB 里 >0」**不可能通过任何分块改造达成** —— 语料里没这个词
- 我把它列为 Agent 的验收目标，是**要求它去做一件做不到的事**
- 若要 TR 编号，必须**补 ACR TI-RADS 白皮书**这份新语料，不是分块问题

**我的错误根源**：我看到 prompt 里用 `TR2~TR5`、KB 里 0 条，就推断是分块丢了。
**没先验证「源语料里到底有没有这个词」。**

## 误判 2：`85%～100%` 0 条 ≠ 分块缺陷，是我的探测串写错

**我说过的**：「`85%～100%` 和 `50%～85%` 在 KB 里各 0 条 → PDF 的 `<br>` 切断数值」

**实测**：
| 字符串 | 源 PDF 出现次数 | KB 条数 |
|---|---|---|
| `85%~100%`（**半角 ~**） | 1 | **13** |
| `85%～100%`（全角 ～） | 0 | 0 |
| `50%~85%`（半角） | 1 | **13** |
| `50%～85%`（全角） | 0 | 0 |

**源文件用的是半角 `~`（U+007E），我探测时打的是全角 `～`（U+FF5E）。**
`85%~100%` 在 KB 里其实有 **13 条**，根本不是 0。

**所以**：「表格被 `<br>` 切断」这个结论**在这一条上不成立**。我用了错误的字符去匹配，
然后把自己的探测错误当成了系统缺陷。

**这是第二次同类错误**（第一次是 NDCG > 1，也是算法/实现错误被我当成数据问题）。

## 真正存在的表格缺陷（Agent 复现的，我核实）

### 真缺陷：orphan 表格 chunk
```
KB 里以 `|` 开头的 chunk: 40 个
其中 orphan（无 `|---` 表头分隔行、无表题）: **16 个**
```
典型如：
```
|DBP mmHg|77±7|75±6|76±6|77±7|78±7<sup>a</sup>|77±6<sup>a</sup>|78±8<sup>b</sup>
|LVESV ml|12 4|50 0|16 2|52 6|15 6|50 8|14 8|49 2|7 8|54 0|12 1|43 5|11 0|42 8|
```
**纯数字矩阵、无表头、无表题 → 零语义，检索必挂。**

### 另一个真缺陷：表格被拆碎
`TI-RADS` 在语料里提及 122 处，实际成表的只有 **38 个 chunk** —— 大量表被拆散。

### 反例：C-TIRADS 表 1 其实是完整的
```
KB: ctirads_2021_counting_table#0000（581 字符，我手工补的那份）
内容含: | 4A 低度可疑恶性 | / | | 2 | 10~50 | 4B 中度可疑恶性 | / | | 3~4 | 50~90 | 4C 高度可疑恶性 |
✅ 表完整
```

**Agent 的原话是**：「v1.4.0 里确有 `表1 基于计数法的C-TIRADS` 整表 chunk（921 字符，
含 `3~4|50~90|4C` 等全部行）→ **这张表其实是完整的**」

**也就是说：我此前以为"表被切碎所以手工补了一份"，但实际上它本来就在。** 我补的那份是冗余的
（虽然多了 `source_set` 元数据，不完全是浪费）。

## 我采纳 Agent 的验证口径

| 项 | 我的原口径 | 改为（Agent 的） | 理由 |
|---|---|---|---|
| A | `TR2-TR5` > 0 | **orphan 表格 chunk 12 → 0** | 前者语料里不存在，后者可机检 |
| B | — | **表头可检索**：用「表名+列名」作 query 命中该表 | 测真实的表可用性 |
| C | `85%～100%` > 0 | **按源字符原样** probe：`50~90` / `10~50` / `2~10` / `85%~100%` / `50%~85%` | 用对的字符 |
| D | B2 回归 | 同（p94b 基线 A1 dense hit@10=0.8718、融合1:2=0.9658） | 无异议 |

## 关于「要不要补 ACR TI-RADS 白皮书」

**我的决定：要补，但归到「语料补充」而不是「分块修复」。**

理由：
- 系统 prompt 与输出里用 `TR1~TR5`，但 KB 里没有这套编号的定义 → **模型只能靠 prompt 里的描述**
- 补 ACR TI-RADS 白皮书后，`TR` 编号才有可检索的权威定义
- 这与 C-TIRADS 并存，又是一个「两套体系」——正好用上我们刚设计的 `source_set` 机制

## 教训（第三次同类）

| 次 | 错误 | 我以为是 | 实际是 |
|---|---|---|---|
| 1 | NDCG 算出 >1 | 数据问题 | 我的算法错 |
| 2 | 97.43% 泄漏 | 模型能力 | 我搞错了权重来源 |
| 3 | **`85%～100%` 0 条 / TR 0 条** | **分块缺陷** | **我打的探测串用错字符 + 语料里本没这词** |

**共同点：在不该省的地方省了验证。** 这次两处都只要 "先看源文件里到底有什么" 就能避免。

**新增纪律**：
- 报「X 在 KB 里 0 条」之前，**必须先确认 X 在源语料里存在**，且**用源文件里的原字符**探测
- 要求别人达成的验收目标，先自己验证一遍是否可达
