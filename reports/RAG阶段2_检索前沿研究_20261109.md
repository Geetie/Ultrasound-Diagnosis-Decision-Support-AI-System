## 1. 学习报告：每篇文献的核心结论 + 可落地参数

完整引文与逐条 URL 见两份子报告（均已落盘）：

### 1.1 BM25 与稀疏检索

**结论**：BM25 的价值不在"语义"，在**精确词面匹配**——缩写、编号、分级符号（`LR-5`、`TR4a`、`4A类`）。dense 模型把这些当成普通 token 的语义，容易糊。

**本项目实测的反证（重要）**：bge-m3 官方 MIRACL-zh 数字（论文 Table 1）：

| 模式 | Avg | **zh** |
|---|---|---|
| Dense | 69.2 | **62.7** |
| Sparse | 53.9 | **36.1** |
| Multi-vec | 70.5 | 63.7 |
| Dense+Sparse | 70.4 | 63.5 |
| All | 71.5 | **64.9** |

**中文上 sparse 比 dense 低 26.6 分**，Dense+Sparse 甚至略低于 Multi-vec。
这与"医学查询该给 BM25 更高权重"的直觉**冲突**，也正是本轮 `1:2` 权重需要重新检验的原因（见 §3.2）。

**可落地参数**：
- `rag_rrf_k = 60` —— Cormack 原文："k = 60 was fixed during a pilot investigation and not altered during subsequent validation"，且"the choice was not critical"。**保持 60，不用调**。
- 权重不要凭直觉定，按 §3.2 的实测走。

### 1.2 RRF（Cormack et al., SIGIR'09）

**公式**：`RRFscore(d) = Σ_{r∈R} 1/(k + r(d))`，k=60。

**核心结论**：RRF 在 TREC 上比 Condorcet Fuse 好 7/7 次（p≈0.008）、比 CombMNZ 好 6/7 次（p≈0.04）、比最好的单系统好 6~7 次（0.008≤p≤0.04）。平均比三者好 **4%~5%**。

**关键设计意图**（常被忽略）：原文明确说 k 的作用是"**mitigates the impact of high rankings by outlier systems**" —— 即 RRF 是**抗单腿异常**的，不是"精细调权"的工具。给某一腿加权重（本项目 1:2）**在原理上削弱了它的鲁棒性设计**，只有在"确实系统性偏向某一腿"时才有理据。

**可落地参数**：加权 RRF `Σ w_leg/(k+rank)` 是本项目已有实现（`retriever.py::_rrf_fuse`），保持 k=60；`w` 必须逐数据集实测，不能跨语料沿用。

### 1.3 ColBERT / ColBERTv2 / PLAID（late interaction）

**为什么比单向量强**：单向量把文档压成 1 个点，多向量按**每个 token** 建表示，相关性建模分解成 token 级计算（"late interaction"）——这正是术语密集文本最吃的部分（`4A类` vs `4B类` 只差一个 token，单向量容易抹平）。

**代价**（ColBERTv2 原文）："it inflates the space footprint of these models by an order of magnitude"，ColBERTv2 做到"reducing the space footprint by 6–10×"，但**仍然比单向量大**。PLAID 是专门的检索引擎（"Performance-optimized…"），要引入新基础设施。

**值不值得上（本项目 3745 chunks）—— 结论：不值得，理由不是成本而是天花板**

一阶段召回实测（bge-m3 + BM25 融合，depth 80）：

| Recall@10 | Recall@20 | Recall@30 | Recall@50 | Recall@80 |
|---|---|---|---|---|
| 0.9145 (107/117) | **0.9573 (112/117)** | 0.9573 | 0.9573 | 0.9744 (114/117) |

**Recall@20 已是 95.73%**。`Recall Ceiling`（arXiv 2609.27953）给出的上界关系是
`E[NDCG@k] ≤ Recall@|W|`。要上 ColBERT 的全部收益，上限只有 **+4.3pt（112→117 中的 5 条）**，
而且这 5 条里有 2 条即使 depth 80 也捞不到（Recall@80 也只有 114/117）。
**投入一套新索引引擎去抢 ≤4.3pt 的天花板，ROI 明显不如"把已有召回的排序做好"**（§3.3 的 96 行代码就拿到 +12pt）。

### 1.4 HyDE

**结论**：用 LLM 生成"假想文档"再嵌入检索，把 query→doc 相似度换成 doc→doc 相似度。原文："the generated document is not real, can contain factual errors but is like a relevant document"，靠 encoder 的"dense bottleneck to serve a lossy compressor"过滤幻觉细节。

**什么场景有效**：**零样本、无相关性标注、弱检索器**。原文 Table 4：

| 生成模型 | Contriever（未微调）DL19/DL20 | ContrieverFT（已微调）DL19/DL20 |
|---|---|---|
| 无 HyDE | 44.5 / 42.1 | **62.1 / 63.2** |
| +FLAN-T5 11b | 48.9 / 52.9 | 60.2 / 62.1（**↓**） |
| +GPT 175b | 61.3 / 57.9 | 67.4 / 63.5 |

**什么场景无效 —— 原文自己写的**：
> "less powerful instruction LMs can **negatively impact** the overall performance of the fine-tuned retriever."

**对本项目的判定：不做。** bge-m3 是在中文医疗语料上训过的强编码器（相当于 HyDE 表里的 ContrieverFT 列），
HyDE 在这列上要靠 175B 模型才转正，而本项目的生成侧是 Qwen2.5-7B。**收益预期为负，且要付一次 LLM 调用延迟。**

### 1.5 查询扩展的实证：**这是本轮最需要纠正引用的一节**

任务书要求「搜 "query expansion hurts retrieval" 的反面证据」。实际上**文献支持的正是"QE 有害"这一面，但引文要引对**：

| 常被引的文献 | 真实主张 | 能不能用来支持"QE 有害" |
|---|---|---|
| Billerbeck & Zobel, ADC 2004 | "these parameters **may not be generally applicable**, and more significantly that the assumption that the same parameter settings can be used for all queries is **invalid**" | ❌ **不能**。它讲的是**固定参数不泛化 + 需 per-query 自适应**，不是"QE 有害" |
| Carpineto & Romano, CSUR 2012 | 摘要**完全不谈**"何时降效"（全文付费墙） | ❌ **不能**（NOT VERIFIED） |
| **Cronen-Townsend et al., ECIR 2004** | "It is a well known fact that Query Expansion (QE) **increases global MAP but hurts the performance on the worst topics**." | ✅ **这才是该引的** |

**真正解释本项目失败的是 Query2doc 自己的表**（arXiv 2303.07678 全文可读）：

> "the gain brought by query2doc **tends to diminish when using** intermediate pre-training or **knowledge distillation from cross-encoder re-rankers**"

| 基座 | NFCorpus | Scifact |
|---|---|---|
| SimLM + query2doc | 32.7 → 32.1（**−0.6**） | 62.4 → 59.5（**−2.9**） |
| E5base+KD + query2doc | — | 70.4 → 67.5（**−2.9**） |
| **BM25 + query2doc** | **全部为正**（+2.1~+6.6） | |

**边界条件清楚了**：QE 的收益**集中在弱检索器（BM25）**；**越强的 dense retriever 越吃不到，还可能倒退**。
bge-m3 属于强模型 → **本项目 QE 负增益是文献可预期的结果，不是实现 bug**。

**可落地参数（如果还要做）**：只在裸缩写且无全称时展开、扩展词限 1~3 个、**且必须过 IDF 阈值卡掉泛词**。
本轮的实现与实测见 §3.4 —— **条件化后仍为负，建议不做**。

### 1.6 Reranker 研究

#### 精排在什么条件下有效

1. **一阶段召回还没饱和**（上界 `E[NDCG@k] ≤ Recall@|W|`）
2. **重排深度小**。`Drowning in Documents`（arXiv 2411.11767）原文：
   > "In the majority of cases, reranking a small set of documents, **e.g. less than 100**, is an effective way to improve recall... as we increase k further **beyond 100**, the rerankers' Recall@10 **dramatically decreases**... for many rerankers, performance at large k is **worse than that of the neural retrievers**."
3. **领域匹配**。MedCPT（领域专门）Hit@10 **46.6%→60.6%（+14.0）**；
   而通用 reranker 在中文医学上是负/零（见下"负增益"）。

#### 精排在什么条件下是负增益

**最硬的证据是厂商自己的表**。BAAI 官方 C-MTEB 里 `bge-reranker-v2-m3` 相对一阶段 `bge-zh-v1.5-large` 的逐任务 Δ：

| 任务 | Δ nDCG@10 |
|---|---|
| avg | +1.36 |
| CovidRetrieval | **+15.98** |
| MMarco / Du | +4.62 / +3.29 |
| T2 | +0.58 |
| **CmedqaRetrieval** | **−3.80** |
| **MedicalRetrieval** | **−0.07** |
| **EcomRetrieval** | **−2.28** |
| **VideoRetrieval** | **−7.42** |

**同一模型、同一张官方表，正负号都有。** 这就是"精排不是全局开或全局关"的直接依据。

BEIR 官方（arXiv 2104.08663）同样：BM25+CE 平均 +11%，但 **ArguAna 0.311 < BM25 0.315**、**Touché-2020 0.271 < BM25 0.367（−9.6）**；延迟 **450ms GPU / 6100ms CPU** vs BM25 20ms（**22×**）。

#### monoT5（Nogueira et al., Findings of EMNLP 2020）

- 输出必须是单 token 的 `true`/`false`，否则"retrieval metrics were **close to zero**"（实现高频坑）
- 深度：**top-1000**
- MS MARCO MRR@10：BM25 .184 / +BERT-large .372 / +T5-large **.383**
- 数据效率："T5 is able to achieve roughly **45% of the possible gain** over BM25 with only **4% of the training data**" —— **对小样本微调有参考价值**
- 训练成本：T5 base/large/3B ≈ **12/48/160 小时单 TPU**

#### 本项目精排为什么负增益 —— 三个假设，逐个验证

**假设 A：模型不对（通用模型不懂中文超声术语）→ ❌ 证伪**

如果术语不懂，那"含术语的自然语言问句"也该打低分。实测（同一 gold 文档、只改查询写法）：

| 查询形态 | bge-reranker-base | bge-reranker-v2-m3 |
|---|---|---|
| B2 原始查询（术语堆叠） | **1.7471** | **−0.0450** |
| 同样内容改成自然语言问句 | **8.6406** | **6.5469** |
| 只有关键词 | 8.0781 | 6.2656 |
| 无关查询（对照） | −10.0625 | −11.0312 |

**base 对纯中文医学问句打 8.64**，说明术语是认识的。**假设 A 证伪。**

**假设 B：查询串被污染（查询形态错配）→ ⚠️ 部分成立，但不是主因**

上表里**查询形态一项就占 6.9 分**，而相关/无关的整个间隔才 12.7~13.2 分 —— 形态敏感性确实极大。
B2 的查询全是"影像征象堆叠 + 怎么分级"的考试式问法（`authored_by=manual`），与精排训练分布里的自然语言问句严重错配。

于是做了一个**只规约句式、不动术语**的对照臂（`--rerank-query-rewrite`：砍设问尾巴、逗号换空格、补"有哪些要点"）：

| 臂 | hit@1 | hit@5 | hit@10 |
|---|---|---|---|
| 融合基线 | 0.6154 | 0.7863 | 0.8462 |
| + base@20（原查询） | 0.5385（**−7.7**） | 0.7350 | 0.8205 |
| + base@20（**+查询规约**） | 0.5641（**−5.1**） | 0.7265 | 0.8034 |
| + v2m3@20（原查询） | 0.6752（**+6.0**） | 0.8547 | 0.8803 |
| + v2m3@20（**+查询规约**） | 0.6923（**+7.7**） | 0.8120 | 0.8889 |

查规约对 base 只是把 −7.7 救到 −5.1（**仍为负**），对 v2m3 是 +6.0→+7.7（小幅正贡献）。
**假设 B 部分成立：形态错配是真的，但单独修它救不回来。**

**假设 C：模型确实是错的（决定性）→ ✅ 成立**

同样的召回、同样的查询、同样的深度，只换模型：

| 臂（融合 1:2，depth 20） | hit@1 | hit@5 | hit@10 | MRR | NDCG |
|---|---|---|---|---|---|
| 不精排（基线） | 0.6154 | 0.7778 | 0.8120 | 0.6878 | 0.6916 |
| **+ bge-reranker-base** | 0.5470（**−6.8**） | 0.7179（**−6.0**） | 0.8034（−0.9） | 0.6020（−8.6） | 0.6130（**−7.9**） |
| **+ bge-reranker-v2-m3** | **0.7009（+8.6）** | **0.8291（+5.1）** | 0.8547（+4.3） | **0.7371（+4.9）** | **0.7285（+3.7）** |

**base 的 NDCG 掉 7.9pt 且 95%CI 全程为负（[−0.1445, −0.0151]）**，是真负增益；
v2m3 五项指标全正。**根因是模型，不是查询、不是深度。**

**假设 D：深度不对 → ❌ 证伪（加深更好，不是更差）**

| 臂（纯 dense 基座） | hit@1 | hit@5 | hit@10 |
|---|---|---|---|
| v2m3 @depth 10 | 0.6667 | 0.8291 | 0.8462 |
| v2m3 @depth 20 | 0.6838 | 0.8718 | 0.8718 |
| v2m3 @depth 40 | **0.6923** | **0.9145** | **0.9231** |

**深度 10→40 单调变好**。这与 `Drowning in Documents` 一致（拐点在 100 之后，本项目远未到）。
**上一轮"depth 20 > 50 > 100 越来越差"的结论，是 base 模型的问题被误读成了深度问题。**

### 1.8 MTEB / BEIR：中文医疗该看哪个子榜

**先说一个事实纠正**：C-MTEB 的中文 retrieval 是 **8 个任务**，不是少数几个：

`T2Retrieval`、`MMarcoRetrieval`、`DuRetrieval`、`CovidRetrieval`、**`CmedqaRetrieval`**、`EcomRetrieval`、**`MedicalRetrieval`**、`VideoRetrieval`

**医疗相关的是 `CmedqaRetrieval` + `MedicalRetrieval` 两个。**

**但这两个都别用来看本项目**，原因是分布不匹配 —— 官方 prompt 逐字：

- `CmedqaRetrieval`: "Given a Chinese community medical question, retrieve **replies** that best answer the question"
- `MedicalRetrieval`: "Given a medical question, retrieve **user replies** that best answer the question"

**语料是"医患问答"，本项目的语料是"指南 prose"。** 拿它选型是外推。

**另外两条必须知道的**：
1. **医疗是 C-MTEB 全表最弱项**。bge-large-zh 逐项 NDCG@10：T2Retrieval 84.82 / DuRetrieval 86.94 / **CmedqaRetrieval 42.40** / MedicalRetrieval 59.39 → Avg 71.53。**看 Avg 会严重高估医疗表现，要看医疗两列。**
2. **bge-m3 官方从不报告 C-MTEB 分数**（model card 与 arXiv 2402.03216 全文 grep `C-MTEB` 零命中，官方榜单也无 bge-m3 行）。任何给你 bge-m3 的 C-MTEB 数字的来源都可疑。

**结论：中文医疗检索没有现成可用的子榜。** 唯一可信的选型依据是**自建域内 golden set**（本项目 B2，n=117）。

### 1.9 元数据过滤：pre-filter vs post-filter

**先纠正一处归属**：本项目文档曾说"Qdrant 解释 post-filter 静默丢结果"。
Qdrant 官方 `concepts/indexing` 与 `concepts/filtering` 两页 grep `post-filter` **命中 0**。
清晰表述来自 **Weaviate**：

> "If the filter is very restrictive... there is a chance that the original vector search **does not contain any match at all**."
> "You cannot easily predict how many elements will be contained in the search"

**Qdrant 讲的是同一机制的另一角度，但有硬数据**（`hnsw_ef=64`，Recall@10）：

| 过滤选择性 | Plain graph | Filterable HNSW | Planner+ACORN |
|---|---|---|---|
| 单关键词 20% | 62.9% | 94.8% | 100% |
| 单关键词 10% | 20.6% | 99.0% | 99.9% |
| **单关键词 1%** | **0.1%** | 99.8% | 100% |
| **双关键词 0.012%** | 0.6% | 1.8% | **100%** |

最该记住的官方原话：
> "one filter returned **39.7%** with ACORN off while every other filter stayed above 90%, **and a single aggregate number would have hidden it**"

**⚠️ Qdrant 的 selectivity 用词与业界相反**：它写 "high-selectivity (weak)" = 命中多；"low-selectivity (strict)" = 命中少。
定义是 "Selectivity is the fraction of points that **pass** the filter"。**照字面读会把策略搞反。**

**对本项目的判定**：3745 chunks ≈ 15.3 MB（1024 维 float32）**根本不需要 ANN**。
暴力精确内积 ~7 亿次乘加，单核毫秒级。**pre-filter 精确筛候选 → 精确打分**可以从工程上消除"过滤静默丢结果"，
不是靠调参。本轮不动（属架构级改动），记入建议。

### 1.10 检索评估：NDCG 的正确算法

**本项目曾算出 NDCG > 1**（30/115 条越界，最高 1.6309），根因：
旧实现按**命中次数**累加 DCG，而 IDCG 按 `min(|gold|, k)` 算。多版本副本让同一 gold 在 ranking 里出现 2~3 次
→ DCG 项数 > IDCG 项数 → NDCG > 1。

**正确做法**（本轮 `p200_prod_ab.py::ndcg_at_k` 实现）：

```python
dcg = 0.0; seen = set()
for rank, cid in enumerate(ranking[:k], start=1):
    if cid in gold and cid not in seen:      # ← 每个 gold 只计一次
        seen.add(cid)
        dcg += 1.0 / math.log2(rank + 1)
n_ideal = min(len(gold), k)
idcg = sum(1.0 / math.log2(r + 1) for r in range(1, n_ideal + 1))
return min(1.0, dcg / idcg) if idcg else 0.0   # ← clamp
```

**本轮全部 14 个臂的 NDCG 越界条数 = 0/117。**（脚本内置 `ndcg_overflow` 计数，非 0 会打印）

### 1.11 医疗领域检索的特殊性

TREC 2011 Medical Records Track 官方失败分析（AMIA 2012，PMC 全文可读）：

- 最好的 bpref 也只有 **0.5–0.6**，"not satisfactory for identifying patients in a set of clinical records"
- "**terminology differences, negation, and time aspects** having the most impact on retrieval inaccuracy"
- 同义词是头号召回杀手："A search for patients with hearing loss tended to overlook visits mentioning **deafness** or **hearing aids**"
- **否定**："patients with hearing loss included many that noted the 'patient **denies** hearing loss'"
- **QE 直接致假阳性**："It is likely that systems were performing query expansion, or some other statistical IR approach that **introduced semantic error**"

**对超声的直接映射**：`未见`、`排除`、`不除外` 高频 → 纯向量分不清「有/无」。
**这是换 embedding 解决不了的**，必须结构化拦截（极性识别）。记入建议，本轮不做（超出检索层范围）。

**领域专用 embedding 是否更好 —— 证据是矛盾的，如实报告**：
- 反例（更贴近真实 EHR）：arXiv 2409.15163 实测 7 模型 × 2 数据源 × 3 任务指出
  "BGE, a comparatively small general-domain model, consistently outperforming all others, **including medical-specific models**"
- 支持方：DR.EHR（arXiv 2507.18583）
- **可验证的共识只有一条：公开榜单不可外推，必须自建 golden set 实测。**

### 3.1 项 1：验证 dense 腿真的在工作 —— ✅ 已验，**前提是错的**

见 §0 第 1 条。附带发现一个**真实的、更严重的问题**：

**dense 腿只回 10.78/20 条。** 逐级测：

| 请求 top_k | 实际返回 | 损失 |
|---|---|---|
| 20 | **10.78** | **−46.1%** |
| 40 | 22.22 | −44.5% |
| 80 | 46.29 | −42.1% |

**根因**（真机日志实证）：`_wrap_search_results` 里的逻辑 chunk 去重是在**取回 `top_k` 之后**做的：

```
retrieval_logical_chunk_deduped after=10 before=20 collapsed=10 source=dense
retrieval_logical_chunk_deduped after=58 before=80 collapsed=22 source=dense
retrieval_logical_chunk_deduped after=40 before=80 collapsed=40 source=dense
```

多版本副本占了请求位的 ~45%，去重把它们折叠掉之后**不会补召回**，空出的位就浪费了。

#### 但这个缺陷「修了几乎没用」—— 我做了 A/B，如实报告

候选修复：向向量库请求 `top_k × M`（M=2,3），去重后再截断到 `top_k`。生产 `Retriever` 实测：

| 基座 | 请求倍率 | hit@1 | hit@5 | hit@10 | MRR | NDCG | 平均返回条数 |
|---|---|---|---|---|---|---|---|
| 纯 dense | ×1（现状） | 0.5726 | 0.8034 | 0.8718 | 0.6709 | 0.6963 | **10.8** |
| 纯 dense | ×2 | 0.5726 | 0.8034 | 0.8718 | 0.6709 | 0.6963 | **20.0** |
| 纯 dense | ×3 | 0.5726 | 0.8034 | 0.8718 | 0.6709 | 0.6963 | 20.0 |
| 融合 1:2 | ×1（现状） | 0.6154 | 0.8462 | 0.8803 | 0.7066 | 0.7260 | **6.2** |
| 融合 1:2 | ×2 | 0.6154 | 0.8462 | 0.9145 | 0.7178 | 0.7438 | 12.0 |
| 融合 1:2 | ×3 | 0.6239 | 0.8718 | **0.9231** | 0.7230 | 0.7488 | 17.4 |

配对检验（×2 vs ×1）：纯 dense 的 hit@5 / hit@10 **变好 0 / 变差 0，p=1.0000**；
融合的 hit@10 变好 4 / 变差 0，**p=0.1250（不显著）**。

**结论（与本报告初稿的预判相反，如实更正）**：
- 多取能把**召回条数补满**（dense 10.8→20，融合 6.2→17.4）—— 这部分是真的
- 但**排名质量几乎不变**：纯 dense 五项指标**逐位相同**，说明重复副本**并没有占据 top-10**
  （去重默认已开，top-10 里本来就没有重复），它们只占据 **top-10 之后**的位置
- 融合基座上 hit@10 +4.3pt，但 **p=0.125 判不动**

**判定：这是"配额没填满"的问题，不是"排序变差"的问题。**
量级远小于「+45% 召回位」这个数字给人的印象 —— **补满配额不会自动变成指标提升**。

**对 `settings.py` 那条注释的更正**：它说"实测 B2 前 10 名里 56.5%（113/200）的位置被重复副本占据"。
那是**去重默认开启之前**的测量。去重上线后，top-10 已无重复（本轮 ×1/×2/×3 三档 hit@k 逐位一致即为证据）。
**该注释描述的是一个已被修掉的状态，不是现状。**

### 3.3 项 4：上下文扩展（取相邻 chunk）—— ⚠️ **口径决定结论，如实报两遍**

知识库实测：`chunk_type` 全是 `child`（9568 条），`parent_chunk_id` **全为 NULL**（0/9571）。
`chunk_id` 形态 `{kb_version}:{source_doc_id}#{chunk_index:04d}` → **只能用 `chunk_index ± 1` 做邻居**，
没有现成的父块可用。

#### 口径 A：把邻居插进排名（❌ 表面上是灾难）

| 臂 | hit@1 | hit@5 | hit@10 | MRR | NDCG |
|---|---|---|---|---|---|
| 基线（top-10） | 0.6154 | 0.7778 | 0.8120 | 0.6878 | 0.6916 |
| + 邻居 ±1 插入 | **0.4017** | 0.7778 | 0.8291 | 0.5751 | 0.6190 |
| + 邻居 ±2 插入 | 0.3932 | 0.7778 | 0.8291 | 0.5595 | 0.6054 |

邻 ±1 vs 基线：hit@1 **变好 3 / 变差 28，p<0.0001**。

**但这不是"上下文扩展有害"** —— 是我用错了度量。把邻居插进排名，等于把真正的命中往下挤，
hit@1 必然崩。**上下文扩展的目的不是提高 hit@k，是给 LLM 更多正文。**

#### 口径 B：邻居带来的**净增召回**（✅ 正确度量）

| top-K | 直接命中 | 含 ±1 邻居后命中 | **净增召回** |
|---|---|---|---|
| 5 | 85/117 = 0.7265 | 90/117 = 0.7692 | **+5 条（+4.3pt）** |
| 10 | 91/117 = 0.7778 | 95/117 = 0.8120 | **+4 条（+3.4pt）** |
| 20 | 103/117 = 0.8803 | 104/117 = 0.8889 | **+1 条（+0.9pt）** |

**判定：净增召回 +0.9~+4.3pt，且随深度增加递减（深度越深，邻居能补的越少）。**
这是**真实但小**的收益，而且**不能体现在 hit@k 里** —— 它的价值在于 prompt 里的正文更完整。

**落地建议（本轮不上线）**：把邻居**追加在 top-k 之后**（像 `_expand_graph_neighbors` 那样不挤占排名），
`top_k + n_neighbors` 一起进 prompt。这样 hit@k 不变（不伤害排名），正文变全。
**代价是 prompt 变长约 2~3 倍，需先测生成侧是否吃得下。**

### 3.4 项 3：查询扩展条件化 —— ❌ **仍然无效，建议不做**

#### 实现（按文献边界条件收紧）

三处收紧，全部有文献依据：
1. **只扩裸缩写**：查询里必须有 ASCII 缩写**且**没给出对应中文全称（对应 `Cronen-Townsend`"伤最差 topics" + 避免无谓改动）
2. **丢泛词**：黑名单 `造影剂/分级/类/超声造影/剪切波…`（本项目实测这些词跨器官高频，会拉偏查询向量中心）
3. **限词数**：每查询最多 3 个扩展词（原实现是 12）

触发面从 **40/117 降到 16/117**。

#### 结果

| 臂（融合 1:2，depth20） | hit@1 | hit@5 | hit@10 | MRR | NDCG |
|---|---|---|---|---|---|
| 基线 | **0.6154** | 0.7778 | 0.8120 | **0.6878** | **0.6916** |

| **条件化扩展（新）** | 0.5983（−1.7） | 0.7863 | **0.8205（+0.9）** | 0.6774 | 0.6775 |

配对检验：
- 全量扩展 vs 基线 hit@1：变好 1 / 变差 6，**p=0.125**
- 条件化扩展 vs 基线 hit@1：变好 3 / 变差 5，**p=0.727**

**判定：条件化把 −4.3pt 收敛到 −1.7pt（改善 2.6pt），但方向仍是负的，且 p=0.727 判不动。**
唯一稳定为正的是 hit@10（+0.9pt）。**建议不做。**

#### 为什么连"最该受益"的裸缩写子集也救不回来

与 Query2doc 的表完全吻合：**bge-m3 是强 dense retriever，QE 的收益集中在小模型/BM25 上。**
本项目同时又有一条 BM25 腿（`1:2` 权重）—— 缩写的中文全称**本来就已经由 BM25 腿负责匹配**，
再往查询里塞一遍中文全称是**重复劳动 + 稀释 dense 向量**。

**这也解释了阶段 1 的一个反常现象**：`TR1~TR5` 的映射实测"3 正 1 负"。
正的那 3 条，大概率是 BM25 腿吃到了；负的那 1 条是 dense 被拉偏。

| 2c | 精排 + 查询规约 | ⚠️ 小幅正 | base −6.8→−5.1（仍负）；v2m3 +6.0→+7.7 | 判不动 | 与 2 一起上，单独看不出 |
| 3 | 查询扩展（条件化） | ❌ **仍无效** | hit@1 **−1.7pt**（原 −4.3） | p=0.727 判不动 | ❌ **不上** |
| 4 | 上下文扩展（插排名） | ❌ **度量错误** | hit@1 −21.4pt | p<0.0001 | ❌ **不要这样用** |
| 4b | 上下文扩展（净增召回） | ⚠️ 真实但小 | **+0.9~+4.3pt**，随深度递减 | 未做检验 | 可上，但**追加在 top-k 之后** |
| 5 | `source_set` 过滤 | ✅ 已接线 | 语料里 0 条该字段 | — | 等语料侧落字段 |
| 6 | ColBERT 类 | ❌ **不值得** | 天花板仅 **+4.3pt**（Recall@20=95.73%） | — | ❌ 不上 |
| 7 | HyDE | ❌ 预期为负 | 文献：弱编码器才有效；bge-m3 是强编码器 | — | ❌ 不上 |
| 8 | 图检索扩边 | ❌ 已有 NO_GO | A.65：召回 0.9853→0.9853（零增益） | — | ❌ 不重开 |

### 一句话总结

**本轮唯一确定有效的是「换精排模型」（+12pt hit@1，三项指标 p<0.05）。
其余全部无效或不可判定：查询扩展条件化后仍为负；上下文扩展的价值只在"正文完整性"不在 hit@k；
"多取后去重"能补满配额但排名质量逐位不变；ColBERT/HyDE 天花板太低不值得上。

最有价值的产出不是任何一项改造，是**推翻了三条既有认知**：
①「集合名 404 导致 dense 腿空转」是假的（Qdrant 自动加前缀，两种写法结果逐位相同）；
②「精排在本项目必然负增益」是假的（换 v2-m3 后 +12.0pt，三项指标 p<0.05）；
③「重复副本占了 56.5% 的 Top-10」是**去重上线前**的旧测量，拿它排优先级会排错。

## 5. 必须承认的不确定性

1. **融合 + 精排 不如 纯 dense + 精排**（hit@5 差 10.3pt）。这个方向性结果目前**没有解释清楚**，
   §3.2.3 给的是假设不是结论。**在弄清之前，不要同时上线"融合权重调整"和"精排"**。
2. **n=117 判不动 ≤5pt**。v2m3 在**融合基座**上 hit@1 的 p=0.0755（不显著），
   只有**纯 dense 基座**上的 +12.0pt 才过线（p=0.0201）。别把两个数字混着报。
3. **`rag_collection` 改名的价值是"可读性"，不是修 bug**。若有人据此得出
   "dense 腿修好后指标会变"，那是错的 —— 本轮已证两种写法结果逐位相同。
4. **上下文扩展的净增召回没做显著性检验**（+4 条在 n=117 上本来也检不出）。
5. **本轮所有数字都绑定 `kb_v1.5.0`（3745 chunks）**。语料仍在增长，换版本必须重测。
6. **代码快照冻结于 11:34:57**。此前 11:24~11:29 跑的 4 个臂（A/B/C/D）用的是**旧 settings**
   （无 `rag_rrf_w_dense`），已作废不引用；本文所有数字均来自冻结快照。

## 6. 建议下一步（按 ROI 排序）

### 6.1 【中，不是最高】修「多取后去重」—— 已 A/B，收益远小于预期

`top_k` 传 `top_k × 2`，去重后再截断到 `top_k`。**已在 §3.1 做过 A/B**：

- 纯 dense：配额 10.8→20 **补满**，但 hit@1/5/10/MRR/NDCG **五项逐位不变**
- 融合：配额 6.2→17.4，hit@10 +4.3pt，**p=0.125 判不动**

**判定：做了不吃亏（配额满 = prompt 正文更多），但别指望指标。降为「中」。**
真正的教训是：**"重复副本占据 Top-10"是去重上线前的旧测量，不是现状** —— 别再拿那个数字做决策。

### 6.2 【高】定「融合 vs 纯 dense」在精排接管后的定位

同时上线融合权重和精排会互相抵消（§3.2.3）。做 2×2：`{融合, 纯dense} × {v2m3@20, v2m3@40}`，
**在冻结快照上跑，一次定死。** 在出来之前**不要拍板权重**。

### 6.3 【高】精排上线的工程细节

- 8007 端口服务化（本轮是临时进程），加进 `server_start_embedding_services.sh`
- 显存：v2-m3 fp16 约 **4.5 GB**（2.27GB 权重 × 2）。当前 GPU 已占 44.9/49.1 GB，
  **上线前必须核对显存预算**（或与 8003/8004 串行调度）
- 延迟：v2m3@40 单查询约 **370ms**（117 条 44s）。相对 bge-m3 嵌入的 50ms 是 **7×**，
  需评估是否只在 `full` 档启用

### 6.4 【中】上下文扩展按正确姿势接

追加在 top-k 之后（`top_k + 2~4` 条邻居），不改排名。**先测 prompt 长度对生成侧的影响。**

### 6.5 【中】`source_set` 端到端联调

等语料 Agent 落字段后，用真机查一条 `source_set` 过滤，确认 dense+sparse 两腿都生效；
同时钉住"PGVector 后端多值恒 0 命中"的 warning 不被删掉。

### 6.6 【中】补 NDCG / 指标单测

本轮 `ndcg_at_k` 的去重 + clamp 逻辑应进 `tests/unit/`，并把"NDCG>1"做成断言而非人工排查。
**这个 bug 不该有第二次。**

### 6.7 【低但必须做】更正 3 处文档错误

1. `settings.py:470-479` 的"生产一直用默认值 → dense 腿查 404 集合" —— 事实错误
2. `98e59fa` commit message 里的因果链 —— 事实错误
3. 任何引用 **CMedRAG** 的地方 —— 该文献不存在（arXiv/PubMed/Crossref 三源均 0）

### 6.8 【不建议做】

- ColBERT / PLAID：天花板 +4.3pt，要引入新索引引擎
- HyDE：强编码器上预期为负，且多一次 LLM 调用
- 继续调查询扩展：两轮负增益，文献也支持"强 retriever 上无效"
- 换更大的精排模型：当前瓶颈已不是排序（Recall@20=95.73%，hit@10 已到 0.9231，
  距天花板 0.9573 只剩 3.4pt）
