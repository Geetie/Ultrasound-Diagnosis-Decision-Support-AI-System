# context_recall 实现与首轮实测：暴露了 hit@k 测不到的问题

> 日期：2026-11-09｜目标交付项 4：能测 context_recall

## 一、为什么要它（与本轮实测印证）

`hit@k` 只回答「找到答案所在的 chunk 没有」。
**检索质量的另一半是「找到的内容够不够答完」**，这要 `context_recall`。

**本轮实测印证了这个区分有意义**：

| 指标 | 值 | 含义 |
|---|---|---|
| **context_recall** | **0.4414** | 检索到的 10 块，只覆盖了参考答案的 **44%** |
| **context_precision** | **0.3189** | 10 块里只有 **32%** 含答案要素 |

**换句话说：即使 top-10 里有一块对，剩下 9 块大部分是噪声，而且答案还缺一半。**

## 二、实现（`p123_context_recall.py`）

Ragas 的 `context_recall` = 「参考答案的每个句子能否由检索上下文推出」。
官方实现用 LLM 判定；本项目折中：

| 口径 | 实现 | 特点 |
|---|---|---|
| **字面覆盖（默认）** | 参考答案切句 → 每句抽关键单元 → 看是否出现在上下文 | 便宜、可复现、**会低估** |
| LLM 判定（可选） | 逐句问模型 | 准、贵 |

## 三、首轮实现的一个真实 bug（必须记）

### 症状
```
context_recall    = 0.1194
context_precision = 0.9324   ← 两个数互相矛盾
```

**93% 的块都"有用"，为什么只覆盖 12% 的答案？**

### 根因
知识库原文**中英混排**（LI-RADS 原文就是英文），而我的「关键单元」里包含
**中文实词二元组**：

```
答案：「即使是小结节（如 CEUS LR-M 特征）…」
二元组：即使 / 是小 / 小结 / 结节 …
上下文（英文）：'CEUS LR-M criteria – any of following: rim APHE OR early (<60s) washout'
→ 「即使」「是小」当然找不到 → 每句都判"未覆盖"
```

### 修法
| 保留 | 去掉 |
|---|---|
| 数值+单位（`>15mm` / `<2%`） | ~~中文二元组~~ |
| 分级码（`CEUS LR-M` / `TR4`） | |
| **英文术语**（`CEUS` / `APHE` / `washout`）— 新增，跨语言强锚点 | |

### 修正效果
```
context_recall:    0.1194 → 0.4414  (+32pt)
context_precision: 0.9324 → 0.3189  (-61pt)
```

**两个数现在都合理了**，且 precision 的下降证明之前的 0.93 是虚高
（中文二元组把几乎所有块都算成"有用"）。

## 四、按格子的 recall（暴露的差异）

| 格子 | recall | n |
|---|---|---|
| multi/abstract/qa/medium | **1.000** | 2 |
| multi/abstract/attending/short | 0.833 | 2 |
| multi/abstract/attending/long | 0.500 | 2 |
| multi/abstract/resident/medium | 0.333 | 2 |
| multi/abstract/qa/long | 0.250 | 2 |

**qa（医务处）的问题覆盖最好，resident（住院医师）最差** ——
因为 qa 的问题偏"两套指南对比"，答案短且结构化；resident 的问题需要具体征象+计分，信息更散。

**n=2 判不动**，但方向值得后续扩大样本后确认。

## 五、与 hit@k 的关系（待在全量数据上验证）

之前 B2（487 条）的 `hit@1 = 0.3760 / hit@10 = 0.7872`。
现在合成集 37 条的 `context_recall = 0.4414`。

**两者不可直接比**（不同数据集、不同口径）。但**同时报告两个指标**能回答：
- hit@10 高但 recall 低 → 找到了位置但内容不够
- hit@10 低但 recall 高 → 没找到标注块但内容其实够

**这是目标要求的「覆盖检索质量的完整两面」。**
