# 「表格 83% 丢失」的真正机制：换行符被吃掉，不是分块切碎

> 日期：2026-11-09｜触发：阶段5 Agent 报「表格管道符保留率 0.1704，约 83% 表行丢失」
> 我核实后发现**根因比它说的更严重**

## 一、Agent 的发现是对的

`scripts/audit/p114_rag_layered_eval.py` 的 `table_pipe_conservation = 0.1704`：
源侧 684 行有实质内容的表格行，进 KB 后只剩约 17%。

**我核实了源侧质量，确认这不是"垃圾被正确丢弃"**：
```
源侧含 | 行总数: 710
  有实质内容 (>=4 字符): 684 = 96.3%
  垃圾空管道 (<4 字符): 26 = 3.7%
```
有内容的样子：`|参数|总数<br>n=678|18~29岁<br> n=128|30~39岁<br> n=118|...`
**96.3% 是真表格，所以 83% 丢失是真问题。**

## 二、但根因不是「分块切碎」，是「换行被吃」

### 决定性证据

```
源 json:  pdf_cardiac_cardiac_echo_measurement_2016_0010.json
          长度 2347，换行数 21
          内容片段: '|||||男性|||||\n|---|---|---|---|---|---|---|---|---|\n|参数|总数<br>n=678|...'

KB chunk: 60 个 chunk 的**换行总数 = 0**
          平均每 chunk 0.0 个换行
```

**源文档有换行（21~136 个），进 KB 后一个都不剩。**

### 这意味着什么

KB 里每个 chunk 都是**一整行连续文本**：
```
长度 1125 字符，行数 1
长度 1528 字符，行数 1
长度 1319 字符，行数 1
```

**表格不是被"切碎"了，是被"压平"了** —— 所有换行消失，`|a|b|c|` 和下一行 `|d|e|f|`
连成了 `|a|b|c||d|e|f|` 这样一长串。

**表格结构彻底消失，任何按行解析的表格识别都失效。**

## 三、为什么这比"分块切碎"更严重

| | 分块切碎 | 换行被吃（实际） |
|---|---|---|
| 原表格行 | 分散在多个 chunk | **全部挤在一个 chunk 里，但无法区分行** |
| 能否修复 | 合并相邻 chunk 即可 | **需要重新从源 PDF 抽取** |
| 影响范围 | 只影响被切断的表 | **影响所有含表格/列表的文档** |
| 检索影响 | 一个表拆成几块，可能命中其中一块 | **表头与数值粘在一起，语义被破坏** |

**而且这解释了另一件事**：为什么 `句末完整率` 只有 0.3272 ——
因为换行没了，分块器看到的是一整段无标点长文本，无法按句/段切。

## 四、根因链

```
pypdf 抽取（PyMuPDF/pypdf 对表格的换行处理不稳定）
  → 清洗脚本把 \n 去掉或替换成空格（设计意图可能是"去掉 PDF 的硬换行"）
  → 源 json 里表格行的 \n 还在（21 个），但正文的 \n 可能已被吃
  → 建库时按 \n 切分 → 由于 \n 少，chunk 内容基本是"一坨"
  → KB chunk 换行数 = 0
```

**需要查的是清洗脚本（`scripts/kb_build_v15_docs.py` 或 `server_assemble_kb_v1.sh` 里的 `re.sub`）**。

我记得 `server_assemble_kb_v1.sh` 里有：
```python
text = re.sub(r'\n\s*\d+\s*\n', '\n', text)   # 去页码
```
这类正则不会吃掉所有换行。**但可能还有别的清洗把 `\n` 换成了空格。**

## 五、修复方向

### 短期（不改现有 KB）
在**分块器**里识别「被压平的表」：
- 检测连续 `|...|...|` 模式（即使在一行内）
- 按 `|` 边界重新切行

### 根治
1. **查清洗脚本**，找出吃掉 `\n` 的那一步
2. **改用 MinerU 的 markdown**（它保留 `##` 层级与换行）
3. 重建 KB

### 验证标准（可机检）
```
KB chunk 的平均换行数 > 0     ← 现在是 0
含 | 且行数 > 1 的 chunk 数 > 0  ← 现在基本是 1 行
```

## 六、对阶段5 Agent 的口径建议

它的 `table_pipe_conservation` 指标本身**设计是对的**（源侧/chunk 侧比行数），
但结论表述建议改：

**它说**：「83% 带 `|` 的表行在分块后不见了」

**更准确的表述**：「83% 的表行在写入 KB 后不可区分 —— 因为**换行符被清洗掉，chunk 被压成一整行**，表格结构消失。这不是分块切的，是上游清洗的问题。」

## 七、我此前的判断需要修正

我此前说「表格被分块切碎」——**这个判断不准确**。

真实情况是：
- pypdf 抽出的表格行**确实破碎**（`|||||男性|||||`）
- 但真正致命的是**换行被吃**，导致连破碎的行都无法区分

**这是我这几天第四次在「表格」这件事上判断失准**（前三次：TR 编号、全角/半角、orphan 表格）。
共同点仍是：**没有先看数据本身长什么样就下结论。**

**新纪律**：报任何「X 丢失/被破坏」之前，**先 print 一段原始数据看它的真实形态**。
