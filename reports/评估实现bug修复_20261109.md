## 已修（3 个）

### BUG-1（P0）：`p94b_retrieval_ab.py` 的 NDCG 没有去重 —— **同类错误复发**

`p94` 的 NDCG 我修过（加 `seen` + clamp），但 **`p94b` 漏了**。

实测复现：
- 同一 gold 出现 3 次 → `ndcg = 2.1309`（数学上不可能）
- 一个 gold 出现 2 次排 rank2 → `1.1309`
- 随机 5000 例：**2392 例 > 1**

**危害**：`p94b` 是 12 份已发布 A/B 报告的产出脚本。那 12 份报告里越界 0 条，
**只是因为 kb 限定到 v1.4.0 后没有重复副本 —— 是数据运气，不是代码正确**。
现在 DB 里确实有 8 个版本，语料一变就会复现。

**已修**：`seen` 去重 + clamp。

### BUG-2（P0，生产代码）：`rag_quality.py` 的 NDCG 同样没去重

`ndcg_at_k(['x','a','a'], {'a'}, 10)` 原实现返回 `1.0`（正确 `0.6309`）。

**它的 `min(..., 1.0)` 只兜住上界，兜底≠算对** —— 把本应 0.6309 的抬成 1.0，
是「静默算错」的隐蔽形态。生产 RAG 链路真实在调（`app/rag/service.py`）。

**已修**：`seen` 去重。

### BUG-5（P1）：`precision_at_k` 的 docstring 与实现不一致

docstring 写 `/ k`，实现是 `/ len(top)`。

**我的判断与 Agent 不同**：Agent 说 `precision_at_k(['a'], {'a'}, 10)` 应为 0.1。
但生产调用是 `precision_at_k(ranked, relevant, top_k)`，`ranked` 是**实际检索返回的列表**，
可能不足 k 个。两种口径：

| 口径 | 值 | 语义 |
|---|---|---|
| `/ k`（固定） | 0.1 | 把「召回不足」算成「精确率低」 |
| `/ min(k, len)` | 1.0 | 「返回的那些里准不准」 |

本函数服务的是**在线质量监控**，关心「这次返回的东西准不准」，
而「召回够不够」是 `recall_at_k` 的职责。**所以保留 `/ min(k, len)`**，
但把 docstring 改成与实现一致，并写明这是本场景的刻意选择（与经典 IR 定义不同）。

## 未修（1 个，属实但影响面小）

### BUG-3：`p94_b2_retrieval_eval.py` 的 gold 解析分支永不触发

```python
gold_ids.add(f"{doc}#{ci:04d}" if "#" not in doc else doc)
```
当 `doc_id` 含 `#` 时**直接丢掉 chunk_index**，等于把 chunk 级口径降级成 doc 级。

B2 当前 120 条 doc_id 都不含 `#`，所以现在不咬人。**这是"golds 写法一变就静默错"的雷。**

**未修原因**：需要先定「doc_id 含 `#` 时该怎么处理」的语义 —— 是剥离 `#` 还是保留？
这要跟 B2 数据集的命名规范一起定，不是单点改。

**未修原因**：属于「补功能」不是「修 bug」，归到阶段5 的评估体系重建里。
