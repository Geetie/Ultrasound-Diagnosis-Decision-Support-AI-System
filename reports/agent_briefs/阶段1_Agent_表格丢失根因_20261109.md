# 致阶段1 Agent：表格丢失的**真正根因**（换行被吃，不是分块切碎）

阶段5 Agent 的 `p114` 测出 `table_pipe_conservation = 0.1704`（83% 表行丢失）。
我核实后确认**这个发现是对的**，但**根因不是分块切碎**，而且比那更严重。

## 源侧质量确认：不是垃圾被正确丢弃

```
源侧含 | 行: 710
  有实质内容 (>=4 字符): 684 = 96.3%
  垃圾空管道:            26 = 3.7%
```
有内容的样子：`|参数|总数<br>n=678|18~29岁<br> n=128|...`

**96.3% 是真表格 → 83% 丢失是真问题。**

## 决定性证据：换行符被吃光

```
源 json (cardiac_echo_measurement_2016_0010.json):
  长度 2347, 换行数 21
  片段: '|||||男性|||||\n|---|---|---|\n|参数|总数<br>n=678|...'

KB chunk (同文档 60 个 chunk):
  换行总数 = 0
  平均每 chunk 0.0 个换行
```

**KB 里每个 chunk 的「行数 = 1」**（实测：长度 1125 字符 / 行数 1、1528/1、1319/1）。

**表格不是被"切碎"，是被"压平"** —— `|a|b|\n|c|d|` 变成 `|a|b||c|d|` 一整串，
行边界消失，任何按行解析的表格识别都失效。

## 这对你的工作意味着什么（重要）

### 你的「表格保护」策略在当前语料上注定失败

如果你在分块器里加「识别 `表N` / 连续 `|` 行 → 整表作为一块」——
**但当前源 json 里表格已经被压平在正文中**，你的正则找不到「连续 `|` 行」，
因为根本没有多行，只有一行超长的。

### 所以正确顺序是：
1. **先修换行**（上游）→ 表格能重新按行区分
2. **再做表格保护**（分块器）→ 才有东西可保护

### 这也解释了你 A/B 里另一个数字：句末完整率 0.3272

换行没了 → 分块器看到的是一整段无标点长文本 → 无法按句/段切 → 句末完整率低。
**这和表格丢失是同一个根因。**

## 建议你调整工作重点（按优先级）

| 序 | 做什么 | 理由 |
|---|---|---|
| 1 | **查清洗脚本吃掉 `\n` 的那一步** | 这是根因。`scripts/kb_build_v15_docs.py` / `server_assemble_kb_v1.sh` 里的 `re.sub` |
| 2 | **改用 MinerU 的 markdown 作为源**（保留 `##` 与换行） | 比修 pypdf 的清洗更彻底 |
| 3 | **验证标准变成可机检**：KB chunk 平均换行数 > 0（现在是 0）、含 `|` 且行数 > 1 的 chunk 数 > 0 | 这两个指标一测就知道修没修好 |
| 4 | 再做表格保护 | 有了换行才有意义 |

## 对你 A/B 的影响

你的 A/B 是「pypdf 语料 → 新分块器」vs「pypdf 语料 → 旧分块器」，
**但两臂用的都是「换行已被吃」的语料**。
在这种语料上，任何"结构感知"分块都发挥不了作用 —— 因为**没有结构可感知**。

**所以你的负增益结论，很可能测的是「在无结构语料上强行做结构分块」的必然失败**，
而不是「结构分块本身不好」。

**建议先把换行修好，再重做 A/B。** 那才是有意义的对比。
