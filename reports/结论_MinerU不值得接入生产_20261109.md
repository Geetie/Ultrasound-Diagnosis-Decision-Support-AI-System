# 结论：MinerU 在当前语料上不值得接入生产（pypdf 表格结构更好）

> 日期：2026-11-09｜推翻了**我自己**前几轮的判断

## 一、我之前的判断是错的

我在这几轮里多次说：
> 「pypdf 会丢表格，MinerU 更可靠」

**实测证明这个判断不成立。**

## 二、关键数值完整性：完全打平

拿 C-TIRADS 2021（最关键的一份）做对照，逐项检查表 1 分档 + FNA 阈值：

| 关键项 | pypdf | MinerU |
|---|---|---|
| 表1-4A档(2~10) | ✅ | ✅ |
| 表1-4B档(10~50) | ✅ | ✅ |
| 表1-4C档(50~90) | ✅ | ✅ |
| 表1-5类(>90) | ✅ | ✅ |
| 4A FNA阈值(15mm) | ✅ | ✅ |
| 多灶/被膜(10mm) | ✅ | ✅ |
| 4B/4C/5阈值 | ✅ | ✅ |
| 恶性率表头 | ✅ | ✅ |
| 分值词 | ✅ | ✅ |
| 分类列 | ✅ | ✅ |
| **命中数** | **10/10** | **10/10** |

## 三、决定性证据：pypdf 的表格结构更好

```
pypdf 的表 1：
  |无结节|无分值<sup>*</sup>|0|1 <sup>无结节</sup>|
  |有结节|-1|0|2 <sup>良性</sup>|
  ||0|<2|3 <sup>良性可能</sup>|
  ||1|2~10|4A<sup>低度可疑恶性</sup>|
  ...

MinerU 的表 1：
  无结节 无分值*      0     1 无结节
  有结节    -1     0     2 良性
         0      <2    3 良性可能
         1     2~10   4A 低度可疑恶性
  ...
```

**pypdf 输出的是标准 Markdown 管道表（有 `|---|` 分隔行）；MinerU 是空格对齐的等宽文本。**

结构特征统计：
| 特征 | pypdf | MinerU |
|---|---|---|
| Markdown 管道表 `\|---\|` | **4** | **0** |
| HTML `<br>` 残留 | 1 | 0 |
| HTML `<sup>` 残留 | 746 | **234** |
| 换行数 | 779 | 910 |

→ **MinerU 唯一优势是 `<sup>` 残留更少（234 vs 746），代价是丢失了管道表结构。**

## 四、为什么我之前判断错了

我看到的证据是：
```
pypdf 抽取:  '85%～<br>100%'
MinerU 抽取: '>90   5 高度提示恶性'
```
于是得出「MinerU 更好」。

**但我后来实测发现**：
1. `85%~100%`（半角）在 KB 里有 **13 条**，是我探测时用了全角 `～` 才显示 0
2. `kb_v2.1.0` 建库后换行数 **32.47/块**，表格行可区分 **101 个 chunk**

**换行 bug 才是真问题，修好后 pypdf 的表格完全够用。**

## 五、结论与决定

**决定：不接入 MinerU 到生产建库。**

理由：
1. 关键数值完整性打平（10/10 vs 10/10）
2. **pypdf 的表格结构更好**（4 个管道表 vs 0 个）
3. 接入 MinerU 需要：25 份 PDF 全部重解析 + 输出格式适配（代码块表格 → 管道表）+ 重建库 + 重测
   —— **成本高，收益为负或持平**
4. 阶段 1 Agent 的 A/B 实测也是「结构化分块负增益」，与这个结论一致

**保留 MinerU 作为备选**：若将来遇到 pypdf 确实读不出的文档（扫描件、复杂公式），
再单独用 MinerU 处理，不做全量切换。

## 六、这是一个值得记住的教训

**我连续 4 轮说「MinerU 优于 pypdf」，但从未做过同等条件下的关键数值对照。**

真正做了对照（10 项关键值逐项查）后，结论是**打平甚至 pypdf 更好**。

这与我这个项目里犯的其他错误同源：
- 看到局部证据（`85%~100%` 0 条、`<br>` 残留）就下全局结论
- 没有先问「用同一把尺子量两个对象，结果如何」

**新纪律**：比较两个方案时，**必须先定义一组可机检的判据，逐项对照，再下结论**。
不能用"我看到的某个例子"代替对照。
