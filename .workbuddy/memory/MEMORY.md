## 1. 前端设计治理准绳（用户明确要求 · 强制）

**原话**：医生作为用户群体，系统应当**只给他们想要看到的东西**。越清晰越简洁越好，越少操作越好。

三条可观测准绳（完整版与逐元素裁决见 **17-医生侧展示契约**）：

| # | 准绳 | 判据 |
|---|---|---|
| P1 | **默认沉默** | 元素仅在「缺了它医生会做错」时才默认可见；其余**不渲染**（不是折叠、不是灰掉） |
| P2 | **一次决策** | 任何时刻医生**只需做一个决定**；两个并列待选动作 = 设计失败 |
| P3 | **按打扰总量记账** | 「操作少」= 被打断次数 × 解除成本，**不是元素个数**。为减少打断而增加按键，算**减法** |

**P3 必须与新需求同时提及**，否则简化会误伤两类设计：冻结/存图拆分、禁忌命中的强制勾选。二者都是净减法。

**不可削减的三条边界**：禁忌命中的强制勾选 · 签发前的依赖度核验 · 诊室可见性默认遮蔽。

**导出时踩到并修掉的两个坑（可复用）**：
1. **别用 0–1 浮点凑近似值**：我按 `0.11, 0.12, 0.14` 填色，导出成 `#1C1F24`，而设计文档写的是 `#1B1E23` —— **差 1 步，等于制造了第二个真相源**。正确做法：用 `hex值/255` 的精确浮点（`27/255=0.105882`）。
2. **token 命名语言要跟代码走**：第一版导出是中文名（`--色彩-bg`），在 TS/Tailwind 工程里别扭；改成英文时**必须用 `replace: true` 整体替换**（否则中英两套集同时存在 = 又一个双真相源）。实测 `replace: true` 返回 `created 44 / deleted 6`，旧集被清干净。
3. 导出给的是 **URL 不是本地路径**，需要 `curl` 下载；下载时**重命名为语义文件名**（`S01-工作列表-深色.png`），不要留 `2_56-时间戳.png` —— Agent 读不懂那种名字。

**交接契约里最容易被做错、已写进 README 的一条**：**"按规则不渲染" ≠ "设计漏画"**。必须显式告诉实现者哪些"缺失"是正确的（S02 无同意/连接状态、S04 无部位标签排、S07 无报告状态行、全稿无绿色…），否则实现者会**照着"补全"**，把设计规则全部破坏。

### 2.3 绘制期实测的工具行为（可复用）

1. `capture_layout` 的 `parentId` **必须是容器帧，不能传页面**（传页面报 `Root node must be a container`）。
2. **改 `textAutoResize` 不会重排已冻结的 hug 父框** —— 文本折行的正确修法是给文本**显式宽度**（对父框改 `fill_container`），不是改 autoresize。
3. **`C()` 的 `descendants` 覆盖会静默失败**：报 `Copy descendant not found: <新帧ID>/<旧子ID>`，因为复制后子节点是新 ID。正确做法：`batch_read` 新帧拿真实子 ID，再用 `U()` 改。

## 3. 两条已验证的工作纪律（本机实测，勿违反）

### 3.1 双证据硬门 + 不信返回码
- 任何「已落地 / 无问题 / 已对齐」的结论，必须同时有：**① 工具返回** 与 **② bash 侧独立取证**（`ls -l` 字节数 + mtime、`grep -c` 标记计数、`wc -l` 交叉验证）。
- **实测事故**：`Edit` 逐条返回 `Successfully edited`，但磁盘一处未落——文件被外部写回旧缓冲（27,075 B 的残缺版本，§7 整节缺失）。**Read 工具输出也可能落在外部写回之前。**
- **因此**：长文档不靠多次增量 `Edit` 累积（增量链一断就找不到丢失边界）；改动后用 bash 取证，不信返回码。
- **若该 .md 可能被用户端编辑器打开**，先提醒关闭再改，否则可能再被覆盖。

### 3.2 阴性结论必做阳性对照
「工具没命中」与「代码里真的没有」**现象完全相同**。凡下"零命中 / 未集成 / 不存在"这类否定性结论前，先用一个**必然存在**的串验证检索生效。
- 本机实例：核"前端零集成 report/multi-organ/confirm-upgrade"时，以 `requestDiagnosis`（命中 3 处）作对照，确认是真阴性。

### 3.3 给用户的选项必须"可判"

**不得把一个决定的差别留给用户去猜。** 选项必须带上"选它会看到什么"的具体后果——屏幕变化、工作量差、标准取舍。

- 本机实例：语义色「四级 vs 两级」被选错一次。**根因不是用户，是选项**：写成"删绿 vs 保留绿"，却没说明"**绿其实在回答另一个问题**（是否已确认），不是第四个颜色档"。
- **判据**：用户能否仅凭选项文字，做出与自己意图一致的判断？不能 ⇒ **是选项的问题，不是用户的问题**，应当先解释再问。
- 延伸：凡建议**删除某个标准 / 惯例元素**，必须先说明"删了之后替代物是什么、代价由谁承担"，再问。

## 4. 已锁定的设计决策（摘要，正文见 14 / 17）

- 交互模型：**「扫查 ⇄ 判读」循环** ＋ 报告侧面板（**不是**三阶段线性推进）。
- 判读触发：**冻结即判读**；**按部位去重**；冻结 / 存图（静默）/ 存图并分析 三键分离。
- 一级导航 **2 项**；诊室可见性**默认遮蔽** ＋ 切患者清屏。
- 语义色 **两级 ＋ 默认无标记**（v5 复盘重判）：「**停**」红 / 「**看一眼**」中性青灰 / 正常**不渲染**。**绿不是第四个颜色档，而是"是否已确认"这一类问题的答案**——医生主链改用「图标＋文字」（`✓ 已核验`），**绿移至质控／管理面**（那里"主动宣告达标"是真实需求）。由此 `08-A6` 红绿配对**在医生侧消解**，但该约束随绿一起搬到质控面。
  - **合并依据**：橙（软警告）与青灰（不确定）在"医生要做什么"上完全一致（看一眼、不挡），差别只在**原因**，而原因属于**文字**不属于颜色。
