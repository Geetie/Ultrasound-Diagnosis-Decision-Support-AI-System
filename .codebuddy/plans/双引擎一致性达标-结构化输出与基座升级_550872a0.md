## Product Overview

攻关双引擎一致性 P0 门控（当前 780 例真机评测分级一致率 23.33%，目标 ≥95%）。按已确认的达标路径分三步：A1 消除输出格式噪音（结构化分级输出 + 抽取器扩展），A2 消除推理栈差异（两引擎统一 chat 端点与解码参数），A3 复测并视结果升级基座（Qwen2.5-7B 双引擎），最终产出“达标”或“二期模型选型依据”的明确结论。

## Core Features

- **A1 分级抽取扩展**：`grading_definitions.py` 补充 TR 码（TR1-TR5，专项 prompt 输出格式）、"3 级（TI-RADS）"括号变体、英文表述（mildly_reduced→mild 等）的正则覆盖与归一化，消除 61 例提取失败
- **A1 结构化输出约束**：一致性评测路径给两引擎统一追加“仅输出 JSON：{"grading": "…"}”的指令模板；解析时优先 JSON 字段、正则兜底；保持既有行为向后兼容（可配置开关）
- **A2 统一推理栈**：LlamaCppEngine 支持 `/v1/chat/completions`（llama.cpp server 原生支持），一致性评测统一两引擎走 chat 端点 + 完全相同解码参数（temperature=0.0、同 top_p、同 max_tokens），消除“裸 prompt vs chat 模板”与量化采样差异中可控制的部分
- **A3 复测与基座升级**：真机重跑 780 例对比 23.33% 基线；若仍 <95%，下载 Qwen2.5-7B-Instruct（GGUF Q4_K_M + vLLM 用权重）替换 8001/8002 基座，核算 48GB 显存预算后复测
- **结论固化**：报告归档 + SKILL/豁免清单/16 号文档更新 + git 提交

## 验收标准

- A1：抽取扩展带守卫单测（含真机 61 例提取失败的实际输出样本形态）；全量本地单测不回归
- A2：两引擎在同一用例上的响应格式可被同一解析器处理；真机 8001/8002 chat 端点健康
- A3：780 例报告落盘 `~/uai/reports/` 并归档本地 `tests/reports/`；产出量化对比（基线 23.33% → 各阶段数值）与达标/未达标结论及依据

## Implementation Approach

1. **A1 抽取扩展（低风险，先做）**：`grading_definitions.py` 的 `_GRADING_PATTERNS` 按 organ 追加模式——thyroid/liver 增加 `TR[-_ ]?(\d[a-zA-Z]?)`（专项 prompt 的 TR 码与 TI-RADS 数字码同义）、`(\d[a-zA-Z]?)\s*级\s*[（(]TI`、英文 `TR\d[a-z]`；cardiac 增加 `mildly_reduced|moderately_reduced|severely_reduced`→mild/moderate/severe 归一。每条模式配正反例单测（正例含真机失败样本形态，反例防误抽如"TR2 随访"外的其他数字）。**不做**模糊匹配——抽取仍失败就如实计 extraction_failure，不伪造一致。
2. **A1b 结构化输出（verifier 层，可配置）**：`ConsistencyVerifier` 增加输出格式包装开关（默认沿用裸 prompt 以保兼容；`scripts/consistency_verify.py` 加 `--structured-output` 启用）：prompt 末尾追加统一指令段（要求最后一行输出 `分级: <TR3/4a/…>` 或 JSON），两引擎收到**完全相同**的指令文本。解析优先匹配该行/JSON 字段，回退既有正则。指令模板放在 `app/inference/consistency/` 下作为常量，两引擎共用同一份（DRY）。
3. **A2 统一 chat**：`LlamaCppEngine` 增加对 `/v1/chat/completions` 的支持（构造参数 `use_chat=True` 或按 endpoint 配置；payload 改 messages，解析取 `choices[0].message.content`），llama.cpp server 原生支持该端点无需改服务。`consistency_verify.py` 创建引擎时统一 `use_chat=True` 并把同一解码参数（temperature=0.0、top_p、max_tokens=512）显式传两引擎。工厂 `create_inference_engine` 透传参数。守卫：payload 构造与响应解析单测。
4. **A3 复测→基座升级（真机）**：先部署 A1+A2 代码重跑 780 例（concurrency 4，约 30 分钟）。若 <95%：经 hf-mirror 下 Qwen2.5-7B-Instruct 的 GGUF Q4_K_M（约 4.7GB）与 vLLM 用 fp16/AWQ 权重；核算显存（7B Q4 约 5GB + vLLM 按 utilization 上调至 ~16GB，与 8003/8004/8005 共存于 48GB 无压力），重启 8001/8002 换基座，再跑 780 例。两份报告均归档。
5. **性能与可靠性**：评测进程独立 nohup 落盘日志防中断；报告即时写盘（verifier 已支持）；GPU 服务重启遵循幂等脚本模式。

- Purpose: 精读 `app/inference/consistency/verifier.py` 的 InferenceRequest 组装与 `app/inference/factory.py`、`llama_cpp.py`/`vllm.py` 的 payload/解析细节，确定 chat 统一改造与结构化输出开关的最小侵入点；梳理 61 例提取失败的实际输出形态
- Expected outcome: A1/A2 改造的精确实现依据（函数签名、调用链、既有测试锚点）
